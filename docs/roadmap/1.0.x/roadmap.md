## 0. 铁律与定位

### 0.1 定位句（改动必须同步五处）

> **配置不再有动词：同一个名字读它、写它，两个方向都不丢——不丢一个字节，也不丢一次更新。**
>
> `Configuration has no verbs: one name reads and writes it, in both directions, without losing a byte or an update.`

英文与中文同源；改一句必须同一次改完这五处：`README.md`、`README.zh-CN.md`、
`pyproject.toml` 的 `description`、`mkdocs.yml` 的 `site_description`、`docs/index.md`。

### 0.2 四条铁律

| 铁律 | 含义 | 状态 |
|---|---|---|
| **文件绝对优先** | 代码不权威，代码只发出写请求；运行期对已存在的值一律只读（不一致只记一条 `op=skip`） | `已实现` |
| **未触及的字节逐字不动** | 回写是外科手术式的：注释、缩进、键序、空行、行尾都保留。词表是例外 —— 它是库自己的资产，整篇重写合法 | `已实现` |
| **不丢一次更新** | 一个配置目录上只有一个执行点（现在是进程内写者线程；2.0 改成独立 Alpha）；锁内按需重读；落盘原子 | `已实现`（进程结构见 §6） |
| **不是服务、不走网络** | 库跑在调用方进程里；默认路径不开端口、不 spawn 子进程 | `已实现` |

### 0.3 两个面（公开 API 只有这两个）

```python
AutoConf(**engine)              # 配置引擎自己（引导层，起来后不可改）
conf(key, value=…, doc=…)       # 读 / 写 / 登记（三种模式）
```

`__all__` 共 8 个符号：`AutoConf`、`conf`，加 `Engine`、`EngineParams` 与四个异常
（`ConfError` / `KeyNotRegisteredError` / `KeyHasNoValueError` / `UnknownEngineParamError`）。
`LockTimeoutError` 在 `_lock.py`，各后端的语法错误是 `ValueError` 子类 —— **接不住 `except ConfError`**。

## 3. 配置面：使用口 `conf` 与配置口 `AutoConf`

### 3.1 使用口的三种模式与判据

- **已定**：签名收敛为 `conf(key, value=MISSING, doc=None)`，返回 `Any`；判据**只看 `value` 位是否填写**（`None` / `""` / `0` 都算填了，`MISSING` 是唯一哨兵）。
  - 依据：每新增一个参数都要往判据里追加合取项，参数面无法封闭。
  - 状态：`已实现`｜出处：D01 §1 / ISSUE-001
- **已定**：五种写法与模式一一对应 —— `conf(key)`=读；`conf(key, value)`=声明+写；`conf(key, value, doc)`=声明+写+登记说明；`conf(key, doc=…)`=只登记（空结构）随即按读规则取值；`conf(key, value, doc=…)`=模式 1。
  - 依据：第 2 位置恒属 `value`，`conf(key, x)` 永远是模式 1；模式 2 只能由 `doc=` 触发，没有位置写法。
  - 状态：`已实现`｜出处：D01 §1 / ISSUE-001
- **已定**：参数面自此封闭（判据里不再出现 `doc` / `type` / `force`）；模式 1 的两种写法等价，只在是否同时登记说明上有差别。
  - 状态：`已实现`｜出处：D01 §1 / ISSUE-001
- **已定**：报错与返回值口径 —— 读未登记 ⇒ `KeyNotRegisteredError`；已登记但事实里没有值 ⇒ `KeyHasNoValueError`；模式 1 返回**事实里的值**（不是传入的默认值）；`key` 不是字符串 ⇒ `TypeError`。
  - 依据：两类错误责任方不同（键名写错 vs 部署漏配）。
  - 状态：`已实现`｜出处：D01 §1 / ISSUE-001
- **曾考虑但判否**：`conf(key, type=int)` 作为第四种形态 —— 它是判据里多出来的合取项所放行的形态，随 `type=` 删除出局（D01 §1 / ISSUE-001）。

### 3.2 「创建」与「覆盖」不再由 `conf` 区分

- **已定**：`force=` 从 `conf` 移除；模式 1 遇到事实里已有不同值时按「尊重文件」处理（`op=skip`，值文件逐字不动）。
  - 状态：`已实现`｜出处：D01 §1.2 / ISSUE-001
- **已定**：覆盖既存值只由**人**发起 —— `onconf build` 按声明**完整重建**值文件与词表（`--path` 换输出目录、原目录不动）；`onconf sync` 只补缺 + 更新词表 + 删除未声明的键、**不覆盖既存值**，`--no-clean` 关掉删除。
  - 依据：「运行期采用增量更新，不会动原始的项的键值；只有命令行才可以获得完整的能力」。
  - 状态：`已实现`｜出处：D01 §1.2、§3 未决 (c)（本轮裁定）
- **已定**：判据不是「能不能覆盖」，而是「**谁发起**」：程序发起只补缺，人发起才可以收敛。
  - 状态：`已实现`｜出处：同上
- **曾考虑但判否**：(a) `AutoConf` 上的动词方法（`engine.overwrite(...)`）—— 方法名/返回值/与声明元数据的登记关系要逐个定义，且 `AutoConf` 从参数类型变成带状态的对象；(b) `conf` 上保留显式透传参数 —— 与「`force=` 离开 `conf`」相反，在温和面上再开一个洞；(c) 不给出口 —— 「程序想持久化一个值」整类场景被砍掉，现由 `build` / `sync` 承接（D01 §3 未决 (c) / ISSUE-003）。

### 3.3 使用口不得配置引擎

- **已定**：`**engine` 从 `conf` 摘除，引擎参数只走配置口；`conf(..., home=…)` 之类已摘除参数抛 `TypeError`，不再静默降级；`AutoConf(**engine) if engine else _engine` 的分派删除，使用口直接取单例。
  - 依据：「一个配置口、一个使用口」不依赖「引擎是否已经起来」这一时序条件。
  - 状态：`已实现`｜出处：D01 §1.4 / ISSUE-001

### 3.4 使用范式：声明处必须字面量（**合法但不合理**）

- **已定**：**声明形态**（`value` 位填了的调用）的键、值与说明都必须是**字面量**；**读取不受限制**（常量、拼接都行，错了当场 `KeyNotRegisteredError`）。
  - 依据：键字符串就是配置项的身份 —— 值文件的键、词表的键、`$schema` 补全、日志 `item=`、命令行扫描认的都是它。
  - 状态：`已实现`（文档：README 一对 + 快速开始 + 设计页）｜出处：D01 §1（本轮裁定）
- **已定**：**不设门禁** —— Python 合法、在本库不合理（error 的分界是「不合法」）；只在文档里写清代价，未来 `check` 按同一判据出 **warning**。
  - 依据：「我们没有办法进行检查和约束……只能在文档里面写清楚……需要自行去决定」。
  - 状态：`已实现`（文档）；`check` 的 warning 属 `2.0`｜出处：ISSUE-051 / ISSUE-053
- **已定**：非字面量实参（`APP_POST = "app.post"; conf(APP_POST, 8080)`、循环、表达式）**不在支持范围内**：不解读、不求值，一律进问题清单；唯一承诺是「不静默丢」。
  - 状态：`已实现`｜出处：D01 §1（本轮裁定）
- **代价（用不用自定）**：命令行看不见它（`sync` 把它当「代码没声明」，并因此拒绝删除任何键，可加 `--no-clean`）；`grep` 与未来的 `check` 覆盖不到；声明点不再自证（计算值与说明看不见）；循环/数据结构形态额外丢掉「从代码回答有哪些配置项」的能力。

### 3.5 配置口参数面的总原则与四组

- **已定**：总原则 =「**凡是引擎的默认行为，都必须是一个能显式声明、能覆盖、能关闭的参数**」；`DESIGN.md` §9.1 把「隐式约定」当作换取「轻」的取舍，该定性作废。
  - 状态：`已实现`（原则成立）｜出处：D01 §3 / ISSUE-003
- **已定**：参数面按性质分四组 —— A 组能力开关、B/C 组文件与路径、D 组日志审计与落盘、引导层/值层二分。
  - 状态：`已实现`（分组已落地）｜出处：D01 §3 / ISSUE-003
- **已定**：词表**不在开关之列**（锁死的核心数据结构，「关掉词表」不存在）；开关关闭 = **该能力完全不参与**。
  - 状态：`已实现`｜出处：D01 §3.1、D03 §2 结论 1 / ISSUE-003、ISSUE-009
- **已定**：终端日志开关（默认**开**）：关闭只影响终端那一份，**文件通道强制**。
  - 状态：`2.0`｜出处：D01 §3.1 / ISSUE-003、ISSUE-005
- **已定**：`audit` 开关**取消**：审计文件恒写，路径改为独立参数，默认 `<home>/audit.log`。
  - 状态：`2.0`｜出处：D01 §3.1、§3.4 / ISSUE-003、ISSUE-005
- **已定**：终端可按**级别词筛选**（只刷 `Change` / 只刷 `Write` / 全刷）；文件通道**永远全量**、不可关。
  - 状态：`2.0`｜出处：D01 §3.3 / ISSUE-005
- **已定**：落盘形式可配（明文默认 / 纯二进制 / 二进制加密 / 明文加密）；加密的算法与密钥由调用方指定，**缺失且必需时抛异常**，引擎不生成、不推导、不保管；轮转 = 落盘规则 / 触发方式 / 轮转方式**三组参数**。
  - 状态：`2.1+`（加密还须先定密钥/算法形态）｜出处：D01 §3.3 / ISSUE-039、ISSUE-041、ISSUE-043
- **已定**：库**不发起网络请求、不收函数式 sink**，职责到「产出数据」为止。
  - 状态：`已实现`（无网络调用，也无 sink 入口）｜出处：D01 §3.3 / ISSUE-005、ISSUE-043

### 3.6 引导层与值层

- **已定**：引导层（`home`、`file_name`、`file_type`、`no_one_file`、`log`、`audit`、`identity`、`flush_window`、`lock_timeout`，以及未来的落盘形式/加密）**不可运行中改**；引擎起来后再带参调用 `AutoConf(...)` 抛 `ConfError`。值层每次从文件重新读。
  - 依据：「如果是配置文件的配置口那无所谓；如果是指初始化配置的形式，改不了一点儿，改了就得重启」。
  - 状态：`已实现`｜出处：D01 §3.4 / ISSUE-003
- **已定**：`DESIGN.md` §15.3「单例可变的必需品」定性**作废**；抛 `ConfError` 行为保留，理由改为「按设计不支持」。
  - 状态：`已实现`｜出处：同上

### 3.7 其余收敛（`home` / `lock_timeout` / 单例 / `__all__` / `.gitignore`）

- **已定**：`home` 缺省从 `.` 改为 `./conf`；`lock_timeout` 补进 `EngineParams`（行为不变，只补可见性）；`AutoConf()` 无参调用保留「取回单例」语义并写进文档；「两个面」的说法与 `__all__` 对齐、异常族保持从顶层可导入；`.gitignore` 按新缺省收窄兜底。
  - 状态：`已实现`｜出处：D01 §3.5、§3 变更项 / ISSUE-003

## 4. 值文件、路径与后端

### 4.1 声明粒度：目录 + 名称 + 类型

- **已定**：目录 `<home>`（参数）、文件名称 `<name>`（参数，多文件时内嵌在键里）、文件类型 `file_type`（参数、单值）、文件路径 `<home>/<name><ext>`（派生）。
  - 状态：`已实现`｜出处：D01 §3.2 / ISSUE-003
- **已定**：文件名主干由 `file_name` 给（**纯文件名**，缺省 `settings`，可显式指定）；`_VALUES_CANDIDATES` / `_pick_values_file` 的「按存在性挑第一个」退役，候选顺序不再参与判定。
  - 依据：不再把「哪个文件生效」交给磁盘上恰好有什么。
  - 状态：`已实现`｜出处：D01 §3.2、§5 / ISSUE-003、ISSUE-054
- **已定**：`file_type` 是**单值**参数，一次只有一个类型，决定实际使用的配置文件与后缀；缺省值是**字面 `"json"`**，`""` **不再是合法取值**（抛 `ConfError`）。
  - 依据：「不是不填就代表没有，而是采用默认参数形式……默认的文件类型就是 json」。
  - 状态：`已实现`｜出处：D01 §3 未决 (a)、§5 未决 1 / ISSUE-054
- **已定**：多文件用**键内嵌路径**表达（`conf("app/conf/net:net.id.post")`），**不新增路径参数**。
  - 状态：`已实现`｜出处：D01 §3.2 / ISSUE-008

### 4.2 「以 JSON 为主」与主 / 辅后端

- **已定**：JSON 是**主值文件格式**（缺省值、能力最完整、`$schema` 指针的落点），其余后端是**可选后端**，不是并列默认；README 定位句 + 特性表 + `docs/api/index.md` 参数表三处标注。
  - 依据：「本质上我们也是以 json 为主的」。
  - 状态：`已实现`｜出处：D01 §5 结论 1、5、§5 未决 2–3 / ISSUE-054
- **已定**：后端能力差异不因定位而消失：`.env` 是字符串后端、TOML 没有 `null`、`$schema` 指针只在能吃下成员的后端可用 —— 逐条写在文档里。
  - 状态：`已实现`｜出处：D01 §5 结论 6 / ISSUE-054

### 4.3 多文件：开关与寻址

- **已定**：多文件 = 一个开关 `no_one_file`（缺省 `False`）。关闭时键就是一整串普通字符，`:` 一个字节都不解析；开启时才把**第一个** `:` 左侧解析成文件路径。
  - 状态：`已实现`｜出处：D02 §1.1–§1.2 / ISSUE-008
- **已定**：语法 `conf("app/conf/net:net.id.post")` ⇒ 文件 `<home>/app/conf/net.<ext>`、文件内键 `net.id.post`；后缀由 `file_type` 决定，键里不写扩展名。
  - 状态：`已实现`｜出处：D02 §1.1、§1.3 / ISSUE-008
- **已定**：层级发生在**文件之间**，文件内部键仍扁平；`.env` 后端在多文件开启时同样可用。
  - 状态：`已实现`｜出处：D02 §1.5 / ISSUE-008
- **已定**：多文件关闭时，键名穿越的行为级回归原样成立（纯增量能力）。
  - 状态：`已实现`｜出处：D02 §1.4 / ISSUE-008
- **已定**：没有 `:` 的键落到**默认文件** `<home>/<file_name><ext>` —— 单文件与多文件可以混用，开启多文件后默认文件仍在、仍被寻址。
  - 依据：本轮裁定（候选 (a)）。
  - 状态：`已实现`｜出处：D02 §1 未决（本轮裁定） / ISSUE-008

## 6. 进程结构（独立 Alpha）

### 6.1 模型、生命周期与端点

- **已定**：Alpha 是**独立于所有客户进程**的进程，不是客户进程内的线程、也不是客户之一；它是该配置目录**唯一的读写者**，持有全局声明集与工作集；一个配置目录对应一个 Alpha。
  - 依据：现状是写者线程住在「碰巧先抢到端点」的客户进程里，一个客户退出就丢执行点。
  - 状态：`2.0`｜出处：D05 §0、§1 / ISSUE-004
- **已定**：启动采**关闭制** —— 默认每个进程都有资格启动，可用参数显式退出该资格；**不由「哪个进程」指定**，而由 `AutoConf` 入口对象自举（谁先发现 Alpha 不存在就拉起）。
  - 状态：`2.0`｜出处：D05 §1、DECISIONS 004-5.1 / ISSUE-004
- **已定**：启动竞态由**操作系统的原子绑定**裁决：只有一个进程能绑上端点成为 Alpha，其余退让并连接，不报错。
  - 状态：`2.0`｜出处：D05 §1 / ISSUE-004
- **已定**：传输沿用 `multiprocessing.connection`（Windows 命名管道 / POSIX `AF_UNIX`），**不开网络端口**。
  - 状态：`已实现`｜出处：D05 §1、DECISIONS 004-5.7 / ISSUE-004
- **已定**：Alpha 的启动参数（`home` / `file_type` / 落盘与日志参数 / `identity`）必须经**新的传递路径**（启动参数或握手）到达 Alpha；现有线上协议不携带任何引擎参数。
  - 状态：`2.0`｜出处：D05 §1 / ISSUE-004
- **已定**：生命周期 —— **不常驻**：多数时间不存在，仅拉起判据成立时出现，那批事务结束即退出。
  - 状态：`2.0`｜出处：D05 §1、DECISIONS 004-5.2 / ISSUE-004
- **已定**：端点生命周期语义重写 —— Alpha 在则独占端点、退出即释放；残留端点只在确认无人应答时清理；`_endpoint_is_alive` 的**裸 `connect` 探测保留**，用途改为判定 Alpha 是否存在。
  - 状态：`2.0`｜出处：D05 §1 / ISSUE-004
- **已定**：存活判断**只依据探测结果**，不引入心跳与 PID 判活。

  - 状态：`2.0`｜出处：D05 §1 / ISSUE-004
- **已定**：客户端 `atexit` 只交出自己的声明并收口日志，**不得关闭 Alpha、不得影响其存活**；「放下写者身份」这一职责随模型消失。
  - 状态：`2.0`｜出处：D05 §1、DECISIONS 004-5.8 / ISSUE-004
- **已定**：Alpha **不向 `<home>` 写 PID 或状态文件**；若确需新增运行态文件，必须同步首层路径白名单断言。
  - 状态：`2.0`｜出处：D05 §1 / ISSUE-004
- **已定**：**每个请求必须有上界** —— 握手沿用 `HELLO_TIMEOUT`，握手之后的 `send` / `recv` 同样加上界；上界是本节其余条款的落地前提。

### 7.4 落盘形式与加密

- **已定**：落盘 = 一组由参数选择的模式：**明文（默认）** / 纯二进制 / 二进制加密 / 明文加密；**载体（明文 / 二进制）与加密（否 / 是）是两个正交维度**；内置形式之外的扩展不在库内实现。
  - 状态：`2.1+`｜出处：D06 §1 §4 / ISSUE-005
- **已定**：**加密算法由调用方指定**；**密钥由调用方提供，缺失且必需时抛出异常**；库**不生成、不推导、不保管密钥，也不评价其强度**。
  - 状态：`2.1+`｜出处：D06 §1 §4、D07 §2、DECISIONS 041 / ISSUE-005、ISSUE-041
- **已定**：**库只产出数据** —— 不发起任何网络请求、不引入 HTTP/HTTPS 等协议库；sink **只接受参数**（用途限定「选模式」「填密钥」），**函数式 sink 取消**；职责到「产出数据」为止。
  - 依据：「我们不会帮你发网络请求」；被执行的发送代码不在 `src/onconf/` 里，静态断言守护不到。
  - **曾考虑但判否**：库支持网络去向（收回）；函数式 sink（会绕过静态断言，且回调过不了 IPC）。
  - 状态：`已实现`（约束现状成立：无 callable 参数面、无网络模块）｜出处：D06 §1 §5、D07 §1、DECISIONS 043 / ISSUE-005、ISSUE-043
- **已定**：静态断言继续守护（源码不得 import `socket` 等），运行时依赖仍为 `pyyaml` + `rich`；二进制与加密形式**不构成能力降级** —— 命令行必须能读取全部落盘形式，包括需要密钥的形式。
  - 状态：`2.1+`｜出处：D06 §1 §5、D10 §1、DECISIONS 042 / ISSUE-005、ISSUE-042
- **已定**：硬约束 —— **引擎参数必须可序列化**（执行点可能不是发起方进程，回调与文件句柄过不去 IPC）。
  - 状态：`已实现`｜出处：D07 §0
- **已定**：缺密钥的抛出时机是**写出任何记录之前**，不产生半份加密文件；异常类**新增一类、继承 `ConfError`**，与既有四类并列，并从顶层导出。
  - 依据：缺密钥若只能抛基类，调用方无法区分「漏配密钥」与其它写入失败。
  - 状态：`2.1+`｜出处：D07 §2 / ISSUE-041
- **已定**：密钥经 **sink 参数**传入（「填密钥」那一类）；命令行读取加密形式时密钥的入参属命令行体系，且命令行必须能读出加密内容。
  - 状态：`2.1+`｜出处：D07 §2、D10 §1 / ISSUE-041、ISSUE-042
- **已定**：密钥**不得出现在任何记录、日志、异常消息与落盘字节中**；源码中不存在密钥的持久化写入路径。
  - 状态：`2.1+`｜出处：D07 §2 / ISSUE-041
- **待裁**：算法名不可用时的异常（U21）、密钥形态与算法不匹配时的异常（U22）→ §11。

## 8. 数据交付边界

### 8.1 sink 的形态

- **已定**：**sink 的形态是参数，不是回调**；参数用途限定为两类：**选模式**、**填密钥**；不接受 callable、可调用对象、事件钩子。
  - 依据：函数式 sink 会让静态断言失效，且回调过不了 IPC。
  - 状态：`已实现`（约束现状成立）；sink 参数面 `2.1+`｜出处：D07 §1、DECISIONS 043 / ISSUE-043
- **已定**：**库不发起网络请求**，不引入 HTTP / HTTPS 等协议库；职责到「产出数据」为止，数据发往哪里、如何发送由调用方自行实现。
  - 状态：`已实现`｜出处：D07 §1 / ISSUE-043
- **已定**：静态断言继续守护（禁 import 集合与运行时依赖不变）；补充「sink 参数不含 callable」的守护；**参数值校验补齐** —— 未知模式与缺失密钥都要报错，不停留在只校验参数名；删除「其余值一律当文件路径」的兜底分派。
  - 依据：静默吞错是这条边界最恶劣的失败模式。
  - 状态：`2.0`（参数值校验）/ `2.1+`（sink 模式）｜出处：D07 §1 / ISSUE-043

### 8.2 调用方取数形式

- **已定**：边界 —— 库的职责到「产出数据」为止；库不发起网络请求、不接收函数；**产出单位是记录（`Record`）而不是渲染文本**，其可序列化性由自身保证。
  - 状态：`已实现`｜出处：D07 §3 / ISSUE-044
- **已定**：对候选形式**同时成立**的三条约束：交付形态不得破坏「引擎参数是可序列化的纯数据」；执行点可能不是调用方进程（记录要跨 IPC 回到发起方）；无论选哪种形式，**落盘那一份仍然恒写、全量**。
  - 状态：`已实现`｜出处：D07 §3 / ISSUE-044
- **待裁**：产出形式（U23）→ §11。

- **已定**：角色定死 —— CLI 是配置目录的**管理者**，运行中的进程是**使用者**；管理动作在运行期执行时，使用者读到的是管理后的结果，而不是崩溃或写了一半的状态（写入是原子替换）。

## 12. 曾考虑但判否 / 收回 / 作废

### 曾考虑但判否（按主题）

- **使用口**：`conf(key, type=int)` 作为第四种形态（随 `type=` 删除出局）。
- **覆盖出口**：(a) `AutoConf` 上的动词方法（方法名 / 返回值 / 与声明元数据的登记关系要逐个定义，且 `AutoConf` 从参数类型变成带状态对象）；(b) `conf` 上保留显式透传参数（与「`force=` 离开 `conf`」相反，在温和面上再开一个洞）；(c) 不给出口（「程序想持久化一个值」整类场景被砍，现由 CLI 承接）。
- **类型**：把跨后端类型差异写进词表（与「只输出一份 JSON Schema」冲突，且词表本就不记录载体能力）。
- **日志**：「日志整体不可关闭」的旧口径（改述为「文件通道不可关闭」）；把「其余值一律当文件路径」当兜底分派（任意字符串都能静音日志）；`report()` 与「人读报告」整条（内容已被 CLI 的 `diff` / `log` / `get` / `check` 分解）；「变更文件」概念（与审计文件本就是同一份产物，从未独立落地）。
- **进程**：心跳 / PID 判活（存活只在端点探测上判定）；保留运行期规则 1、靠「写者长命」兜住（声明集不是持久状态，换人就丢并集）；成员计数与成员发现（设计上已砍掉，且要求 Alpha 不存在时也能计数）。
- **多文件**：没有 `:` 的键 (b) 报错（既有调用全部不可用）(c) 落到上次用过的文件（引入跨调用状态）；「每个值文件一份词表」（多份互相不知道的登记册）。
- **数据交付**：「库支持网络去向」（**收回**，方自行引入 HTTP 库）；函数式 sink（会绕过静态断言，回调也过不了 IPC）。
- **文档诊断的备选方案**：方案 B「只做作废标注、不重排」（治标，结构仍按时间堆叠、会继续腐化）；方案 C「先修静默反转」（每处都要你先表态，作者无法替你决定，实际由 D01/D06 各自收口）；方案 D「口径漂移进 CI」（需先做完 A 或 B，已独立为 D11 §3、排 2.1+）。
