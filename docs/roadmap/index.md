# 路线图

本目录是 **OnConf 状态的唯一出处**：每一版收什么、每条决策定成什么样、现在到底能用哪些。
每条决策的证据、实测数字与历史变更都在 git 里，本目录不回头讲。

## 两份页面

- **[1.0.x —— v1.0.0 交付了什么](1.0.x/roadmap.md)**：已经发出去的那一份。只读，不再改。
- **[2.0.x —— 下一版收什么](2.0.x/roadmap.md)**：四根柱子、已写进代码还没发版的、
  还没做的，以及要拍板的问题。

分界按**发布**切，不按仓库现状切：代码在主线上已经改了、但还没打 tag 的
（三模式 `conf`、`file_name` / `file_type`、多文件、`build` / `sync`），记在 2.0.x，
状态写「已实现（待发版）」。

想知道**某一版具体改了什么**（含破坏性变更与迁移说明），看仓库根的
[`CHANGELOG.md`](https://github.com/HanYang06/OnConf/blob/main/CHANGELOG.md)；
本目录只回答「现在是什么状态、下一版收什么」。

## 每条怎么写

固定四段，**不用表格**：

1. **标题** —— 一句话说清这条决策或这个能力是什么。
2. **正文** —— 定成了什么、为什么。不写备选方案的考古。
3. **状态** —— 取下面状态词里的一个。
4. **引用设计文稿** —— 这条的意图记在哪一份设计稿的哪一节。

## 状态词

- `已实现` —— 代码里就是这样，1.0.x 里的每一条都是这个。
- `已实现（待发版）` —— 主线上已经改完，但还没打 tag、没发版。
- `待实现` —— 这一版要收，代码还没写。
- `待裁` —— 需要人拍板才能落地，登记在 2.0.x 末尾的「要拍板的问题」。
- `不计划` —— 已判定不做。
- `已定不动` —— 口径已经定死，这一版不改也不做。
