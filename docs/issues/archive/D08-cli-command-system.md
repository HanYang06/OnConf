## 1. 命令行体系：九个命令的语义与分工（原 ISSUE-031）

| 原项 | 值 |
|---|---|
| 原类型 / 优先级 / 状态 | 设计变更（新能力） / P1 / 部分已定 |
| 原依赖 | ISSUE-004（执行点决定日志归属）、ISSUE-005（文件通道强制全量，是 `diff` 与日志分析的数据来源）、ISSUE-008（键内嵌路径，`--file` 的等价物）、ISSUE-035（规则 1 移除后能力转入 `sync`） |
| 原影响面 | `src/onconf/__init__.py`、新增 CLI 包、`pyproject.toml:56-57`、`tests/`、`README.md`、`README.zh-CN.md`、`docs/getting-started.md`、`docs/roadmap.md`、`docs/security/threat-model.md`、`DESIGN.md` §6 / §10 |
| 原标签 | `area:cli`、`breaking` |

### 背景

- 控制台入口是占位：`main()` 只打印配置目录就返回（`src/onconf/__init__.py:136-138`），`pyproject.toml:57` 的 `onconf` 指向它。一个打印目录就退出的命令比没有命令更容易误导。
- 状态声明仍写着这个缺口：`docs/roadmap.md:41,54,67`、`README.md:184`、`README.zh-CN.md:177`。
- 删除能力在进程内按 ISSUE-035 移除，而命令行还没有出口：现状代码里唯一的删除动作由 `clean` 分支产生（`src/onconf/_engine.py:846-849`），它只由完整提交点 `sync()` 触发（`src/onconf/_engine.py:404-407`），单键删除无路可走。
- 破坏性操作（批量清理、格式化、生成代码）在命令面没有任何安全形态，登记项（原 ISSUE-037）尚未落地。

### 结论

#### 1. 命令表

| 命令 | 语义 | 破坏性 |
|---|---|---|
| `build` | 加载并执行声明代码，把值文件收敛到与声明一致；不删任何键 | 否 |
| `sync` | 离线、单次、全量执行声明代码得到完整期望集，收敛并删除代码未声明的键与无效键 | 是 |
| `check` | 纯检查，不写一个字节（ISSUE-049） | 否 |
| `format` | 只对 JSON 值文件重排缩进（ISSUE-045） | 是（重写文件） |
| `diff` | 按哈希索引查询变更历史 | 否 |
| `read` | 文件级原始数据读取 | 否 |
| `get` | 键级语义取值 | 否 |
| `set` | 修改已有键的值 | 是 |
| `add` | 新增键、更新词表、生成声明代码（ISSUE-046） | 是（产出新文件） |

`build` 与 `sync` 都要执行声明代码，差别只在是否清理：`build` 不删，`sync` 删。默认行为下「执行等于构建」，`build` 只是把执行这一步独立出来。`set` 只改已有键，`add` 才创建新键。

#### 2. `sync` 是规则 1 的新家

- 判据是代码里的完整声明集，来源只能是**执行代码**：常量传参、元组循环、非字面量实参让静态扫描拿不到完整键集（`src/onconf/_engine.py:321-325` 只要求键在运行期是字符串；`DESIGN.md:1756-1758` 把「值引用值」与「键用表达式算」分开，后者对静态扫描不可见）。
- 「期望集完整」成立的前提是离线、单次、全量执行，`sync` 满足全部三条，因此可以安全删除。
- `sync` 是破坏性命令，必须支持 `--dry-run`，且输出必须逐条列出将被删除的键。
- ISSUE-035 的裁定与本项一致：规则 1 不是消失，是转移到 `onconf sync`。

#### 3. 破坏性操作的形态与安全

- 破坏性命令一律支持 `--dry-run`：只打印将发生的变化，不写一个字节。
- 缺省不是 `--dry-run`；执行前必须能回答「哪个文件、哪些键、变成什么」。
- 非 TTY 下禁止任何交互。
- 是否要求显式确认或先备份，见未决事项。

#### 4. 统一约定

1. `--dry-run` 不写一个字节：工作区文件的 mtime 与内容都不变。
2. 每个命令的退出码必须定义：0 表示成功或检查通过，非 0 按错误分类（分类表见未决事项）。
3. 需要机器可读输出的命令提供 `--json`；同一命令的 `--json` 与非 `--json` 必须来自同一份数据。
4. 非 TTY 时禁止交互：`set` 的多命中选择在管道与 CI 里会永久阻塞，非 TTY 下直接以非 0 报错，并要求用 `--file` 指定目标。
5. `--file X k` 与键内嵌路径 `X:k` 等价（ISSUE-008）：`get --file X k` 与 `get X:k` 输出一致；两种写法只在多文件开启时解析路径。
6. `read` 与 `get` 的边界：`read` 取文件级原始数据，覆盖明文 / 二进制 / 加密三种落盘形式；`get` 取键级语义值，按词表校验后输出明文。
7. 加密落盘的密钥由参数传入（ISSUE-041：密钥由调用方产生，库不生成、不推导、不保管）；缺少必需密钥时命令以非 0 退出。具体入参形式见未决事项。
8. `diff` 建立在明确定义的哈希索引上。现状的审计记录只有 `old=` / `new=`，没有内容哈希（`src/onconf/_audit.py:176-200`）；仓库里唯一的哈希是声明集指纹（`src/onconf/_core.py:280-300`，落在词表键 `x-onconf-hash`，`src/onconf/_vocab.py:35`），它不是内容哈希。
9. 轮转会切断 `diff` 的历史：审计文件超过阈值后分片为 `audit-<stamp>.log`（`src/onconf/_audit.py:99,392-405`），`diff` 与日志分析必须跨分片按时间序合并查询。
10. `build` 必须定义「怎么找到并执行声明代码」：入口来自显式声明或约定的默认文件名，不得扫描整个工作区。

#### 5. 现状入口的处置

`main()` 的打印行为删除，不留兼容层；`pyproject.toml:57` 的 `onconf` 指向新的 CLI 入口。占位行为没有存在的价值：它只输出一个目录名，却占用了唯一的入口名。

### 验收标准

- [ ] 九个命令各有 `--help`，且 `--help` 不写任何文件
- [ ] `--dry-run` 下工作区文件 mtime 与内容逐字不变
- [ ] 每个命令的退出码有定义，成功为 0，非 0 按错误分类
- [ ] 非 TTY 下 `set` 的多命中选择不进入交互，直接以非 0 退出
- [ ] 多文件开启时 `get --file X k` 与 `get X:k` 输出一致
- [ ] `sync` 删除代码未声明的键，`build` 不删任何键，两者差异有回归测试
- [ ] `diff` 跨轮转分片查询有测试（阈值见 `src/onconf/_audit.py:99`）
- [ ] 入口不再打印配置目录，无参数调用的行为有明确定义与测试
- [ ] 文档同步（`docs/` 未同步视为未完成）

### 未决事项

1. `diff` 的哈希索引定义：候选 (a) 查询时按 `old=` / `new=` 现算；(b) 在审计记录里新增内容哈希字段。代价：(a) 不改落盘格式，但为值没有变化的记录提供不了索引；(b) 改变落盘格式，轮转分片的兼容性要一并处理。
2. 读取加密文件时密钥的入参形式：候选 (a) `--key` 参数；(b) 环境变量；(c) 交互输入。代价：参数会进 shell 历史与进程列表；环境变量对子进程可见；交互与 CI 冲突。
3. `build` 找到并执行声明代码的入口规则：候选 (a) 约定的默认文件名 `conf.py`；(b) 显式 `--code-file`；(c) 由配置声明入口模块。代价：(a) 约定名可能与用户项目冲突；(b) 每次都要显式给出路径，缺省落点不存在；(c) 需要新的配置面。
4. 退出码的分类表（错误类别与数字取值）未定。
5. 哪些命令提供 `--json` 未定。
6. `set` 拒绝创建新键，而 API `conf(key, value)` 会创建：候选 (a) 保留差异并在文档写明；(b) `set` 也创建，与 `add` 的分工改由文档区分。代价：(a) 两套语义并存；(b) 命令面出现两个都能创建键的命令。
7. 破坏性命令是否需要显式确认或先备份（原 ISSUE-037 的落点，已并入本文件 §1）。
8. 无参数调用 `onconf` 的行为（打印用法并返回非 0 / 列出命令 / 进入交互）。

## 2. §28.3 门禁第 1 条降级为 lint 警告（原 ISSUE-051）

| 原项 | 值 |
|---|---|
| 原类型 / 优先级 / 状态 | 设计变更 / P2 / 已定稿，待实现 |
| 原依赖 | ISSUE-031（`check` 是约定检查的落点）、ISSUE-053（约定要有成文载体） |
| 原影响面 | `DESIGN.md:1766-1773`（§28.3）、`check` 的约定检查、`README.md`、`README.zh-CN.md`、`tests/` |
| 原标签 | `area:cli`、`area:docs` |

### 背景

- §28.3 把「键必须是 `ast.Constant[str]`」列为门禁第 1 条，同一节又写明「这是使用者的选择，不是引擎的禁令。引擎不设限；门禁的能力边界如实写进 README 即可」（`DESIGN.md:1766-1773`）。
- 「门禁」在全仓只出现两处：`DESIGN.md:1766`、`DESIGN.md:1773`。它从未实现，README 中也没有任何对应说明（`README.md` 与 `README.zh-CN.md` 中均无「字面量 / 门禁 / 约定 / literal」的匹配）。
- 引擎对键没有任何静态限制：运行期只要求键是字符串（`src/onconf/_engine.py:321-325`），`conf(conf("alias.pack"))` 这类间接寻址是被支持的（`DESIGN.md:1756-1764`）。

### 结论

1. 判据定死：error = 不合法（引擎拒绝执行）；warning = 合法但不合理（约定提示）。
2. 「`conf()` 第一实参不是字符串字面量」属于合法但不合理，因此从门禁降级为 lint 警告，不作拒绝。
3. 警告由 `check` 的约定检查给出（ISSUE-053），不是引擎的运行期行为：`conf()` 的执行路径不因该写法改变，也不因此产生额外级别的日志。
4. §28.3 的表述改为约定，并把「门禁」一词从 `DESIGN.md` 与 README 中撤下。
5. 约定必须成文，载体是 README 的「使用约定」一节加 `check` 的约定检查；只写在设计稿里不算成文。
6. 约定检查的警告不改变 `check` 的通过判定：CI 的退出码仍由不合法项决定。

## 3. 「使用约定」要成文（原 ISSUE-053）

| 原项 | 值 |
|---|---|
| 原类型 / 优先级 / 状态 | 文档 / P2 / 待决策 |
| 原依赖 | ISSUE-031（约定检查的落点是 `check`） |
| 原影响面 | `README.md`、`README.zh-CN.md`、`check` 的约定检查、`tests/`、`docs/getting-started.md`、`DESIGN.md:1770-1773`（§28.3） |
| 原标签 | `area:docs`、`area:cli` |

### 背景

- §28.3 要求把约定的能力边界如实写进 README（`DESIGN.md:1772-1773`），而 README 里一个字都没有：`README.md` 与 `README.zh-CN.md` 中「字面量 / 门禁 / 约定 / literal」均无匹配。
- 「门禁」在全仓只出现在设计稿的两行（`DESIGN.md:1766`、`:1773`），从未实现。
- 约定管的是写法，不是引擎的禁令：引擎不设限，只在键不是字符串时报错（`src/onconf/_engine.py:321-325`）。
- 现状没有任何地方列出这些约定，用户无法知道哪些写法合法但不合理，也无法知道代价是什么。

### 结论

1. 约定要有成文载体，由两部分组成：README 的「使用约定」一节，加 `check` 的约定检查。
2. 约定检查输出 warning，不拒绝执行。判据沿用 ISSUE-051：error = 不合法，warning = 合法但不合理。
3. 每条约定以「一条约定 + 一句代价 + 一个可检测判据」的形式成文。
4. 没有可检测判据的条目不进 `check`，只进 README；有判据的条目同时进 `check`。
5. 第一条约定已定：`conf()` 的第一实参不是字符串字面量 —— 合法但不合理；代价是静态可查性丢失，间接寻址（`conf(conf("alias.pack"))`）至少还看得见内层的那一层（`DESIGN.md:1766-1770`）。
6. 约定不改变 `conf()` 与引擎的执行结果；`check` 的 warning 不影响退出码的通过判定。
7. README 的中英文两份必须逐条对齐（两者是一对）。

| 位置 | 改动 |
|---|---|
| `README.md` / `README.zh-CN.md` | 新增「使用约定」一节，逐条对齐（两者是一对） |
| 新增 `check` 约定检查 | 对每条可检测约定报 warning |
| `tests/` | 第一条约定的用例：warning 出现，且 `conf()` 行为不变 |
| `docs/getting-started.md` | 指向 README 的约定一节 |
| `DESIGN.md:1770-1773`（§28.3） | 载体从「写进 README」改为「README 加 `check` 约定检查」 |

### 验收标准

- [ ] `README.md` 与 `README.zh-CN.md` 各有一节「使用约定」，条目逐条对齐
- [ ] 每条约定含代价说明与可检测判据，缺判据的条目在 README 中标注不可检测
- [ ] `check` 对每条可检测约定各报一条 warning，且不改变 `conf()` 的执行结果
- [ ] 第一条约定（非字面量第一实参）有用例覆盖 warning 出现与执行不受影响
- [ ] 约定检查不写入任何字节（与 ISSUE-049 的只读约束一致）
- [ ] 文档同步（`docs/` 未同步视为未完成）

### 未决事项

1. 约定条目的完整清单：第一条已定，其余条目尚未列出。候选来源包括间接寻址（`conf(conf(…))`）、值引用值、多文件模式下的键内嵌路径、`.env` 的 dict / list 编解码、`doc` 与词表的关系。代价：条目越多，`check` 的误报面越大。
2. 约定的落点划分：候选 (a) 全部写进 README 一节；(b) README 只写约定与代价，判据细节写进设计稿。代价：(a) README 变长；(b) 判据与约定分处两地，容易再次失去一致。
3. 约定检查的输出形态：候选 (a) 单独一节；(b) 与其它检查结果同列。代价：(a) 输出分组清晰；(b) 用户容易把 warning 与 error 混读。
