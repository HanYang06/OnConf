## 0. 本决策的整体口径

命令行「能不能读到落盘的全部东西、能不能查日志、与运行中的进程怎么共处」三问。

- 命令行必须能读全部落盘形式（明文 / 纯二进制 / 明文加密 / 二进制加密）；需要密钥的形式同样必须可读，因此二进制是等价选择而不是降级（原 ISSUE-042）；
- 缺一条日志分析命令：按级别 / 时间 / 键 / 执行者筛选，跨轮转分片按时间序合并，只读（原 ISSUE-048，未定）；
- 角色定死：CLI 是配置目录的管理者，运行中的进程是使用者；CLI 不与 Alpha 的内存状态同步，破坏性命令只依靠自己取锁（原 ISSUE-050，未定）。

## 1. 命令行必须能读取全部落盘形式（原 ISSUE-042）

| 原项 | 值 |
|---|---|
| 原类型 / 优先级 / 状态 | 设计变更 / P1 / 已定稿，待实现 |
| 原依赖 | ISSUE-005（四种落盘形式）、ISSUE-031（CLI 命令体系与密钥入参） |
| 原影响面 | `src/onconf/__init__.py`、新增 CLI 模块、`src/onconf/_audit.py`、`tests/`、`README.md`、`README.zh-CN.md` |
| 原标签 | `area:cli`、`area:audit` |

### 背景

命令行入口目前是占位实现：`main()` 只打印配置目录（`src/onconf/__init__.py:136-138`），没有任何读取日志的代码路径，命令清单里也没有日志分析命令（命令表见 D08 原 ISSUE-031 §1）。

落盘侧只存在一种形态：紧凑文本。两处输出都调用 `_render_compact`（`src/onconf/_audit.py:666`、`:673`），没有二进制、没有加密。新模型把载体与加密拆成两个正交维度，共四种形式（ISSUE-005 §4）：明文、纯二进制、明文加密、二进制加密。

如果命令行只能读明文，纯二进制与加密形式就成了能力降级——选它们等于放弃分析能力。落盘形式是调用方的选择，读取能力必须覆盖全部选项，否则「四种形式等价可插拔」不成立。

### 结论

#### 1. 可读性全覆盖

- 命令行必须能读取全部落盘形式：明文、纯二进制、明文加密、二进制加密。
- 需要密钥的形式同样必须可读，不能以「需要密钥」为由排除在外。
- 因此二进制是**等价选择**，不是降级选择：选它在读取能力上不付出代价。

#### 2. 密钥入参

- 读取加密形式时，密钥由命令行接收；来源与优先级按 ISSUE-031 的约定（见 D08 原 ISSUE-031 §4 第 7 条与未决事项 2）。
- 缺少密钥时的报错沿用 ISSUE-041 的异常类语义。
- 本项只要求这条通道存在，不规定它的取值形态。

#### 3. 读取与落盘解耦

- 读取侧是独立的解码路径，不复用渲染函数的输出作为解析输入。
- 读取得到的记录与落盘时的记录语义一致；终端渲染的截断与对齐（ISSUE-006）不影响读取结果的完整性。

### 变更项

| 位置 | 改动 |
|---|---|
| `src/onconf/__init__.py:136-138` | 占位入口替换为真实 CLI 入口 |
| 新增 CLI 模块 | 读取路由：按落盘形式分派到明文 / 二进制 / 加密解码路径 |
| 新增 CLI 密钥入参 | 与 ISSUE-031 的入参约定一致 |
| `src/onconf/_audit.py:666,673` | 渲染与落盘解耦，读取侧不再从 `_render_compact` 的输出反推结构 |

## 2. 日志分析命令缺失（原 ISSUE-048）

| 原项 | 值 |
|---|---|
| 原类型 / 优先级 / 状态 | 任务 / P1 / 待决策 |
| 原依赖 | ISSUE-005（文件通道强制、全量、不截断，是分析的数据来源）、ISSUE-031（命令形态与统一约定） |
| 原影响面 | 新增 CLI `log`、`src/onconf/_audit.py`、`tests/`、`README.md`、`README.zh-CN.md`、`docs/getting-started.md` |
| 原标签 | `area:cli`、`area:audit` |

### 背景

- 落盘形态已定：文件通道强制、全量、永不截断（ISSUE-005）。级别集合是四条配置事实级别 `Read` / `Write` / `Change` / `Error` 加三条进程结构级别 `Start` / `Link` / `Send`（`src/onconf/_audit.py:83-93`）。
- 记录是纯数据且字段齐备：`level` / `txn` / `pid` / `item` / `file` / `identity` / `op` / `origin` / `data` / `old` / `new` / `at` / `err` / `message` / `count` / `reason`（`src/onconf/_audit.py:176-200`），可直接筛选与输出。
- 命令表里没有日志分析：ISSUE-031 的九个命令中只有 `diff` 触到变更历史。查错误、查谁读了什么，`diff` 都不覆盖。
- 轮转会产生分片：审计文件超过阈值后改名为 `audit-<stamp>.log`（`src/onconf/_audit.py:99,392-405`），分析必须跨分片。

### 结论

1. 补一条日志分析命令（名称未定，暂记 `log`），数据来自文件通道那一份，不来自终端那一份。
2. 落点覆盖四个筛选维度：按级别（`--level Change`）、按时间范围（`--since` / `--until`）、按键（`--key`）、按执行者（`--id`，对应记录里的 `pid` 与 `identity`）。
3. 查询覆盖全部轮转分片，按时间序合并输出。
4. 输出提供机器可读形式（ISSUE-031 §4），字段与 `Record` 一一对应。
5. 命令是只读的：不写值文件、不写词表、不写审计文件，工作区指纹不变。
6. `diff` 与 `log --level Change` 的关系定死：`diff` 是变更历史的一个视图，可以建在日志之上，但两者不等价 —— `diff` 带哈希索引与变更语义，`log` 是原始记录的筛选。
7. 终端通道被关闭或被级别筛选时，`log` 的结果不受影响：数据只取自文件通道。

| 位置 | 改动 |
|---|---|
| 新增 CLI `log` | 四个筛选维度、跨分片合并、`--json`、只读 |
| `src/onconf/_audit.py:176-200` | 记录字段是筛选与输出的唯一依据；如需索引字段，在此扩展（见未决事项） |
| `tests/` | 四个筛选维度各一组；跨轮转分片一组；只读回归一组 |
| `README.md` / `README.zh-CN.md` | 日志分析一节（两者是一对） |
| `docs/getting-started.md` | 命令用法 |

### 验收标准

- [ ] 四个筛选维度各有用例，筛选结果与 `Record` 字段一一对应
- [ ] 跨轮转分片的查询有用例：造出多个 `audit-*.log` 后结果仍按时间序完整
- [ ] 跑完 `log` 后工作区文件 mtime 与内容不变
- [ ] 终端通道关闭或按级别筛选时，`log` 的输出不变
- [ ] `--json` 与非 `--json` 输出取自同一份数据
- [ ] 行为变更带测试；只读断言覆盖既有文件与新增文件

### 未决事项

1. 命令名与形态：候选 (a) `log` 加参数；(b) `log` 带子命令（`log tail` / `log find`）；(c) `audit`。代价：(a) 参数面变宽；(b) 命令表从九条变多；(c) 与「日志」在文档里的既有叫法分叉。
2. `diff` 与 `log` 的分工边界如何在文档里写死：候选 (a) 按问题类型分（变更历史归 `diff`，其余归 `log`）；(b) 按数据来源分（`diff` 读索引，`log` 读原始记录）。代价：(a) 边界靠举例维持；(b) 要求 `diff` 的索引独立于日志。
3. 加密 / 二进制落盘形式的读取密钥入参（ISSUE-005、ISSUE-031 同源问题）。

## 3. CLI 与运行中进程的并发语义（原 ISSUE-050）

| 原项 | 值 |
|---|---|
| 原类型 / 优先级 / 状态 | 设计变更 / P2 / 待决策 |
| 原依赖 | ISSUE-031（CLI 直接改文件，不经过进程模型） |
| 原影响面 | `src/onconf/_engine.py`、新增 CLI、`tests/`、`docs/architecture/index.md`、`docs/security/threat-model.md`、`README.md`、`README.zh-CN.md` |
| 原标签 | `area:cli`、`area:concurrency` |

### 背景

- CLI 直接改文件，而同一配置目录可能正被进程使用（可能有一个 Alpha 在跑）。CLI 不要求 Alpha 存在，也不经 IPC（ISSUE-031）。
- 运行中的进程靠指纹检查加锁内重读发现变化：`_disk_stamp()` 取值文件与词表的 mtime + size（`src/onconf/_engine.py:794-808`），`_commit_pending()` 在排他锁内调用 `_reload_if_changed()`（`src/onconf/_engine.py:691-692`）。
- 两个具体风险：Alpha 的内存词表变旧（CLI 删了键，Alpha 的 `_vocab` 仍记着它）；`sync` 删掉正在使用的键后，进程读到「键不存在」并抛出 `KeyNotRegisteredError`（`src/onconf/errors.py:16-17`）。
- 写入是原子替换（`src/onconf/_engine.py:153-158`），因此读者不会看到写了一半的文件，但看不到「CLI 正在改」这件事本身。

### 结论

1. 角色定死：CLI 是配置目录的**管理者**，运行中的进程是**使用者**。管理动作在运行期执行时，使用者读到的是管理后的结果（键消失、值改变），而不是崩溃或写了一半的状态。
2. 进程侧发现变化的机制不变：指纹检查 + 锁内重读（`src/onconf/_engine.py:691-692,794-813`）。指纹同时覆盖值文件与词表，因此只改词表的 CLI 动作也会被读到。
3. CLI 不与 Alpha 的内存状态同步。内存词表变旧不构成误删，因为规则 1 已从进程内移除（ISSUE-035）。
4. `sync` 删除正在使用的键之后，进程读到的失败类型取决于词表是否同步更新：词表条目保留时抛 `KeyHasNoValueError`（有登记无值，归因是部署漏配），词表条目一并删除时抛 `KeyNotRegisteredError`（归因是键名写错）（`src/onconf/errors.py:16-21`）。两种归因都不指向「键被管理者删掉了」。
5. 破坏性命令的输出必须提示「目标配置目录可能正在被进程使用」，与 ISSUE-047 的写回提示并列。
6. 破坏性命令只依靠自己取锁完成写入，不引入与进程模型的握手（不要求 Alpha 存在、不经过 IPC）。
7. 角色定义写进 `docs/architecture/index.md` 与 `docs/security/threat-model.md`；README 一对只保留命令层面的提示。

### 未决事项

1. 是否给破坏性命令加「目录正在被使用」的检测：候选 (a) 不做检测，只在输出提示；(b) 检测锁文件或端点存在并警告（不阻塞）；(c) 检测到占用时拒绝执行，要求显式 `--force`。代价：(a) 零新增机制，误操作只能靠人看输出；(b) 检测是启发式的（锁文件存在不等于有进程在用），会误报；(c) 会挡住 CI 里删除键这类正常流程。
2. 读取失败与写入之间的时间窗是否需要给出量化上界并写进文档。
3. `check`（只读路径）遇到并发写入时的行为是否与其它命令一致（ISSUE-049 的未决事项 1 与此同源）。
4. 「键被 CLI 删掉」是否需要与既有两种归因区分：候选 (a) 不区分，只由文档说明；(b) 新增一个指向「键已被管理者移除」的异常类别。代价：(a) 使用者排查时要自己分辨键名写错、漏配与键被删；(b) 公开异常族扩张，且与 ISSUE-047 的词表处置绑定。
