## 0. 本决策的整体口径

「日志往哪去」被拆成了通道、渲染、轮转、暴露面、成本数字五份文件。合成一条：

- 日志有两个互不影响的通道 —— 文件强制、全量、永不截断；终端可关、可按级别筛选（原 ISSUE-005）；
- 终端通道在 TTY 下用 `rich` 着色，且必须惰性导入；非 TTY 不得输出 ANSI，落盘那一份绝不能带转义（原 ISSUE-006）；
- 落盘规则 / 轮转触发 / 轮转方式三组参数由调用方声明（原 ISSUE-039）；
- 明文值是默认落盘内容，不再是开关造成的 opt-in 暴露（原 ISSUE-040）；
- 「`import rich` 要不要上强制路径」这条约束的依据数字，全仓只留一处权威（原 ISSUE-016）。

## 1. 审计与日志：文件通道强制、终端通道可选（原 ISSUE-005）

| 原项 | 值 |
|---|---|
| 原类型 / 优先级 / 状态 | 设计变更（breaking） / P0 / 已定稿，待实现 |
| 原依赖 | ISSUE-004（执行点归属决定日志由谁写）、ISSUE-006（终端渲染） |
| 原影响面 | `src/onconf/_audit.py`、`src/onconf/_engine.py`、`src/onconf/__init__.py`、`tests/test_audit.py`、`docs/security/threat-model.md`、`README.md`、`README.zh-CN.md` |
| 原标签 | `area:audit`、`breaking` |

### 背景

现状把日志建模为「一条主去向 + 一个可选副本」：日志不可关闭、只能改去向（`src/onconf/_engine.py:69`），`audit=True` 时才额外追加 `<home>/audit.log`（`src/onconf/_engine.py:268`）。由此产生两个问题：

- 口径宣称「不可关闭」，但 `src/onconf/_audit.py:659-666` 只精确匹配 `"stderr"` / `"stdout"`，其余值一律当文件路径，于是 `log=os.devnull` 事实上静音整条日志（`tests/test_audit.py:622` 正在这么用）。
- 审计文件是否产生取决于一个布尔开关，而「用命令行分析日志」需要一份恒定、完整、可长期依赖的数据来源。

### 结论

#### 1. 两个互不影响的通道

| 通道 | 强制性 | 默认 | 形态 |
|---|---|---|---|
| 文件 | 强制，不可关闭 | 总是写 | 紧凑 `key=value`，全量，永不截断 |
| 终端 | 可选，可关闭 | 开 | 带色彩样式（ISSUE-006），可按级别筛选 |

强制性从「日志整体」下移到「文件那一份」，终端首次成为可关项。DESIGN.md §20.1「不可关闭，只能改去向」据此改述为「文件通道不可关闭」。

#### 2. 级别筛选只作用于终端

- 筛选语义是「刷新终端时只刷哪些级别」，取值集合为 `[Read]` / `[Write]` / `[Change]` / `[Error]` 的任意子集，允许为空（终端全静）。
- 文件通道永远全量，不受筛选影响，否则命令行分析日志缺少数据。
- `log=os.devnull` 在新模型下只能关闭终端那一份，文件照写：口径与实现重新一致，后门消失。

#### 3. `audit` 开关与「变更文件」一并取消

- `EngineParams.audit` 删除；审计文件路径改为独立参数，默认 `<home>/audit.log`。
- 「变更文件」概念取消。它与审计文件本就是同一份产物，且从未作为独立文件落地。
- 变更事项判定：`fill` / `overwrite` / `clean` / `register` / `update_meta` 计入变更；`skip` / `noop` 不计入。词表变更计入，标记 `scope=vocab`。

#### 4. 落盘体系可插拔，默认明文

落盘不是「往固定文件写」，而是一组由参数选择的模式：

| 内置形式 | 加密 | 说明 |
|---|---|---|
| 明文（默认） | 否 | 现有紧凑文本形态 |
| 纯二进制 | 否 | 二进制记录 |
| 二进制加密 | 是 | 二进制记录 + 加密 |
| 明文加密 | 是 | 明文内容加密后落盘 |

载体（明文 / 二进制）与加密（否 / 是）是两个正交维度，上表是四种组合。加密算法由调用方指定；密钥由调用方提供，缺失且必需时抛出异常，引擎不生成、不推导、不保管密钥，也不评价其强度。内置形式之外的扩展不在库内实现。

#### 5. 库只产出数据，不发送、不回调

| 边界 | 内容 |
|---|---|
| 不发网络 | 库不发起任何网络请求，不引入 HTTP / HTTPS 等协议库 |
| 不收函数 | sink 只接受参数，用途限定为「选模式」与「填密钥」；函数式 sink 取消 |
| 职责终点 | 库的职责到「产出数据」为止；数据发往哪里、如何发送由调用方自行实现 |

因此 `tests/test_security_invariants.py` 中「源码不得 import `socket`」的静态检查原样成立，运行时依赖仍为 `pyyaml` + `rich`。二进制与加密形式不构成能力降级：命令行必须能读取全部落盘形式，包括需要密钥的形式。

#### 6. 落盘行为可由参数声明

落盘规则（一个等级一个文件 / 几个等级一个文件）、轮转触发（文件尺寸比例 / 条目数比例）、轮转方式（按时间 / 其他）三组参数由调用方声明，默认值见 ISSUE-039。

#### 7. 明文值默认落盘的定性改变

日志记录携带真实值（`data=` / `old=` / `new=`）。现状的定性是「开启 `audit` 才构成主动暴露」，新模型下这是默认行为，不再是 opt-in。`README.md:233` 与威胁模型 T12 必须按新定性重写，见 ISSUE-040。

## 2. 渲染层：`rich` 上线（原 ISSUE-006）

| 原项 | 值 |
|---|---|
| 原类型 / 优先级 / 状态 | 设计变更 / P1 / 部分已定 |
| 原依赖 | ISSUE-005（终端通道可选；`rich` 只作用于那一份） |
| 原影响面 | `src/onconf/_audit.py`、`tests/test_audit.py`、`tests/test_security_invariants.py`、`pyproject.toml`、`docs/design/DESIGN.md` §21、`docs/roadmap.md`、`README.md`、`README.zh-CN.md` |
| 原标签 | `area:audit`、`area:render` |

### 背景

- `rich` 声明在运行时依赖里（`pyproject.toml:53`），但 `src/onconf/` 对它零引用；`pyproject.toml:50-52` 自己注明「没有任何代码 import」，用途留给一个从未落地的报告。
- 现行设计条款与「`rich` 上线」相反：`DESIGN.md:1327-1333`（§21.4）写着「不要为此引入 rich」，理由是 `import rich` 实测 222 ms，而日志在强制路径上。
- 人读渲染目前全部手写：显示宽度 `src/onconf/_audit.py:129-145`、单元格 `:295-348`、弹性制表位 `:351-368`、终端渲染与截断 `:376-384`、紧凑文件形态 `:371-373`。
- `src` 中没有 TTY 判据，也从不输出 ANSI：只有剥离用的 `_ANSI`（`src/onconf/_audit.py:115`）与 `strip_ansi`（`:129-131`）。
- 为什么不可接受：一个零引用的依赖与一条相反的设计条款并存，读者无法判断 `rich` 到底用不用。

### 结论

#### 1. `rich` 用于终端人读渲染，且必须惰性导入

`import onconf` 不得触碰 `rich`；只有真的要往终端渲染时才导入，导入点是 `src/onconf/_audit.py:_emit_log`（`:651-666`）。「惰性导入」这条前置条件在原设计里已写明两次（`DESIGN.md:365`、`:1333`），本项沿用同一约束，不新造机制。

#### 2. 作用范围仅终端通道

| 通道 | 强制性 | 渲染 |
|---|---|---|
| 文件 | 强制，总是写 | 紧凑 `key=value`、全量、永不截断、**不含 ANSI**（§21.5 约束 1，`DESIGN.md:1335-1339`） |
| 终端 | 可选、可关 | `rich` 着色；列宽与对齐沿用现有 stdlib 路径（§21.2 / §21.3，`DESIGN.md:1294-1325`） |

#### 3. §21.4 的结论作废，理由保留并升级

`DESIGN.md:1327-1333` 的判断「不要为此引入 rich」不再成立；该节真正的约束保留下来，写成通用规则：**强制路径（`import onconf` 与文件通道）不得多付 `rich` 的导入与渲染成本**。同一类约束在 `DESIGN.md:1502-1503`（§24.3）以「惰性导入」的形式出现过。

#### 4. 级别名保持完整词，不变

`[Read]` / `[Write]` / `[Change]` / `[Error]` / `[Start]` / `[Link]` / `[Send]`（`src/onconf/_audit.py:85-93`）。

#### 5. 非 TTY 不得输出 ANSI

- 判据用 `rich` 的 `Console.is_terminal`，判据本身要有测试守护；
- 非 TTY 走现有纯文本路径，输出与现状逐字一致；
- 日志改到文件时 stderr 必须严格为空（`tests/test_audit.py:376` 是精确相等断言）；
- 落到 `audit.log` 与值文件里的那一份绝不能带 ANSI 转义（§21.3，`DESIGN.md:1324-1325`）。

#### 6. `report()` 判定不做

它原本要回答的内容已被 CLI 的 `diff` / `log` / `get` / `check` 分解；`DESIGN.md:170-178`（§6）的人读那一路整条作废，`docs/roadmap.md:66` 的「rich 报告未开始」改为判定不做。

#### 7. `rich` 不再是死依赖

`pyproject.toml:50-52` 的「预留」注释改为实际用途：终端人读渲染，惰性导入。

## 3. `rich` 导入成本数字在仓库内有四个版本（原 ISSUE-016）

| 原项 | 值 |
|---|---|
| 原类型 / 优先级 / 状态 | 文档 / P2 / 已定稿，待实现 |
| 原依赖 | ISSUE-006（`rich` 的用途定位） |
| 原影响面 | `DESIGN.md` §11.3、§21.4、§24.1、`pyproject.toml` |
| 原标签 | `area:docs`、`area:perf` |

### 背景

决定 `rich` 去留的那个数字在仓库里有四个版本，倍数口径互不一致：

| 位置 | 数字 |
|---|---|
| `DESIGN.md:349`（§11.3 实测表） | `import rich.console` **~222 ms**，rich 是 bare 的 **3.4 倍** |
| `DESIGN.md:1330`（§21.4） | `import rich` 实测 **222 ms**（空解释器的 **5.6 倍**） |
| `DESIGN.md:1483`（§24.1 实测表） | `import rich` **+180 ms** |
| `pyproject.toml:51` | `import rich` 实测 **+180~222 ms** |

绝对值的 180 与 222、倍数的 3.4 与 5.6 之差来自基线不同：§11.3 表以「冷启动一个 Python 进程 ~65 ms」为底（`DESIGN.md:347`），§21.4 以空解释器为底，§24.1 表的第一行是**解释器启动 41 ms**（`DESIGN.md:1482`）。同一个测量给出四个口径，而它正是「rich 是否上强制路径」这条约束的依据（`DESIGN.md:1329-1331`、`pyproject.toml:50-52`）。依据本身漂移时，读者无法判断该约束是否还成立。

### 结论

#### 1. 只保留一处权威数字

- 权威数字落在 `DESIGN.md` §24.1 的实测表（`DESIGN.md:1478-1489`）：该表是所有导入成本的统一入口，且每行标了成本性质。
- 其余三处不再各自给出数字，改为引用 `DESIGN.md` §24.1，不重复数值。

#### 2. 数字必须可复现

- 权威数字由一次可复现的实测产生，并记录测量脚本、解释器版本、重复次数与基线定义。
- 倍数必须写明相对哪个基线；同一处只出现一个基线。
- 无法复现时只写绝对值，不写倍数。

#### 3. 范围

- 本项是文档一致性任务，不改任何导入行为，也不改 `rich` 的用途定位（ISSUE-006）。
- `pyproject.toml:50-52` 的注释改写后只保留用途与惰性导入约束，数值交给 `DESIGN.md` §24.1。

### 变更项

## 4. 落盘规则与轮转参数由调用方声明（原 ISSUE-039）

| 原项 | 值 |
|---|---|
| 原类型 / 优先级 / 状态 | 设计变更（breaking） / P1 / 部分已定 |
| 原依赖 | ISSUE-005（落盘体系可插拔、审计文件恒写） |
| 原影响面 | `src/onconf/_audit.py`、`src/onconf/_engine.py`、`src/onconf/__init__.py`、`tests/test_audit.py`、`README.md`、`README.zh-CN.md`、`DESIGN.md` §20.4 |
| 原标签 | `area:audit`、`breaking` |

### 背景

审计文件的轮转策略是写死的常量：阈值为 `AUDIT_MAX_BYTES = 1 << 20`（`src/onconf/_audit.py:98-99`，即 1 MiB），触发依据是文件字节数（`src/onconf/_audit.py:392-397`），分片命名为 `<stem>-<YYYYmmdd-HHMMSS>[-N]<suffix>`（`src/onconf/_audit.py:399-405`）。等级到文件的映射同样写死：全部记录不分级别地追加进同一个文件（`src/onconf/_audit.py:96`、`:668-673`）。

这套策略对调用方不可见也不可声明：需要按条目数而非字节数轮转、需要按等级分流、需要按日期切片时，只能改库。分片还有第二个后果——历史被切到多个文件，`diff` 一类的变更历史查询必须跨片拼接才能得到完整序列（见 D08 原 ISSUE-031 §4 第 9 条；分片规则见 `src/onconf/_audit.py:399-400`）。

### 结论

#### 1. 三组参数由调用方声明

| 组 | 取值集合 |
|---|---|
| 落盘规则 | 一个等级一个文件 / 几个等级一文件 |
| 轮转触发 | 文件尺寸比例 / 条目数比例 |
| 轮转方式 | 按时间 / 其他 |

- 「比例」相对一个基准而言，基准本身也由参数给出，不是写死的常量。
- 三组参数只描述落盘形态，不改变文件通道恒写、全量、永不截断这三条（ISSUE-005 §1、§2）。
- 每个取值组合都要能被命令行读到，读取路径按 ISSUE-042 对全部落盘形式成立。

#### 2. 参数默认值

三组参数的默认值不在本项内指定，候选与代价见「未决事项」。默认值落定之前，实现保留现有取值：1 MiB、按文件尺寸、单文件装全部级别。

#### 3. 轮转与 `diff`

轮转分片是可预期产物，查询侧必须按分片命名顺序拼接历史。分片命名规则随轮转方式参数改变，`diff` 侧的实现与测试同步跟进，见 ISSUE-031。

### 变更项

| 位置 | 改动 |
|---|---|
| `src/onconf/_audit.py:98-99` | `AUDIT_MAX_BYTES` 由写死常量改为参数派生的默认值 |
| `src/onconf/_audit.py:392-405` | `_rotate_if_needed` 改为按声明的触发方式与命名规则轮转 |
| `src/onconf/_audit.py:96,668-673` | 单一审计文件路径改为按落盘规则解析出的路径集合 |

| `tests/test_audit.py` | 每种落盘规则与每种触发方式各一组轮转回归 |
| `README.md:127,169`、`README.zh-CN.md` | 参数表与日志审计说明补三组参数 |

## 5. 明文值默认落盘后的暴露面定性（原 ISSUE-040）

| 原项 | 值 |
|---|---|
| 原类型 / 优先级 / 状态 | 设计变更（breaking） / P1 / 部分已定 |
| 原依赖 | ISSUE-005（文件通道强制、明文是默认落盘形式） |
| 原影响面 | `README.md`、`README.zh-CN.md`、`docs/security/threat-model.md`、`src/onconf/_audit.py` |
| 原标签 | `area:audit`、`area:security`、`breaking` |

### 背景

记录携带真实值：`data=` / `old=` / `new=` 属于字段白名单与可截断列（`src/onconf/_audit.py:112`，白名单全文见 `docs/security/threat-model.md:275-278`），落盘时完整写出（`src/onconf/_audit.py:666,673`）。现状文档把这件事定性成**开关造成的暴露**：

- `README.md:233`：`data=` / `old=` / `new=` 携带真实值，`audit=True` 才把它们写入 `<home>/audit.log`，为装满密钥的配置文件打开这个开关构成一次刻意暴露。
- `docs/security/threat-model.md:271-272`：缓解第一条是「去向由调用方选，`audit` 默认**关**：不开就没有审计文件」；`:280-282` 的残余风险写「库**不做值脱敏**」。
- `README.md:222` 同口径：日志可以改去向，但不可以关闭。

新模型取消了 `audit` 开关与「开不开」这个维度（ISSUE-005 §3、§4）：明文是默认落盘形式，文件通道恒写。上述三处的因果链因此不成立——值随配置落盘不再需要一次显式开启，而是一个默认事实。

### 结论

#### 1. 定性

- 明文值是**默认落盘内容**，不需要任何开关，也不是 opt-in。
- 该定性不因落盘形式改变而放松：选择加密形式只改变字节形态，不改变「未加密时值原样存在」这一事实。
- 既有缓解继续成立：文件以 `O_APPEND` 追加、以 `0600` 创建（`src/onconf/_audit.py:417`）、字段白名单、键名与身份里的 CR / LF 折成可见转义（`docs/security/threat-model.md:273-278`）。

#### 2. 文档按新定性重写

- `README.md:222,233` 与 `README.zh-CN.md` 对应段落：去掉「开启才暴露」的因果，改为「文件通道恒写，落盘内容包含真实值」。
- `docs/security/threat-model.md` 的 T12（`:263-285`）与 `:321` 的章节映射：缓解手段中删除「默认关」，保留权限、追加写、白名单、转义；把值原样落盘写成默认状态而不是开关后果。
- `README.md:169` 能力表中 `audit=True` 前缀同步改写为落盘形式。

是否提供值脱敏不在本项内指定，候选与代价见「未决事项」。

### 未决事项

是否提供值脱敏选项：把 `data=` / `old=` / `new=` 换成哈希或长度。

| 候选 | 代价 |
|---|---|
| (a) 不提供 | 审计可完整回放值，`old` 到 `new` 的追溯能力无损；凭据随配置落盘 |
