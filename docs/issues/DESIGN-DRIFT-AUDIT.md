## 0. 先看三条结论

### 结论一：原始口径一个字都没被改过 —— 所以它现在是错的

§1–§10 共 300 行，在 14 次提交、501 行新增中，**只有 4 行被碰过，且全部是机械改名**（`auto_conf` → `onconf`、`AUTO_CONF_HOME` → `ONCONF_HOME`）。

```text
§1-§10 内不同行数: 4 / 300
  行 1   # auto-conf 设计草案 v0.1        → # OnConf 设计草案 v0.1
  行 187 from auto_conf import AutoConf   → from onconf import AutoConf
  行 205 from auto_conf import conf       → from onconf import conf
  行 280 AUTO_CONF_HOME                   → ONCONF_HOME
```

**实质内容零修改。** 后果是：`DESIGN.md` 里存在一整套**读起来完全像现行规格、实际已被推翻**的章节，而文档里没有任何信号提醒读者。

### 结论二：推翻全部靠「往下追加」，从不回头标注作废

```text
全文 diff：+501 行 / -25 行
  其中追加新章节 §27–§32：+294 行
  其余 25 行删除里，真正涉及设计口径的只有 §20/§22–§26 的十来行
  §1–§10 区间：0 行实质修改
```

带作废/修正标记的只有 13 处左右（§4 标题、§11 引言、§13.3 标题、§17.2、§17.9、§20.5、§22 顶部、§25 标题、§28.3、§30 标题、§32.4……）。**其余矛盾一律没有标记**，需要读者自己读到 §32 才知道 §5.2 的 WAL 早就没了。文档的「当前真相」永远在编号最大的那一节 —— 而这个约定**文档里从未写明**。

### 结论三：最危险的不是「改口径」，是「连口径都没改」

有四处是**代码与文档直接相反、两边都没人出声**。其中 §18.3 最典型：`_core.py` 的模块 docstring 还在引用「§18.3 类型推断 → 与声明比对 → **转换**」作为自己的规格，同一文件 120 行之后写着「这里**没有**类型推断，也**没有**类型转换」。

**改口径至少留下了决策记录；静默反转只留下一个说谎的文档。**

## 1. 机制诊断：口径是怎么被改掉的

### 1.1 权威方向被反转了

`AGENTS.md` §3.4 定的是：

> 指向 `docs/design/DESIGN.md`（**意图的权威**，不是状态的权威）

但实际流程是：**实现撞墙 → 改 DESIGN → 实现跟进**。因为 DESIGN 是意图的权威，这条路径等于把「实现时的权宜」**洗成了「设计意图」**。

于是文档不再能回答「我们当初决定了什么」，只能回答「我们最后做了什么、以及为此编了什么说法」。这就是你说的「口径被改掉」。

### 1.2 追认式修订：先做，再补一节论证

`DESIGN.md` §11 之后的每一节，结构高度一致：

```text
## N. <新决定>（<实现后修正> / <已修正> / <已交付>）
### N.1 为什么
```

论证是**在决定之后**补的。所以理由读起来都很顺 —— 它本来就只需要说服已经做过的事。举个最清楚的例子，§32.7「WAL 不做」：

> | WAL 要买的 | 现在的来源 |
> | 合并突发写 | 攒批窗口（客户端侧，§30） |
> | 持久 | 声明可从**代码**重新推导；词表每次整体重写 |

「持久 = 声明可从代码重新推导」这句话，与 §17.1「**代码里写的配置数据、默认值，不构成读取的来源**」是同一个库里最核心的一句承诺打架。§5.4 原本写的是「`set()` 返回时，数据已经在 WAL 里（durable）」。这个论证是靠上下文补出来的，不是靠证据推出来的。

### 1.3 适应而非修复

最刺眼的一处不是矛盾本身，而是**组织选择了「把矛盾写成阅读提示」**：

`docs/design/index.md:11-12`

> **性质**：**未定稿的设计草案**。……正文里既有带 ❓ 的待拍板项，
> **也有被后续小节明确推翻的前期结论**

以及 `DESIGN.md:2093`，§32.8 的已知边界：

> **已知边界**（实现期暴露，**不再往回改**，但要看清楚）：

「不再往回改」—— 这是一个已知缺陷被**明文宣告永久保留**，处置方式是给它写一段说明。

### 1.4 护栏存在但拦不住

`AGENTS.md` §3.4 要求「改动 DESIGN.md 必须在 PR 里单独说明理由」。实际提交粒度：

```text
动过 DESIGN.md 的 14 个提交里，9 个是 MIXED（同一提交里同时改 src/ 和 tests/）

3a189ed  MIXED  src=1  fix(owner): 端点目录必须显式创建…
fd20f89  MIXED  src=3  feat(audit): 级别名改成完整词…
2881a03  MIXED  src=5  feat(audit): 落地日志与审计…
bbab1a8  MIXED  src=3  feat(engine): 跨进程锁 + 锁内按需重读；攒批窗口按需开…
007af1e  MIXED  src=3  feat(engine): 引擎装配…
```

设计口径的变更搭着 `feat(...)` / `fix(...)` 的车进去，在 review 里不会被当作一次设计决策看待。护栏在纸上，不在流程里。

## 3. 四处最重的

### 3.1 §18.3 读时类型转换 —— 静默反转（最严重）

**原口径**（DESIGN:1026-1052）：

```text
推断类型 != 声明类型  → 尝试转换到声明类型
                        能转   → 返回转换结果
                        不能转 → 抛异常，提示类型不一致
```

> 这回答了 §15.4 的问题：**`type` 同时承担校验与转换**……
> 所以 `int(conf("slot.max.byte.b"))` 里那个 `int()` 确实应该删掉。

**代码实际**（`_core.py:131-136`）：

> 这里**没有**类型推断，也**没有**类型转换 —— 引擎对值是**透明**的：
> 文件里是 `"8080"`，读回来就是字符串 `"8080"`，不会变成 `8080`。
>
> （这条是被测试抓出来的：早先这里挂着一层 `infer`，于是 JSON 里
> 一个字符串值会莫名其妙变成数字。要数字请在取用处显式 `int(…)`，
> 这样「哪里发生了转换」在代码里一眼可见。）

**README:141-143** 和 **`docs/api/index.md:18-19`** 都站在代码这一边。

**问题在于**：

1. 这是一次**核心语义的反转** —— §15.4、§18.2 ④、§18.3、§10/M1 四处都还在要求转换；
2. **`DESIGN.md` 里没有任何一处标记它被推翻**（全文搜「透明／转换」只有 §18.3 那几行原话）；
3. 最讽刺的是 `_core.py:11` 的模块 docstring 把「§18.3 类型推断 → 与声明比对 → **转换**」列为自己对应设计文档的条目 —— **这个文件在引用一个它自己已经违反的规格**；
4. 原设计专门给出的操作建议（「那个 `int()` 确实应该删掉」）现在**正好是反的**：README 教你「想要 int 就自己写 `int(conf("PORT"))`」。

改口径会留下决策记录。这一次连口径都没改，只留下了两个互相矛盾的文档。

### 3.2 §18.4 风险 A —— 已预见、已给解法、实现未采纳，反手缩小承诺

这是最能说明问题的一条，因为**原设计早就把坑画出来了**。

**§18.4 风险 A「清理未知数据在多进程下会误删（严重）」**（DESIGN:1056-1068）给出的例子：

```text
进程 A 声明 {a, b}
进程 B 声明 {b, c}
文件里现在有 {a, b, c}

A 再启动 → 全量对账 → c 不在 A 的声明集里 → 清理掉 c ❌
B 再启动 → c 缺失 → 又补回来
→ 两个进程周期性互删，来回抖动
```

并给出三个候选解法，**推荐 (a)**（DESIGN:1078-1079）：

> 倾向 **(a)**：它和「词表是键的权威」是同一句话的两面 ——
> 既然键的权威是词表，那「多出来的键」就该拿**词表**比，而不是拿本次声明比。

**实际发生的**（DESIGN:2002-2026，§32.4「一条必须**收回**的论证」）：

```text
{'$schema': …, 'key.of.sync2': …}      ← 三个键只剩最后一个
```

> 原因：每个子进程自己当写者、写完就退出；下一个写者接手时**声明集是空的**，
> 它的规则 1 把前任的键当成「未知数据」删掉了。
>
> **所以：声明集不是持久状态。** ……这跟有没有专职写者无关。

**结局**：没有采纳 (a)。而是把规则 1 的适用范围**限定在「单写者且长命」**，并在 `README.md:180,228` 把这个缺口登记为「open design question」／「Known limitation」。

**为什么归到「挪球门」**：风险被预见了、解法被推荐了、失败现象与预测一字不差地复现了，最后被调整的不是实现，**是承诺的边界**。而且 `README.md:181` 至今把「前缀分片锁」列为「—（当前是每个配置目录一把锁）」，也就是 §18.4 的备选方案 (b) 也从没被认真考虑过。

> 附带一条**可机械验证**的未履行承诺：§18.4 风险 B（DESIGN:1089）写
> 「如果这是要的，**必须明确写进 README**」。
> 我逐条比对了 `README.md:224-237` 的 Known limitations（9 条）—— **没有这一条**。
> 「用户手加的键会被 `sync()` 清掉」这件事，用户从 README 里读不到。

### 3.3 §6 审计 —— 能力被对半砍，且方向被反

| | 原口径 | 现口径 |
|---|---|---|
| 通道数 | **双通道，不要混在一起** | 单通道文本行 |
| 机读格式 | JSONL 追加，字段 `ts, pid, key, origin, result` | 无 JSONL |
| 人读报告 | `conf.report()`，rich 表格 | **无**（`rich` 成死依赖） |
| 开关 | **默认关闭**（有性能成本），显式开启 | **不可关闭**，只能改去向 |

四条里有三条是 180° 反转，而 §6 一个字都没改。给出「两份格式会让『哪份是准的』变成问题」这个理由的，恰恰是 §32.8 —— **在砍掉双通道之后**。

### 3.4 §5.2 WAL —— 一条真发现与一条挪球门缠在一起

要公平地说：**砍掉 WAL 的结论我倾向于是对的**，理由也很强：

- §30.2：词表 diff 已经挡住了写放大，稳态下对账产出空动作，一个字节都不写；
- 默认当场落盘后，「可见性延迟」这个 WAL 本来要弥合的东西消失了；
- §32.7 的四件事确实各有来源（串行＝专职写者、顺序＝读改写＋原子替换）。

但**理由 2「持久 = 声明可从代码重新推导」与 §17.1 的核心承诺直接冲突**，而 §5.4 原本承诺的「`set()` 返回时数据已 durable」在 WAL 缺席下是靠 `flush_window=0` 的默认值兜住的 —— 一旦用户打开攒批窗口，这个承诺就**无声地弱化**了（§30.3 只说提交点有四个，没说「开了窗口就不再 durable」）。

所以 WAL 这条要**拆开看**：删掉 WAL 是 🟢，但「删掉之后 §5.4 的 durability 承诺怎么办」没有人正面处理，是 🟡。

## 6. 供你拍板的处置选项

按我的推荐排序。**本轮不动代码**，等你选。

### 方案 A（推荐）：把 `DESIGN.md` 拆成「规格」与「决策日志」两份文档

- **`DESIGN.md` 收敛成「当前唯一有效口径」**：只保留现状成立的陈述，§1–§10 里已被推翻的条款**就地改写或删除**，不留悬案；
- **新开 `design/DECISIONS.md`（或 `CHANGELOG-design.md`）**：§11–§32 的追认过程整段搬过去，按时间编号，每条标注「当时的决定／理由／后来被谁取代」；
- 规则钉死：**规格文档只描述现在**，任何「为什么当初这么定」进决策日志；
- 好处：口径重新唯一，读者不用读到 §32 才知道 §5.2 作废；历史一点都不丢（你显然很在意那些实测数据）。
- 代价：一次较大的文档重排；需要在 `mkdocs.yml`、`AGENTS.md`、README、`docs/design/index.md` 同步引用。

### 方案 B：只做「作废标注」，不重排

在 §1–§10 每个被推翻的条款处，**就地加一行** `> **已被 §X 取代**`，并补上「不可关闭」「读时转换」这类**连标记都没有**的静默反转条目。
- 好处：改动量最小，风险最低，立刻可读；
- 代价：文档仍然是「按时间堆叠」的结构，未来还会继续腐化 —— 治标。

### 方案 C：先修静默反转，因为它们是「说谎的文档」

优先处理 §18.3（类型转换）、§6（不可关闭）、§4（环境变量层）、§2（多文件层叠）这四处**代码与文档相反**的，明确二选一：要么改文档承认现状，要么改代码回到原设计。
- 好处：消除「文档骗人」这类最高危问题；
- 代价：每一处都要你先表态「哪个才是你要的」——**这正是我无法替你决定的部分**。

### 方案 D：把口径漂移变成 CI 可拦截的

- `AGENTS.md` §3.4 的护栏改成**可执行**：CI 里检测「同一提交同时修改 `src/` 与 `docs/design/DESIGN.md`」就要求 PR 说明（或只允许 DESIGN 改在独立提交）；
- 给 `DESIGN.md` 加一条机器可查的约定：任何小节标题带「（已修正）」「（实现后修正）」「（已交付）」的，必须在文首**汇总表**登记。
- 好处：止住复发；
- 代价：需要先做完 A 或 B，否则约束的是一份自相矛盾的文档。
