# 初始化配置

> 本页是**初始化配置**的设计口径：两个面、引导层与值层、`conf` 的三种模式、运行期写路径、
> 目录约定、使用范式。

## 1. 两个面

对外只有两个入口，别的一律不是公开面：

| 面 | 职责 |
|---|---|
| `AutoConf(**engine)` | 配置**引擎自己**：配置目录、值文件名与类型、多文件开关、日志落点与开关、身份 |
| `conf(key, value=…, doc=…)` | 干所有的活：读 / 写 / 登记 |

```python
from onconf import AutoConf, conf

AutoConf(home="./conf")   # 可省略 —— 省略时按约定找配置目录
conf("app.server.port", 8080)      # 声明 + 写；返回当前生效值
print(conf("app.server.port"))     # 读
```

**使用口不得配置引擎。** 以前 `conf("a.b", 1, home="/x")` 能顺带把引擎也配了，
现在是 `TypeError`：一个配置口、一个使用口，不靠「引擎是否已经起来」这种时序条件成立。

## 2. 引导层与值层

配置口分两层，这是本页最重要的一条：

| 层 | 内容 | 能不能运行中改 |
|---|---|---|
| **引导层** | `home` / `file_name` / `file_type` / `no_one_file` / `log_path` / `log_console` / `log_rotate` / `log_scrub` / `log_encode` / `identity` / `flush_window` | **不能**。改了等于改代码，必须重启 |
| **值层** | 值文件里的一切 | 随便改 —— 值每次从文件重新读 |

引擎起来之后带参数再调 `AutoConf(...)` 会抛 `ConfError`：

```python
AutoConf(home="./conf")
conf("a.b", 1)
AutoConf(home="./other")   # ConfError：引导层不可运行中改
```

值层不受这条限制，因为文件才是事实：

```python
AutoConf(home="./conf")
conf("a.b", 1)
# 手改 ./conf/settings.json 里的 a.b，下一次 conf("a.b") 就读到新值
```

`AutoConf()` 不带参数调用**永远合法**，语义是「把单例取回来」。

## 3. `AutoConf` 的参数

参数清单只有一处权威：`onconf.EngineParams`。它既是类型提示也是运行时校验依据
（`AutoConf` 的注解与 `Engine.__init__` 的形参一一对应，有回归守着）。

| 参数 | 默认 | 说明 |
|---|---|---|
| `home` | `./conf` | 配置目录。显式参数优先，`ONCONF_HOME` 环境变量次之 |
| `file_name` | `settings` | 值文件名主干，**纯文件名**（过包含性校验）。见[文件支持](file_support.md) |
| `file_type` | `"json"` | 值文件类型，**单值**、缺省是字面的 `"json"`；`""` 不是合法取值。见[文件支持](file_support.md) |
| `no_one_file` | `False` | 多文件：键的 `<路径>:` 前缀寻址 `<home>/<路径>.<ext>`；没有前缀的键仍落默认文件 |
| `flush_window` | `0.0` | 攒批窗口（秒）。`0` = 每次声明当场落盘 |
| `log_path` | `""` | 审计文件（文件出口）的落点；空串 = `<home>/audit.log`，相对路径按 `<home>` 解析。见[日志](log.md) |
| `log_console` | `True` | 控制台出口（`stderr`）开关；文件出口没有开关 |
| `log_rotate` / `log_scrub` / `log_encode` | `None` | 三个口子：下一批写到哪个文件、落盘前怎么脱敏、最终落盘的字节。默认全不做 |
| `identity` | `""` | 写进每行记录的可选 `服务@主机` 标记 |

**写权限不在这里**：它由进程树决定 —— 创建实例的进程是属主，`fork` 派生出来的只读。
同一时刻只有一个写者是部署责任，见[并发模型](concurrency.md)。

拼错的参数不会被吞掉：

```python
AutoConf(hme="./conf")   # UnknownEngineParamError（它同时是 TypeError）
```

## 4. 使用口的三种模式

模式**只看 `value` 位填没填**，不看这一行「在不在声明」：

| 模式 | 写法 | 判据 | 语义 | 返回 |
|---|---|---|---|---|
| 1 | `conf(key, value)`、`conf(key, value, doc)` | `value` 填了 | 声明 + 写 | 当前生效值 |
| 2 | `conf(key, doc=…)` | `value` 空、`doc` 给了 | 只登记（空结构） | 事实里的值；没有就报错 |
| 3 | `conf(key)` | `value` 空、`doc` 没给 | 读 | 文件值，其次词表默认值 |

```python
conf("app.port")                    # 模式 3：读
conf("app.port", 8080)              # 模式 1：声明 + 写
conf("app.port", 8080, "服务端口")   # 模式 1：第三个位置就是 doc
conf("app.port", doc="服务端口")     # 模式 2：只登记，随即取值
```

四条硬口径：

- **`None` / `""` / `0` 都是填了**，一律算模式 1；`MISSING` 是唯一哨兵。
- 第 2 位置恒属 `value`，所以 `conf(key, x)` 永远是模式 1；模式 2 只能由 `doc=` 触发。
- `doc` 是第三个**位置**参数，也是唯一的登记元数据。判据只看 `value` 位，
  所以参数面**封闭**：新增参数不需要动判据。
- 值类型由载体决定（见[文件支持](file_support.md)）；覆盖既存值不是 `conf` 的能力
  （见下一节）；引擎参数只走 `AutoConf`。

### 报错口径

| 情形 | 结果 |
|---|---|
| 读未登记的键 | `KeyNotRegisteredError` |
| 已登记但事实里没有值 | `KeyHasNoValueError` |
| `key` 不是字符串 | `TypeError` |
| 传了不属于使用口的参数（`type=` / `force=` / `home=`…） | `TypeError` |
| 引导层参数在引擎起来之后改 | `ConfError` |

两类读错误必须分开，因为责任方不同：**键名写错了** vs **部署漏配了**。

## 5. 运行期的写路径：只补缺，不改已有

代码发出的写请求只做两件事：

1. **补缺**：期望有、事实没有 ⇒ 写进去；
2. **补元数据**：词表里的说明 / 默认值指纹与声明不一致 ⇒ 只更新词表。

对文件里**已经存在的值**，运行期一律只读：

```python
conf("app.port", 9090)   # 文件里已经是 8080（有人手改过）
                         # ⇒ 文件一个字节都不动，日志里记一条 op=skip
                         # ⇒ 返回的是 8080（当前生效值），不是 9090
```

**为什么没有覆盖出口**：配置是用户的持久状态，代码只能「补它没有的」，不能
「改它已经有的」。这是「文件是绝对权威」的直接推论 —— 如果代码能覆盖文件，
那文件的权威就是可撤销的，「文件优先」就不再是铁律，只是个默认值。

> 「程序想持久化一个值怎么办」的答案是：**不做**。
> 程序故意改一个已存在的值，越过了「配置属于用户行为」这条线。

## 6. 收敛与清理归命令行

「把值文件收敛到与声明一致」（含覆盖旧值）和「删掉代码未声明的键」都是**人主动
发起**的动作，不属于代码的写路径：

| 路径 | 发起方 | 做什么 |
|---|---|---|
| 导入即执行（本库） | 程序 | 只补缺 + 补元数据 |
| `onconf build` | 人 | **完整重建**：按声明集重写值文件（值 = 声明里的默认值）与词表；`--path DIR` 把整份产物写到别处，原目录一个字节不动。因为会丢手改内容，**建议先备份** |
| `onconf sync` | 人 | **温和收敛**：只补缺 + 更新词表 + 删除声明集里没有的键；**不覆盖已存在的值**。`--no-clean` 关掉删除，只做增量构建 |

判据不是「能不能覆盖」，而是「**谁发起**」：程序发起只补缺，人发起才可以收敛。

### 命令行

```text
onconf build [--home DIR] [--file-name NAME] [--file-type TYPE] [--no-one-file]
             [--path DIR] [--dry-run] [--json]
onconf sync  [--home DIR] [--file-name NAME] [--file-type TYPE] [--no-one-file]
             [--no-clean] [--dry-run] [--json]
```

声明**不靠执行代码**得到：使用口只有一个函数，所以命令行在项目里静态扫描
`conf(...)` 调用、按参数形态解读即可（`key` / `key,value` / `key,value,doc` /
`key,doc=…` / `key,value=…`）。

**非字面量实参不在支持范围内**：`APP_POST = "app.post"; conf(APP_POST, 8080)` 这种写法
会有人用，但命令行不解读、也不去替它求值 —— 只认字面量，其余一律进问题清单。**不静默
丢**是唯一的承诺。这类调用存在时，`sync` 会**拒绝删除任何键**（清理只在期望集完整时
才允许执行的直接推论）；确认无碍可以加 `--no-clean` 只补缺。

**为什么静态扫描够用**：扫描范围是「当前项目里的全部 `*.py`」，所以命令行与代码天然
同步 —— 不存在「加载了哪个声明入口、漏了哪个文件」这件事，也就不需要额外约定一套
声明文件。它是个**独立个体**：只依据当前代码，因此可以完整重建；也正因为如此，
**空目录（没有值文件、没有词表）直接 `sync` 同样成立** —— 重建与收敛本来就是同一件事
的两面。

`--dry-run` 一个字节都不写。扫描范围默认为当前项目（固定跳过 `.git` / `.venv` /
缓存目录等），`pyproject.toml` / `.gitignore` 的收敛留待后续版本。

> 其余七条命令（`check` / `format` / `diff` / `read` / `get` / `set` / `add`）
> **尚未实现**。**运行期不清理未声明的键**已经落地：删除只走 `onconf sync` 这一条
> 离线路径。口径见[并发模型](concurrency.md)。

## 7. 目录约定

```text
<home>/<file_name>.json       值文件（用户手改）；名字与类型分别由 file_name / file_type 决定
<home>/app/conf/net.json      多文件模式：键 `app/conf/net:…` 的落点（no_one_file=True）
<home>/schema/<file_name>.json  词表（**库自己的资产**，随便重写；多文件下也只有这一份）
<home>/audit.log              审计文件（append-only；落点由 log_path 决定）
```

- `home` 缺省是 **`./conf`**；`ONCONF_HOME` 仍然可以把它指到任何地方。
- 文件名主干由 `file_name` 给（缺省 `settings`，纯文件名），后缀由 `file_type` 给
  （缺省 `"json"`）；两者都改了就是换一套值文件与簿记，必须重启。
- 每个值文件的 `$schema` 指针按自己的层级算出相对路径（`app/conf/net.json` 写
  `../../schema/settings.json`）。

## 8. 使用范式：声明处必须字面量（**合法但不合理**）

### 判据

**声明形态**（`value` 位填了的那些调用）的键、值与说明都必须是**字面量**：

```python
conf("app.post", 8080, "服务端口")                     # ✅ 这就是规格
conf("slot.max.byte.b", 512, "格长档位之一")           # ✅

APP_POST = "app.post"
conf(APP_POST, 8080)                                  # ❌ 合法，但声明处不是字面量
for key, default in _TIERS:                           # ❌ 同上，而且链条更长
    conf(key, default)
conf(build_key(), 8080)                               # ❌
```

**读取不受这条限制**：`conf("app.post")` 与 `conf(APP_POST)` 都可以。读取不产生任何持久状态，
常量写错了会当场 `KeyNotRegisteredError`，不会静默。

### 为什么这么定

本库里**键字符串就是配置项的身份**：值文件的键、词表的键、`$schema` 给编辑器的补全、日志里的
`item=`、命令行的扫描，认的都是那串字符。声明处一旦换成名字，这串字符就不在声明点了 ——
不是「解析器不够强」，而是**没有可依据的东西**。

### 为什么不设门禁

**error 的分界是「不合法」；这一类是「合法但不合理」。** Python 完全允许这么写，在本库不合理，
所以：

- 代码里**不加**强制检查 —— 那等于把风格偏见做成硬约束（同一个口径：门禁降级为
  lint 警告）；
- 文档里**写清代价**，用不用由使用者自己决定；
- 未来 `check` 落地时，按上面的判据出 **warning**（不是 error）。

### 代价（写成这么用会丢的东西）

| 丢什么 | 具体后果 |
|---|---|
| 命令行的收敛能力 | `build` / `sync` 靠读 `conf(...)` 的实参得到期望集，藏起来的声明它们看不见：`sync` 会把它当作「代码没声明」；存在这类调用时 `sync` **拒绝清理**（宁可不动，也不猜），要清理得先去掉它们 |
| 静态可读性与可审计 | `grep` 一个键名找不到声明点；评审时看不到一张规格表；任何按调用点做的静态分析（含未来的 `check`）都覆盖不到 |
| 声明点的自证 | 计算出来的值与说明（`X if cond else Y`、f-string）在声明处看不见，读者得在脑子里求值 |
| 循环/数据结构形态额外丢的 | 代码里回答不了「我们到底有哪些配置项」；顺序之类的约束只能活在注释里（`_TIERS` 那种「顺序即书写顺序」） |

**不丢的**：值文件的编辑器补全靠的是**词表**（运行期登记过就有），所以补全照旧 —— 丢的是
「在代码里一眼看见键名」和静态工具链。

真需要批量声明同形键，那是**词表 / 代码生成**的活（`add` 之类生成出来的仍然是字面量），
不是运行期循环的活。
