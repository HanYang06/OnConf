# 命令行

> 本页是**命令行**的设计口径：九条命令各自做什么、写不写字节、入参与输出、退出码，
> 以及它与运行中的进程是什么关系。

## 1. 定位

命令行是**人 / CI 发起的配置管理者**，运行中的进程是**使用者**。两者不通过 IPC 对齐：
命令行不要求属主存在、不探测谁在用、不等谁点头（路线图 2-047）。

它是配置目录的**离线写入口**：运行期只补缺、不删键，完整重建与删除都归这里
（[初始化配置](init_config.md) §6）。命令行会先清掉 `ONCONF_OWNER_PID` —— 「想更新，
拿命令行去」这句话得成立（[并发模型](concurrency.md) §3）。

声明**不靠执行代码**得到。使用口只有一个函数 `conf(key, value=…, doc=…)`，所以命令行
在项目里静态扫描 `conf(...)` 调用、按参数形态解读：只做 `ast.parse`，**不 import、
不 eval**。扫描范围默认为当前项目，固定跳过 `.git` / `.venv` / 缓存目录等；
`pyproject.toml` / `.gitignore` 的收敛是后续版本的事（路线图 2-056）。

**命令行不执行项目代码**是安全不变量（[威胁模型](../security/threat-model.md) 的 T13）：
扫不动的调用不猜、不静默丢，直接列进问题清单。

### 1.1 解析层不引第三方框架

解析层是标准库 `argparse`，不引 Click / Typer / Cyclopts 这类 CLI 框架：

- 九条命令的工作量全在语义（只读路径、寻址、退出码），换框架一点不省，只多一层迁移面；
- 输出要逐字可控、非 TTY 必然无 ANSI，手写输出比框架的渲染更贴这条要求
  （[日志](log.md) §4 对终端渲染的取舍同源）；
- 破坏性命令的输出与退出码已经是定稿的契约（路线图 2-046），换框架会把改动从解析层
  牵连到输出层。

美化 `--help` 只动渲染层，不动解析层，因此不构成换框架的理由。

## 2. 命令表

主干九条 —— `build` / `sync` / `check` / `read` / `get` / `set` / `diff` / `format` / `add`
—— 再加 `log` 一条补条：

| 命令 | 语义 | 破坏性 | 分配版本 |
|---|---|---|---|
| `build` | 按声明**完整重建**值文件与词表；`--path DIR` 把整份产物写到别处，原目录一个字节不动 | 是（重建） | 2.0.0（已交付） |
| `sync` | **温和收敛**：补缺 + 更新词表 + 删除声明集里没有的键；`--no-clean` 只补缺 | 是（删除） | 2.0.0（已交付） |
| `check` | 三个口径的对比（代码 / 词表 / 值文件）；通过回一行，不通过按六类逐条报 | 否 | 2.0.0 |
| `read` | 文件级原始数据读取（读落盘的原始字节） | 否 | 待定（取决于 2-036） |
| `get` | 键级取值：输出 `key` / `value` / `path` / `doc` 四列，多命中全部刷出 | 否 | 2.0.0 |
| `set` | 改**已有**键的值；`--default` 改词表里的默认值（不改代码） | 是 | 2.0.0 |
| `diff` | 扫日志里全部 `Change` 记录，一行一条变更 | 否 | 2.0.0 |
| `format` | 只对 JSON 值文件重排缩进 | 是（重写文件） | 2.0.0 |
| `add` | 新增键 + 更新词表 + 生成声明代码（产出新文件） | 是（产出新文件） | 2.1.0 |
| `log` | 日志分析：按级别 / 时间 / 键 / 执行者筛选，跨落点按时间序合并 | 否 | 2.1.0 |

三条分工判据，别混：

- `build` 与 `sync` 的差别只在**是否清理**；
- `get` 是键级取值，固定四列；`read` 后移，存在性取决于日志能不能二进制落盘（路线图 2-073）；
- `set` 有两个动作：缺省改**值文件**，`--default` 改**词表默认值**；创建键是 `add` 的活。

### 2.1 参数面

| 参数 | 命令 | 语义 |
|---|---|---|
| `--home DIR` | 全部 | 配置目录；缺省 `./conf` 或 `ONCONF_HOME` |
| `--file-name NAME` | 全部 | 值文件名主干；缺省 `settings` |
| `--file-type TYPE` | 全部 | 值文件类型；缺省 `json`（2.0 只保证 JSON，见 §2.2） |
| `--no-one-file` | 全部 | 多文件：键里的 `<路径>:` 决定落点 |
| `--dry-run` | 破坏性命令 | 只打印要做什么，不写一个字节 |
| `--json` | 全部 | 机器可读输出 |
| `--path DIR` | `build` | 重建产物的输出目录 |
| `--no-clean` | `sync` | 只补缺，不删键 |
| `--file X` | `get` / `set` | 限定目标文件；与键内嵌路径 `X:k` 等价 |
| `--default` | `set` | 改词表里的默认值，不改代码；会去追踪声明点 |
| `--default-force-code` | `set` | 未来版本：尝试改声明处的代码（路线图 2-075） |
| `--verbose` | `check` | 细节模式：完整报告；缺省只报 CI 状态 |
| `--strict` | `check` | 把 warning 也算进通过判定（缺省不升级，路线图 2-048） |
| `--indent N` | `format` | 缩进宽度，也是唯一的触发参数 |
| `--code-file PATH` | `add` | 生成物落点；缺省 `conf.py` |
| `--level` / `--since` / `--until` / `--key` / `--id` | `log` | 四个筛选维度 |

`--home` / `--file-name` / `--file-type` / `--no-one-file` 与 `AutoConf` 的同名参数一一对应：
命令行不引入第二套配置目录约定。`check` **不带 `--fix`** —— 它只检查与报告，收敛是 `sync` 的活。

### 2.2 2.0 只保证纯 JSON

2.0 的设计、检查项与验收**只覆盖纯 JSON 值文件**。YAML / `.env` / TOML 上的命令行行为
**不承诺**，不进这一版的验收范围；扩展留到后续版本（路线图 2-072）。

- `--file-type` 仍与 `AutoConf` 的 `file_type` 一一对应，是透传参数；
- `check` 的第三个口径是值文件，只读不写；
- `format` 只做 JSON —— 除了版本范围，三条技术理由也各自成立：YAML 的缩进是语法、
  TOML 的注释必须保留而标准库只有读侧、`.env` 结构扁平；
- `read`（条件项）读的就是落盘的原始字节；二进制与加密形式随路线图 2-036 / 2-037 一起定。

## 3. 统一约定

1. **`--dry-run` 不写一个字节**：工作区内既有文件的 mtime 与内容都不变，也不新增文件与目录。
2. **每个命令的退出码必须定义**：`0` 表示成功或检查通过，非 0 按错误分类（分类表见 §6）。
3. **需要机器可读输出的命令提供 `--json`**；同一命令的 `--json` 与非 `--json` 必须来自**同一份数据**，不许各算一遍；`--json` **一律给全量字段**，细节模式只影响人读渲染。
4. **不做交互选择**：一个键命中多个文件时不问「选哪个」，直接把候选逐条列出来并要求显式给出落点 —— 在管道与 CI 里问，等于永久阻塞。
5. **`--file X k` 与键内嵌路径 `X:k` 等价**：`get --file X k` 与 `get X:k` 输出一致；两种写法只在多文件开启时解析路径。
6. **`get` 是键级取值**：每行四列 `key` / `value` / `path` / `doc`，与值文件类型无关；`--json` 就是这四列的对象数组。
7. **`diff` 扫日志里的 `Change` 记录**：一行一条变更，参照系是**词表里的值**与**日志里记的值**；不读哈希、不建索引，对着值文件比归 `diff --value`（路线图 2-071）。
8. **查询跨落点合并**：轮转是「换落点」，切断的是一个文件里的历史，`diff` 与 `log` 必须按时间序合并全部落点。
9. **破坏性命令的输出要能回答「哪个文件、哪些键、变成什么」**，并提示目标配置目录可能正在被进程使用。
10. **不建实例的命令不落盘**：`check` 走只读路径，因此没有记录、不建目录 —— 那是「没有记录」，不是「有个开关把它关了」（[日志](log.md) §3）。
11. **输出一律英文**：状态、标签、错误、建议都用英文，不混中文；已交付的 `build` / `sync` 也照这条改（路线图 2-077）。

## 4. 逐命令细则

### 4.1 `build` / `sync`

```text
onconf build [--home DIR] [--file-name NAME] [--file-type TYPE] [--no-one-file]
             [--path DIR] [--dry-run] [--json]
onconf sync  [--home DIR] [--file-name NAME] [--file-type TYPE] [--no-one-file]
             [--no-clean] [--dry-run] [--json]
```

- `build` 的产物里**只有声明集**：值文件从后端种子起步逐键追加，词表整篇重写。它会丢掉
  手改内容，所以输出固定建议**先备份，或改用 `--path`**。
- `sync` **不覆盖已存在的值**：只补缺、更新元数据、删除声明集里没有的键。`--no-clean`
  关掉删除，只做增量构建。
- 期望集**不完整**（扫描到读不懂的调用）时两条命令分开处置：
  - `sync` 要删键，而删除的判据「事实里有、声明集里没有」只在期望集完整时才成立 ——
    因此它**拒绝删除任何键**并以非 0 退出；确认无碍请加 `--no-clean`，或把那些调用改成字面量；
  - `build` 本来就以声明为准，照常执行，把读不懂的调用逐条打出来。
- 空目录（没有值文件、没有词表）直接 `sync` 同样成立：重建与收敛本来就是同一件事的两面。

### 4.2 `check`

逻辑是**三个口径的对比**，最后给一份报告：

- **代码** —— 静态扫描项目里的 `conf(...)`，得到配置项、默认值与 `doc`；
- **词表** —— 读当前 `<home>/schema/<file_name>.json`；
- **值文件** —— 读 `<home>` 下的值文件（多文件模式下是全部落点）。

两个模式，只有报告详略不同：

| 模式 | 参数 | 输出 |
|---|---|---|
| 缺省 | —— | **纯 CI 状态**：通过回一行，不通过只报问题本身 |
| 细节 | `--verbose` | **完整报告**：每条问题补上落点文件，多文件模式下这才看得清 |

通过：

```text
All config items are OK.
```

不通过，缺省模式一类一行，只带键：

```text
missing     new.key
stale       old.key
default     app.post   8080 => 8000
doc         app.post   "服务端口" => (none)
unfilled    app.port
undeclared  legacy.key
```

`--verbose` 在行尾补上 `path`（多文件模式下它是「这个键落在哪个文件」）：

```text
missing     new.key     settings.json
unfilled    app.port    app/conf/net.json
undeclared  legacy.key  settings.json
```

六类判据，每一类都对应一个收敛动作：

| `kind` | 判据 | 谁来收敛 |
|---|---|---|
| `missing` | 代码声明了、词表里没有 | `sync` / `build` 登记 |
| `stale` | 词表里有、代码没声明 | `sync` 删除 |
| `default` | 默认值不一致（代码 vs 词表） | `sync` 更新词表 |
| `doc` | `doc` 不一致（代码 vs 词表） | `sync` 更新词表 |
| `unfilled` | 代码声明了、值文件里没有 | `sync` 补缺 |
| `undeclared` | 值文件里有、代码没声明 | `sync` 删除 |

**不报「值文件里的值 ≠ 当前默认值」**：那是「文件绝对优先」的正常结果，报它等于让每个真实
部署的 CI 恒红。

- **不带 `--fix`**：这个工具只做检查与报告，不改任何东西。不通过时末行固定推荐收敛工具：
  `Run "onconf sync" to align the vocabulary and the value files.`
- **顺序稳定**：全部发现按 `key` 的**码位序**排（`sorted()`：数字 < 大写 < 小写），
  同一份输入跑两次必须逐字相同 —— CI 里要比对两次输出。
- 扫不动的**声明**（第一实参不是字符串字面量）出 warning，不改变通过判定
  （[初始化配置](init_config.md) §8）；`--strict` 把 warning 也算进通过判定。
- 走一条**专门的只读路径**：不建引擎实例，因此不产生记录、不落盘、不建目录。它读三个口径，
  **一个字节都不写**。
- 只读性是硬约束，写成回归断言：跑完 `check` 后工作区内既有文件的 mtime 与内容不变，
  且不新增文件与目录。
- 受众是手动查一遍与 CI；`--json` 与报告同源，字段是**全量**的（细节模式只影响人读渲染）。
  每条 finding 的字段**固定五个**（`kind` / `key` / `path` / `code` / `vocabulary`），
  不适用的写 `null` —— 固定字段比按需省略好解析，`ruff` / `eslint` 的 JSON 都是这个路子：

  ```json
  {
    "command": "check",
    "ok": false,
    "summary": {
      "missing": 1, "stale": 1, "default": 1, "doc": 0, "unfilled": 1, "undeclared": 1
    },
    "findings": [
      {"kind": "missing", "key": "new.key", "path": "settings.json", "code": null, "vocabulary": null},
      {"kind": "default", "key": "app.post", "path": "settings.json", "code": 8080, "vocabulary": 8000},
      {"kind": "stale", "key": "old.key", "path": null, "code": null, "vocabulary": null}
    ],
    "warnings": [
      {"kind": "convention", "where": "app/conf.py:12", "message": "key is not a string literal"}
    ]
  }
  ```

### 4.3 `get`

输出是**固定的四列**，与值文件类型无关：

```text
key            value   path              doc
app.post       8080    settings.json     服务端口
```

- `path` 这一列在多文件模式下才有信息量（键落在哪个文件）；单文件模式就是那份值文件。
- **同名的键有多少刷多少**：多文件模式下同一个键可能出现在多个文件里，`get` 不挑一个，
  全部列出来 —— 这正是 `path` 这一列存在的理由。
- 按词表校验：键没登记过 ⇒ `KeyNotRegisteredError`（键名写错）；登记过但事实里没有值 ⇒
  `KeyHasNoValueError`（部署漏配）。两类失败刻意分开，因为责任方不同。
- `--json` 就是这四列的对象数组。
- `--file X`（等价于 `X:k`）只用来**过滤**候选文件，不是消歧义的必要条件。
- 只读：不写值文件、不写词表、不产生记录。

### 4.4 `set`

`set` 有两个动作，改的不是同一个东西：

| 写法 | 改什么 |
|---|---|
| `set <key> <value>` | **值文件**里的值 |
| `set --default <key> <value>` | **词表**里的默认值 |

#### 改值文件（缺省动作）

- 只改**已有**键的值，落点是后端的 `set_value` —— 这条路径在运行期没有驱动者，
  本来就是留给命令行收敛动作的（[文件支持](file_support.md) §7）。
- 成功只回一行 `OK`；失败回 `Error: …` 并以非 0 退出。
- **命中多个文件就拒绝**，把候选逐条列出来：

  ```text
  Error: key "app.post" exists in more than one file
    1: app.post   settings.json
    2: app.post   app/conf/net.json
  Please specify the file with --file, or write the key as <path>:<key>.
  ```

  消歧义的手段是 `--file` 或键内嵌路径 `X:k`，不是交互选择（统一约定 4）。
- 破坏性：支持 `--dry-run`；执行前必须能回答「哪个文件、哪个键、从什么变成什么」。

#### 改词表默认值（`--default`）

- 它**不改代码**：改完会回到静态扫描里找「哪一处声明了这个键」——
  - 找到了 ⇒ 告诉你要长期保留这个默认值就得改代码的哪一处（或者改用参数）；
  - 找不到 ⇒ 出一条 warning，说明这个默认值在代码里没有声明点。
- 词表是库自己的资产，改它与 `build` / `sync` 一样是管理者动作，由人发起。
- 破坏性：支持 `--dry-run`。
- `--default-force-code`（**当前版本不设计**）：主动去改声明处的代码 —— 找到且只有一处时
  **尝试**改，改不动就警告让你手改，改成功才算成功。只为未来版本预留（路线图 2-075）。

### 4.5 `diff`

默认输出一行一条变更：

```text
<path> : <key>  <value>  <doc>  =>  <key>  <value>  <doc>
```

两边各是一个三元组：`key` 是身份，两边永远显示；`value` 与 `doc` 只有变了的那一侧才不同。

- 参照系是**词表里的值**（当前的声明口径）与**日志里记的值**。不对着值文件比 ——
  日志跟踪的是词表，不是值文件；要对着值文件比就得另做一层跟踪，那是 `diff --value`
  的活，放到后续版本（路线图 2-071）。
- 右侧的 `doc` 在 2.0 里**没有来源**：日志的 `Record` 不记 `doc`，所以先占位显示 `(none)`，
  等日志把 `doc` 记上（路线图 2-076）才有真值 —— 列位不变，格式不用跟着改。
- 数据来源就是**日志文件的 `Change` 记录**：扫一遍全部落点，按**键**给出变更历史。
- **不读哈希、不建索引、不产跟踪文件**：索引那条路要么新增一种落盘形态，要么与 git
  配合，复杂度与收益不成比例（路线图 2-050 已定）。
- 与 `log` 的分工按**问题类型**分：变更历史归 `diff`，原始记录筛选归 `log`
  （路线图 2-067 已定）。
- 轮转会切断一个文件里的历史，所以查询必须跨落点按时间序合并。
- 只读。

### 4.6 `format`

- **只对 JSON 值文件生效**，YAML / TOML / `.env` 一律不提供且不写字节：
  - YAML 的缩进是**语法**而不是视觉，schema 指针与用户注释必须逐字保留；
  - TOML 有行尾注释且写回必须保留，而标准库只有读侧；
  - `.env` 扁平且字符串化，缩进没有可作用的结构。
- JSON 不支持注释，所以格式化等于**纯缩进重排**：键集合、键序、每个值的语义与 `$schema`
  成员逐字等价，只有空白变化。
- **不带格式化参数时一个字节都不写**：默认状态是「能塞就塞」，命令不得顺手重排。
- 实现是一条与外科手术式回写**并列**的独立路径；四个后端既有的 `append_key` /
  `set_value` / `delete_key` 不变量不受影响。

### 4.7 `add` / `log`

两条都是 2.1.0 的活（路线图 2-045），口径先落在这里：

- `add` 的动作集合 = 新增键 + 登记词表 + **生成声明代码**，生成物是**新文件**，不改写任何
  既有文件。落点由 `--code-file` 给，缺省 `conf.py`。生成物**不被 import 就不生效**，
  命令输出必须提示这一点；生成文件的头注释写明「import 该文件即写盘」。
- `log` 的数据**只来自文件出口那一份**，不取终端出口。四个筛选维度：`--level`（`Read` /
  `Write` / `Change` / `Error` / `Start`）、`--since` / `--until`、`--key`、`--id`
  （对应记录里的 `pid` 与 `identity`）。`--json` 的字段与记录一一对应，查询跨全部落点
  按时间序合并，命令只读。

### 4.8 `read`（条件项）

- `read` 取**文件级原始数据**：不按词表解读，落盘是什么就读回什么。
- 它存在的前提是**日志落盘能走二进制**。落盘形式由文件出口的 `log_encode` 决定
  （路线图 2-036 / 2-037）：二进制可行才需要一条把原始字节读回来的命令，不可行就不需要它。
- 因此它**不在 2.0 的范围内**，随落盘形式一起定（路线图 2-073）。

## 5. 破坏性操作的形态与安全

- 破坏性命令**一律支持 `--dry-run`**，且**缺省不是** dry-run。
- 执行前必须能回答「哪个文件、哪些键、变成什么」；输出逐条列出将发生的变化。
- **不做交互选择**：多命中直接列出候选并以非 0 报错（统一约定 4）。
- 破坏性命令的输出必须提示「目标配置目录可能正在被进程使用」。
- **命令行不与进程模型握手**：不看锁文件、不探测端点、不要求属主存在（路线图 2-047）。
- **不要求显式确认，也不自动备份**：安全阀是「计划打全 + `--dry-run`」（路线图 2-046 已定）。

## 6. 退出码与输出

**语言：一律英文。** 命令行**自己写的**文本 —— 状态、标签、错误、建议 —— 都用英文，不混
中文；已交付的 `build` / `sync` 也照这条改（路线图 2-077）。

**库产出的文本不在这条口径里**：`ConfError` 的消息、计划里的 `reason=` 取自库的数据
（后者还要落进审计文件），它们随库的语言，命令行原样透传 —— 不要为了「输出纯英文」
去翻译它们。

**通道分工**：

- **`stdout`** 放这次命令的**结果**：报告、计划、`--json` 文档；
- **`stderr`** 放**跑不起来**的原因（参数错、目录读不到）与库日志 —— `stdout` 是调用方的数据通道；
- `--json` 时 `stdout` 上只有那一份 JSON 文档，不放别的东西。

**退出码**：`0` = 成功 / 检查通过，非 0 = 失败。细分类别是给脚本看的，CI 只问「是不是 0」：

| 码 | 含义 | 例子 |
|---|---|---|
| 0 | 成功 / 检查通过 | —— |
| 1 | 引擎错误（`ConfError` 族） | 键未登记、派生进程试图写 |
| 2 | 用法错误 | 未知子命令、参数不合法（沿用 argparse 的约定） |
| 3 | 值文件读不出来（读期 `ValueError` 子类） | JSON 语法错误（非 JSON 后端随路线图 2-072） |
| 4 | 期望集不完整，拒绝清理 | `sync` 扫到非字面量实参 |
| 5 | `check` 发现问题 | 三个口径对不上（见 §4.2 的六类） |

## 7. 与运行中进程的关系

- 角色定死：命令行是**管理者**，运行中的进程是**使用者**。管理动作在运行期执行时，
  使用者读到的是管理后的结果（键消失、值改变），而不是崩溃或写了一半的状态 ——
  写入是原子替换，读者看不到半截文件。
- 使用者发现变化靠指纹（值文件 + 词表的 `mtime` + 大小）与读前重读，机制不变
  （[并发模型](concurrency.md) §6）。
- 命令行不与任何进程的内存状态同步：这是「离线、单次、全量、由人发起」的定义。
- 删除未声明的键时，词表条目**一并消失**（`clean` 动作同时也从词表里去掉该键），
  因此使用者随后读到的是 `KeyNotRegisteredError` —— 它的归因写的是「键名写错」。
  这条归因要不要单列一类「键已被管理者移除」，见 §8.3。
