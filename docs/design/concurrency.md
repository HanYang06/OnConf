# 并发模型

> 本页是**并发**的设计口径：一个配置目录上谁能写、读会看到什么、引擎不管什么。
>
> 本页写的是**目标口径**，不是既有能力 —— 与当前实现之间的差异集中在最后一节
> 「还没落地的部分」。哪些能力算交付、按什么顺序交付，以路线图为准。
> 使用口见[初始化配置](init_config.md)，值的落点见[文件支持](file_support.md)，
> 记账见[日志](log.md)。

## 1. 一句话

**引擎只干三件事：读配置、写配置、生成词表。跨进程并发不是它的事。**

没有**跨进程**锁、没有独立写者进程、没有 IPC、没有端点、没有待折日志、没有跨进程一致性
保证。引擎不探测、不等待、不猜。

**进程内那一层由引擎自己兜住**：同一进程里的多个实例、以及同一实例的多个线程，共用一把
**纯内存**的锁（键是「配置目录 + 值文件名主干 + 后缀」）。那是常见的那一种并发，也是不加锁
就会当场丢更新的那一种。

## 2. 实例 = 池 + 寻址，读写只是信号

每个进程里都有一个配置实例，它是这笔事务的**上下文** —— 没有它连「这次事务属于谁」
都画不出来。

| 组成 | 是什么 |
|---|---|
| **池** | 值文件的事实、词表、本进程的声明集，全部驻内存 |
| **寻址** | `conf(key)` = 键 → 哪个值文件 → 文件内哪一条 |
| **信号** | 调用方只表达意图；**是命中内存还是读盘、什么时候落盘，由实例决定** |

## 3. 角色：创建者写，派生的读

写权限不靠承诺、不靠开关，靠**进程树**：

| 角色 | 怎么进入 | 能力 |
|---|---|---|
| **属主** | **创建这个实例的进程** | 读 + 写值文件 + 生成词表 |
| **派生** | `fork` 出来的进程（内存被复制，但 pid 对不上） | 只读 |
| **派生** | `spawn` / `subprocess` 出来的进程（读到了属主留下的 `ONCONF_OWNER_PID`） | 只读 |

判据是**两次核对**，都不需要谁发誓：

- 实例记下创建它的 pid，落盘前比一次 —— 对不上就是 `fork` 出来的；
- 属主建实例时把 pid 写进环境变量 `ONCONF_OWNER_PID`，子进程天然继承 —— 这是
  `spawn` / `subprocess` 唯一能拿到的线索（它们不继承内存，只继承环境）。

任一条对不上就拒绝写、当场报错并写明两条出路（让属主写，或用命令行离线写）。
`ONCONF_OWNER_PID` 与 `ONCONF_HOME` 同级：**可信输入**。

**唯一的例外是命令行自己**：`onconf` 是人 / CI 发起的配置管理者，它会先清掉
`ONCONF_OWNER_PID` —— 「想更新，拿命令行去」这句话得成立。它不跟运行中的进程协调，
那是调用方的部署责任。

## 4. 唯一的一条禁令

> **同一个配置目录，同一时刻只有一个写者。**

这条禁令是调用方的**部署责任**，不是引擎的运行期机制。违反它的后果是明确的：

- 两个进程各自读-改-写同一个值文件 ⇒ **丢更新**（后写的把先写的整段盖掉）；
- Windows 上替换文件撞上并发的读者 ⇒ `os.replace` 报 `ERROR_ACCESS_DENIED` ——
  引擎在有界范围内重试（读者不参与互斥，也不该参与），但不会去协调写者。

## 5. 三种部署形态都有确定答案

| 形态 | 谁写 | 运行期 |
|---|---|---|
| 单进程（脚本、工具、单实例服务） | 它自己 | 读写 |
| 主进程 + 子进程 | 主进程 | 主进程读写；`fork` 出来的子进程自动只读 |
| N 个平级进程 | **没有人** | 起进程之前用命令行把配置落好（`onconf build` / `sync`），运行期全部只读 |

第三格是唯一正确的答案，也是**唯一的并发故事**：引擎不替它们协调 —— 那种写法本来
就不该被支持。

## 6. 读：事实优先 + 指纹校验

读**任何进程都能做**，也不需要许可。两条规则：

- **值只从值文件读**：先事实、再词表兜底、都没有才报错（两类错误分开）。
- **读之前比一次指纹**（`mtime` + 大小），变过就重读。少了这一步，进程内存会永远停在
  第一次加载的样子 —— 属主进程后来的写、用户的手改，它都看不见。

读的寻址**按被读的键自己决定**加载哪个值文件：多文件模式下，一个进程完全可以读别人
声明过的键，只看「本进程声明过哪些路径段」会读到词表默认值而不是文件里的值。

## 7. 写：只补缺、只补元数据

运行期的写只有两种动作：

- **补缺**：期望有、事实没有 ⇒ 写进去；
- **补元数据**：词表里的说明 / 默认值指纹与声明不一致 ⇒ 只更新词表。

对文件里**已经存在的值**一律只读（值不一致时产出一条 `op=skip`）。**运行期不删任何键**：
删除的判据「事实里有、声明集里没有」只有在声明集**完整**时才成立，而运行期一个进程的
声明集永远只是它自己那份。删除归命令行（离线、单次、全量、由人发起），代价是值文件会
随时间积累不再声明的键。

## 8. 引擎明确不做的

| 不做 | 依据 |
|---|---|
| 跨进程锁、选举、端点、IPC | 禁令把并发排除在模型之外，跨进程锁只是在保护一个不存在的保证 |
| 待折日志 / 缓存目录 / 收敛（fold） | 同上；顺序、冲突消解、跨进程可见性都随之不需要 |
| 跨进程一致性 | 一个进程 = 一个快照 + 它自己的写；要看见新值就重新起一个进程 |
| 运行期清理未声明的键 | 见「写」一节 |
| 探测「现在有几个进程在用」 | 探测结果不该改变行为。真要看，那是 `check` 的诊断，不是运行期机制 |

**进程内不在此列**：同一份值文件上的多个实例 / 多个线程共用一把内存锁，这是引擎的
分内事 —— 它不碰文件系统，也不改变「跨进程只有一条禁令」这件事。

## 9. 对配置面的影响

| 参数 | 说明 |
|---|---|
| `flush_window` | 保留，但语义收窄成**纯攒批**：跨进程没有可见性问题，攒批只是少写几次 |
| `ONCONF_OWNER_PID`（环境变量） | 属主标记，不是参数：与 `ONCONF_HOME` 同级，**可信输入** |

刻意不给开关的东西，连同理由一起记在这里（配置引擎自己的行为也该有据可查）：

- **不给 `read_only` 开关**：只读是由进程树推导出来的角色，不是一个需要用户表态的选项 ——
  让用户表态等于把时序问题换成配置问题。
- **不给「等待/重试」参数**：唯一的重试是替换文件时的有界重试（Windows 的读者冲突），
  它是实现细节，不值得暴露成参数。

## 10. 还没落地的部分

当前实现与本页口径之间的已知差异，逐条列出，不要当成既有能力：

| 事项 | 现状 |
|---|---|
| 派生进程只读（`fork` 与 `spawn` 两条路） | 已经落地（pid 核对 + `ONCONF_OWNER_PID` + 当场报错） |
| 进程内实例 / 线程互斥 | 已经落地（一份值文件一把内存锁） |
| 运行期不清理未声明的键 | 已经落地；删除只由 `onconf sync` 走 |
| 读的指纹校验 | 已经落地（读前比对，变过就重读） |
| `check` 报告目录上的并发使用 | 未实现 |
