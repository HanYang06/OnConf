---

## 1. 定位

一句话：**一个基于本地文件的、进程内使用的配置引擎，对外只暴露一个入口。**

- 不是服务、不是配置中心、不走网络。
- 单机，但要**多进程 / 多实例同时读写**安全。
- 目标场景：同一个程序被起多份，或一份程序里多个模块，都要读写同一批配置文件。

---

## 2. 能力清单

| 能力 | 说明 |
|---|---|
| 声明配置 | 代码里声明「存在这样一个键」，带类型 |
| 声明默认值 | 键不存在时取的值 |
| 无参数配置 ❓ | 不依赖任何文件 / 环境变量就能取到的配置（纯默认层） |
| 读写参数 | `get` / `set` |
| 多格式 | JSON、YAML、`.env`、系统环境变量 |
| 多文件 | 一次加载多个文件，按顺序层叠覆盖 |
| 词表 | 按文件格式导出该文件的可寻址键空间 |
| 审计报告 | 「本次运行声明了什么、读写情况如何」 |
| 并发 | 多进程 / 多实例同写不丢更新 |
| 事务 / 攒批 | 攒一批写一批，避免高频写打死磁盘 IO |
| 前缀控制 ❓ | 语义待定，见 §9 |

## 3. 地基：键空间与词表

**结论：词表不是一个附加功能，它是整个引擎的核心数据结构。** 声明、默认值、层叠、前缀、审计，全部建立在它之上。

### 3.1 统一寻址

对外只有一种键写法：点分路径 `app.server.port`。

每个后端有一个 KeyCodec，负责把统一键翻译成该格式的物理形态：

| 后端 | 物理形态 | 可逆性 |
|---|---|---|
| YAML / JSON | 嵌套结构 `{"app":{"server":{"port":8080}}}` | 可逆 |
| `.env` / 环境变量 | 扁平 `APP_SERVER_PORT=8080` | **不可逆** |

### 3.2 不可逆映射是必须正面处理的问题

`app.server.port` → `APP_SERVER_PORT` 没问题，但反过来：
`APP_SERVER_PORT` 可能来自 `app.server.port`、`app.server_port`、`app_server.port` 三者中的任意一个。

处理规则：

1. 词表里保存**已声明键 → 物理键名**的显式映射，优先走映射表。
2. 未声明的键走默认规则（`.` → `_`，全大写）。
3. Windows 上环境变量**大小写不敏感**，词表内部需统一归一化，否则会出现「同一个键两个名字」。

### 3.3 词表的形态

```python
{
  "app.server.port": VocabEntry(
      type=int, default=8080,
      origin="declared|file|env",     # 这个键当前的值是哪来的
      physical="APP_SERVER_PORT",     # 物理键名（.env / env 后端才有意义）
      writable=True,
  ),
  ...
}
```

### 3.4 「能支持词表的格式才给词表」

不同格式的表达力不同，词表能力分档：

| 后端 | 能枚举键 | 能表达嵌套 | 能表达类型 | 词表档位 |
|---|---|---|---|---|
| YAML / JSON | ✅ | ✅ | 弱（靠声明补） | 完整 |
| `.env` | ✅ | ❌ | ❌（全字符串） | 仅扁平键清单 |
| 系统环境变量 | ✅（全量，噪音大） | ❌ | ❌ | 仅已声明键，否则不给 |

含义：`vocab()` 对 `.env` 只返回键名列表，不给结构；对系统环境变量**只返回被声明过的键**，不返回全量（否则会把整个环境倒出来）。

## 4. 层叠与优先级（已按「代码不权威」原则修正）

**代码里的默认值不是一层配置源。** 它只在「注册」这一瞬间起作用，
作用是写入词表（登记键、类型、文档、默认值）。注册完成后，代码不再参与求值。

求值链路：

```
① 词表        ← 权威：这个键存在吗、类型是什么、文档是什么、默认值是什么
② 配置文件    ← 值的事实来源
③ 环境变量    ← 运行时覆盖（12-factor）
④ 代码        ← 不参与
```

- 「无参数配置」= 词表里有这个键，但文件与环境都没有 → 直接取词表里的默认值。
  这才是「无参数」的准确含义：不需要任何外部参数就能解析出来。
- 注册规则：**有默认值 → 更新配置文件并填上默认值；无默认值 → 只更新词表**（只登记）。
  这条保证每次注册都有落脚点。
- 代码改了默认值，**已注册的键不会跟着变**，除非显式重注册。
- `get()` 返回时同时记录 `origin`，这是审计报告的关键信息。

## 5. 并发 · 事务 · 攒批（本项目最大的工程难点）

### 5.1 危险组合

「攒批写」+「多进程同写」如果实现成「内存里攒一批，定时写回文件」，必然出两个问题：

1. **丢更新**：两个进程各自 read-modify-write，后写的把先写的整段覆盖掉。
2. **崩溃丢数据**：攒在内存里的那批，进程一挂就没了。

攒批是为了 IO，不是为了让语义变弱。所以二者必须分开设计。

### 5.2 方案：WAL + 单写者合并 + 前缀分片锁

```
x.yaml            ← 主文件（物化视图，给人看 / 给别的工具读）
x.yaml.wal        ← 预写日志，append-only JSONL
x.yaml.lock       ← 跨进程锁
```

**写入路径**

1. `set(k, v)` → **只 append 一条记录到 WAL**，立刻返回。
   `{"k":"app.port","v":9090,"ts":...,"pid":1234,"op":"set"}`
   - WAL 是顺序写，极快，几十万次 set 也不会打死 IO。
   - 数据在 WAL 里就是持久的 → **崩溃不丢**。
2. `flush()` 触发时机（三选一先到）：定时去抖 `flush_interval`（默认 0.5s）、批量阈值 `flush_batch`、显式 `flush()` / `close()` / `with` 退出。
3. `flush()` 流程（拿排他锁）：
   读主文件 → 回放 WAL → 写临时文件 → `os.replace()` 原子替换 → 压缩 / 清空 WAL。

**读取路径**

主文件 + WAL 回放。所以**读一定能看到其他进程已经 append 的写入**，不需要等 flush。

**崩溃恢复**

- `os.replace` 是原子的 → 主文件不会半写。
- 残留 `.tmp` → 启动时清理。
- 残留 WAL → 启动时自动回放，然后再合并。

### 5.3 前缀分片锁 ❓

锁粒度不应该是整个文件，而应该是 **key 前缀**：不同前缀的写互不阻塞，同前缀串行。
这大概是你说的「前缀控制」。**需要确认**：前缀是纯粹的并发优化，还是同时承担命名空间隔离的职责？

### 5.4 必须写进文档的语义

> `set()` 返回时，数据已经在 WAL 里（durable）；主文件是延迟物化的视图。

这是唯一能同时满足「攒批」和「不丢数据」的语义。如果你要的是「纯内存攒批、挂了就丢」，那是另一种设计，请明确。

### 5.5 已知坑

- Windows 上文件锁与杀毒软件 / OneDrive 同步目录会打架，配置文件必须放本地普通目录。
- 手工编辑主文件与 WAL 冲突时，按时间戳「最后写赢」；**手工改的键如果也在 WAL 里，会被 WAL 覆盖**。这个规则要写进 README。

## 6. 审计与报告

双通道，不要混在一起：

- **事件流**（机读）：JSONL 追加，事件类型 `declare / get / set / flush / conflict / error`，每条带 `ts, pid, key, origin, result`。
- **人读报告**：rich 表格，`conf.report()`。
  内容：本次运行声明了哪些配置、哪些被读取、哪些被写入、跨进程冲突几次、WAL 合并了几次。

默认关闭（有性能成本），显式开启。

## 7. 公开 API 形态 ❓

**提案 A（推荐）——「1 个 API」= 1 个入口符号**

```python
from onconf import AutoConf

conf = AutoConf.load("./conf", env=True, audit=False)   # 唯一入口

conf.declare("app.port", int, default=8080)
conf.declare("app.name", str, default="svc")

conf.get("app.port")        # 8080
conf.set("app.port", 9090)
conf.flush()

conf.vocab()                # 词表
conf.report()               # 审计报告
```

**提案 B —— 字面意义上的「一个函数」，op 是第一个参数**

```python
from onconf import conf          # 模块级单例，无需初始化

conf("set", "app.port", 9090)
conf("get", "app.port")             # -> 9090
conf("declare", "app.port", default=8080, type=int)
conf("set", items={"a.b": 1, ...})  # 批量：一次调用 = 一批
```

**提案 C（讨论中，= B + 可选 IPC）**

同一个 `conf` 函数，透明地支持两种传输：

```text
进程内直连 ──┐
             ├─→ 同一套 core（WAL + 前缀锁 + 词表）
IPC 到守护进程 ┘
```

守护进程不是另一套实现，只是「一个长命的 embedded 客户端」。

### 支持单函数形态的理由（按重要性排序）

1. **参数是纯数据 → 整个 API 天然可序列化。** 这一条是决定性的：
   可序列化 ⇒ 可以走 IPC / 消息队列 / 跨语言；⇒ 可以录下来重放；
   ⇒ 可以写成数据放进文件（配置操作脚本）；⇒ **审计日志 = 调用日志**，
   「生成了哪些配置」这个需求变成白送的，不需要单独设计事件模型。
2. **只有一个拦截点。** 日志、审计、mock、性能统计、限流、dry-run，全部一处生效。
3. 学习成本最低：只需要记住「一个东西」。

### 需要接受的代价（不是没有）

- **参数在运行时校验**，除非用 `@overload` + `Literal["get"]` 补类型。可以补，但要写。
- **返回类型随 op 变化**，静态检查靠 overload 逐个标注，mypy 能过，但要维护。
- **op 集合必须封闭且克制**：建议钉死 8 个以内
  （`get / set / declare / unset / vocab / flush / report / snapshot`）。
  超过 10 个就该回头审视，否则单函数会退化成 god function。

### 一个重要的简化：把「去抖」从时间维度移到调用维度

原方案里 `flush` 由定时器触发（隐式、不可预测、退出要 drain、测试难写）。
但既然 API 支持批量参数，`conf("set", items={...})` **一次调用本身就是一批**：

- 调用方决定批次边界 → 行为确定、可测试、可复现。
- 一次调用 = 一个 WAL 段 = 一次可能的主文件合并。
- 定时去抖退化为可选优化，只在守护进程里做，不在库里做。

### 吞吐量参考（本地回环 ~20–50 µs/RPC）

| 方式 | 10 万次 set |
|---|---|
| 逐条 `conf("set", ...)` 走 IPC | 约 2–5 s |
| `conf("set", items=[1万条])` × 10 次走 IPC | 几十 ms |
| 进程内直连 + 批量 | 十几 ms |

结论：**单函数形态 + 批量参数，恰好就是「攒一批写一批」最干净的实现方式。**

## 11. 本轮拍板（含实测校准）

> 本节结论取代 §9 的第 1 条。

### 11.1 API 面收敛为 2 个

| # | 名称 | 职责 |
|---|---|---|
| 1 | `AutoConf`（库自身） | 配置这个库自己：配置目录、模式、审计开关、并发策略 |
| 2 | `conf(op, key, value=..., type=..., doc=...)` | 所有配置操作，无之一 |

这正好补上了我上一轮指出的「单函数形态没有引导入口」的漏洞：

```python
from onconf import AutoConf, conf

AutoConf(home="./conf", audit=True)   # ① 只管库自己；可省略，走约定
conf("app.port", 9090)                # ② 干活
```

四个核心参数：

| 参数 | 作用 | 备注 |
|---|---|---|
| `key` | 配置键 | 点分路径 |
| `value` | 配置值 | |
| `type` | 类型，用于校验 | 可由 `value` 的运行时类型**魔法推断** |
| `doc` | 说明这个配置干什么用的 | 有硬问题，见 §11.4 |

### 11.2 并发模型：短命事务进程

临时进程的生命周期 = 一次事务：
起 → 拿锁 → 读主文件 + 回放 WAL → 合并 → 原子替换 → 读回校验 → 退出。
**不缓存任何配置数据**；配置的内存副本归主进程。

这消掉了我上一轮反对守护进程的全部理由：无常驻、无生命周期管理、无自举成本。

但价值定位要精确：**它不解决「并发写」——那是文件锁的事**（OS 在进程退出时自动释放锁）。
它真正买到的是**跨语言可调用**：任何语言只要能起子进程 + 读写 stdio，就能用这个引擎，
不需要在该语言里重新实现文件锁与合并逻辑。这也符合「它是库，不是项目专属」的定位。

### 11.3 实测数据（本机 Windows / Python 3.14.8 / .venv）

| 操作 | 实测 | 备注 |
|---|---|---|
| 冷启动一个 Python 进程 | **~65 ms** | 只 import 本库 |
| 同上 + `import yaml` | **~125 ms** | |
| 同上 + `import rich.console` | **~222 ms** | rich 是 bare 的 3.4 倍 |
| WAL 追加一条 | **1.8 µs** | |
| `os.replace` 全量原子替换 | **533 µs** | 比 WAL 慢 **301 倍** |

推论（10 万次 set）：

| 策略 | 总耗时 |
|---|---|
| 每次 set 起一个临时进程 | **约 2 小时** ❌ |
| 每次 set 全量原子替换主文件 | 约 53 秒 ❌ |
| 每次 set 追加 WAL | **0.18 秒** ✅ |
| 按批起进程（1 万条/批） | 秒级 ✅ |

**结论：临时进程只能按「批」起，绝不能按「次」起。**
「攒一批写一批」和「短命事务进程」是同一件事的两面，不是两个独立优化。

附带约束：`report()` 必须惰性 `import rich`，否则每次 import 本库都白付 220 ms。

### 11.4 新发现的硬问题：`doc` 存哪？

`doc` 一旦要持久化，就会撞上格式能力差异：

| 后端 | 支持注释 | 回写时能否保住 |
|---|---|---|
| YAML | ✅ | ❌ **PyYAML `dump` 会丢掉全部注释**，要保住得换 `ruamel.yaml` |
| JSON | ❌ 不支持注释 | — |
| `.env` | ✅ | 取决于自研解析器 |

更严重的是：引擎会周期性回写主文件，
**全量重 dump 会摧毁用户手写的注释、格式、键顺序与锚点**。
对一个「本地文件配置引擎」来说这几乎是致命的——用户用它的前提就是想手改这些文件。

两个必须定的问题：

1. `doc` 是否进配置文件？倾向**不进**：放 sidecar schema，或只活在内存与报告里。
2. 回写是「全量重 dump」还是「外科手术式改写（只动变更的键，其余字节保留）」？倾向**外科手术式**。

## 12. 事实结构、主/子进程模型与词表

### 12.1 事实结构 = 词表，且它不属于代码

「事实结构不是代码的事实结构」——这句话的落点是：
**词表是一个独立于任何一份代码而存在的持久化资产。**

- 代码只产生「登记请求」，不产生「事实」。
- 词表才是「有哪些配置项、什么类型、什么意思、有没有默认值」的唯一权威。
- 因此词表可以脱离代码传播（本地文件 / 网络下发），这也是它能做网络绑定机制的前提。

### 12.2 主进程 / 子进程模型

```text
主进程（常驻，持有内存视图）
  │  ① 整理：收集所有声明、解析默认值、算出词表 diff
  │  ② 启动 conf 子进程，把要写的东西交给它
  ▼
conf 子进程（短命，唯一写者）
     拿锁 → 读当前事实 → 应用变更 → 原子替换 → 读回校验 → 退出
     不缓存任何配置数据
```

**必须修正的一处**：不能把「主进程整理出的全量」当作子进程的写入内容——
**全量传递 + 全量覆盖 = 必然丢更新**：

```text
主进程 A 整理出 {a: 1}
主进程 B 整理出 {b: 2}          # B 没见过 A 的更新
子进程 A 写 → 文件 {a: 1}
子进程 B 写 → 文件 {b: 2}        # a 没了 ❌
```

子进程拿到一份全量 map 时，**无法区分「这是本次要写的」和「这是继承来的」**，所以它没有能力正确合并。

结论——两条路必须分开：

| 传递内容 | 用途 | 形态 |
|---|---|---|
| **变更集**（keys + values + 操作） | 写入 | 增量，必须 |
| **词表 / 全量快照** | 注册、对账、同步 | 全量，可以 |

### 12.3 实测：全量传递到底贵不贵

| 操作（10 万条配置项，3.2 MiB JSON） | 实测 |
|---|---|
| `json.dumps` | 13.2 ms |
| `json.loads` | 28.7 ms |
| 起子进程 + 全量传输 + 子进程解析 | **88.2 ms** |
| 起子进程 + 子进程自己读全量文件 | **90.1 ms** |

**我原本猜「全量传递是 O(N)、会很贵」，实测证明我猜错了**：传输全量和让子进程自己读文件
几乎同价（88 vs 90 ms），因为成本被 65 ms 的进程启动吃掉了大半，3.2 MiB 的管道传输只要 23 ms。

但要注意：**便宜 ≠ 可以拿来当覆盖写**。全量便宜只说明「词表全量同步」这条线可以做得简单粗暴；
值的写入仍然必须是增量，理由见 §12.2。

### 12.4 词表格式：建议直接对齐 JSON Schema

不要发明格式。JSON Schema 的三个关键字正好就是需求里的三个概念：

| 需求 | JSON Schema 关键字 |
|---|---|
| 类型校验 | `type` |
| 说明文档 `doc` | `description` |
| 默认值 | `default` |

收益：现成的 IDE 补全与校验、现成工具链、YAML/JSON/.env 都能映射到同一套描述。
`doc` 也就自然有了归宿——**进词表，不进配置文件**（与 §11.4 的结论一致）。

### 12.5 网络绑定词表：**推迟到 V2**

「词表可以在网络上传播」把难度从「本地文件」抬到了「分布式一致性」：权威冲突、版本与顺序、
安全（能改词表 = 能改程序行为）、分区、幂等。

**决定：V1 只做本地词表**（最好做、收益最大、风险最低）。网络词表留到 V2，且届时建议只做**单向**
（本地只读订阅 / 单向汇报），不做双向同步——双向的复杂度高一个数量级。

## 13. 时间轴与事务模型（本地）

### 13.1 核心机制：借用 Python 的导入期执行

`conf(...)` 是**函数调用**，写在模块顶层就**必然在导入时执行**。
不需要注册表、不需要装饰器、不需要扫描代码——Python 的导入机制免费提供了「把所有声明跑一遍」。

这就是为什么 API 必须是函数形态，而不是类 / 装饰器 / 配置对象。

### 13.2 时间轴

```text
t0  Python 主进程启动
    │
t1  import 用户模块（导入图展开）
    │   conf("app.port", 8080)        ┐
    │   conf("app.host", "0.0.0.0")   ├ 顶层调用连续发生 → 进同一个待提交缓冲
    │   conf("db.url", doc="...")     ┘
    │
t2  ★ 事务边界 1 —— 第一次「需要真值」的时刻（或显式 commit / atexit）
    │   ├─ 起 conf 子进程（实测 65~90 ms，只此一次）
    │   ├─ 主进程传：变更集（增量）
    │   ├─ 子进程 ① 核对变更：与本批词表 diff 对账，没变的跳过
    │   ├─ 子进程 ② 统一读取：把本批涉及的键一次性读回
    │   ├─ 子进程 ③ 汇报结果：返回 {键: 值}
    │   └─ 主进程装入内存视图 → 此后 get 全部命中内存（微秒级）
    │
t3  业务运行 ……（get 走内存，不再起进程）
    │
t4  某个类初始化 / 函数被调用时才出现的 conf(...)
    │   → 这是**第二个独立事务**（晚于 t2 的边界）→ 再起一次子进程
    │
t5  进程退出 → atexit 提交最后一个事务
```

### 13.3 事务边界（关键定义，已按时间窗口修正）

> **一个进程内，从上次提交到此刻累积的所有 `conf` 调用 = 一个事务。**
> 边界由一个收集窗口决定。

**窗口 = 固定窗口（tumbling），不是滑动去抖：**

- 第一个 `conf` 调用**开启窗口并开始计时**。
- 窗口内继续有调用 → 继续收集。
- 窗口到期 T（默认 150~200 ms）→ **提交这一批**，无论后面还有没有。
- 到期后新来的调用 → 开新窗口、新事务。

为什么用固定窗口而不是滑动去抖：滑动去抖在持续负载下会**永远不提交**
（每次都因为「还有新事件」而顺延），固定窗口保证提交延迟上界 = T。

**被迫提交**（不等窗口到期）：

1. 任何「需要真值」的读操作——读必须同步返回，不能等
2. 显式 `conf("commit")`
3. 进程退出（`atexit`）

**窗口自适应**：`T = max(200 ms, 上次事务耗时 × 2)`。
固定 200 ms 在忙时会退化成背靠背起进程（一次事务本身就要 65~90 ms）。

**实现上优先「无线程」**：不启后台线程，而在每次 `conf` 调用与每次读操作时
检查「距窗口开始是否已超过 T」。零线程、零竞态、行为确定。
代价：进程若在最后一次声明后不再调用 `conf`，最后一批要等 `atexit` 才落盘。
需要及时可见性时再开定时器线程（可选）。

（本条也取代了我此前提出的「`conf("set", items={...})` 显式批量参数」方案——
按调用簇自动分组更自然。）

### 13.4 子进程只做三件事

| # | 动作 | 说明 |
|---|---|---|
| ① | 核对变更 | 与本批声明的词表做 diff（含默认值变更）；**无变更则不写** |
| ② | 统一读取 | 一次把本批涉及的键读回（全量读；实测 10 万条 ≈ 88 ms） |
| ③ | 汇报结果 | 返回 `{键: 值}`，主进程装入内存视图 |

**写增量、读全量** —— 与 §12.2 的结论一致。

### 13.5 「无变更不写」是必需的，不是优化

顶层的 `conf(...)` 每次启动都会重跑一遍。如果没有 diff 对账，
每次启动都会重写配置文件 → mtime 天天变 → 用户的 `git diff` 天天脏。

### 13.6 约束：声明集中在导入期，读取只在导入期之后

「启动那一刻把所有配置扫完」是一个**近似**。真正的边界是「第一次需要值」。
一旦导入期出现 `get`，事务就会被提前切开。

| 写法 | 结果 |
|---|---|
| 顶层写声明，业务逻辑里 get | ✅ 一个事务，最优 |
| 顶层写声明 + 顶层 get | ⚠️ 事务在此切开 |
| 类 / 函数初始化时才声明 | ⚠️ 独立事务，各付一次 65~90 ms |
| 循环里声明 | ❌ 灾难，需要护栏 |

### 13.7 其他必须钉死的边界

- **崩溃**：`atexit` 不执行 ⇒ 未提交的声明丢失。丢的是「注册」而非用户数据，可接受但要写明。
- **multiprocessing**：子进程会重新 import，顶层 `conf(...)` 会再跑一遍 ⇒ 必须只让主进程提交。
- **提交失败**（子进程崩、锁拿不到、文件损坏）：建议**抛异常**，不静默降级。
  魔法不能在关键处静默失败。
- **跨进程陈旧**：主进程的内存视图在下一次事务之前，感知不到别的进程的更新。需要定 TTL 或显式 refresh。

### 13.8 审计报告从「附加功能」升级为「必需」

事务边界是隐式的、取决于调用位置。用户必须能看到：
**本次运行发生了几个事务、每个事务包含哪些声明、边界为什么切在那里。**

没有这个，`conf` 写错位置造成的性能问题几乎无法排查。
审计在这里不是锦上添花，它是这个设计的**配套设施**。

## 14. 命名与 Python 版本

### 14.1 命名：`auto-conf` 有实测可见的撞名风险

PyPI 查询结果（HEAD 请求实测）：

| 名字 | 状态 |
|---|---|
| `auto-conf` | **可用** |
| `autoconf` | **已被占用，且是同领域 Python 配置库** |

PyPI 上的 `autoconf` 是 PyAutoConf——「layered configuration system」，
用法 `from autoconf.conf import Config`，读目录下的 YAML。**同名、同语言、同领域。**

再加上 GNU Autoconf（C 构建工具、`configure` 脚本）这个更老的既成事实，
「auto conf」这个名字在搜索、`pip install`、问题定位上都会被污染。

**结论：import 名 `onconf` 可以留，但发布名要另选；或者整体改名。**

其余候选可用性（实测）：`confhub` **可用**；
`confetti / confit / confab / conflux / pyconf / konf / confkit / konfig / confer / onconfig` **均已被占用**。

### 14.2 Python 3.14 实测（本机 3.14.8 / MSC v.1944 / 64bit）

| 项 | 值 |
|---|---|
| GIL | **启用**（`Py_GIL_DISABLED = 0`）⇒ **不是 free-threaded 构建** |
| `annotationlib` | 存在（PEP 749 惰性注解） |
| `tomllib` | 标准库可用 ⇒ 免费拿到 TOML 读取 |

启动成本（热缓存，7 次平均）：

| 变体 | 平均 | 最低 |
|---|---|---|
| `-c pass` | 39.7 ms | 36.5 ms |
| `-E -s` | 38.3 ms | 36.1 ms |
| `-S`（不加载 site） | **27.5 ms** | 26.6 ms |

`-S` 省 12 ms，但会丢掉 site-packages ⇒ 子进程无法 `import yaml`。
**不建议**，除非用显式 `sys.path` 注入，得不偿失。

### 14.3 真正对口的 3.14 特性

| 特性 | 对本项目 |
|---|---|
| **PEP 649/749 惰性注解求值（3.14 默认）** | ✅ **直接利好**。我们选定的「单函数 + 大量 `@overload` + `Literal["get"]`」形态，在 ≤3.13 里注解于定义时求值（成本 + 前向引用麻烦），3.14 改为惰性。 |
| **`typing.ReadOnly`（3.13）** | ✅ 词表的 TypedDict 描述可用。 |
| **`tomllib`（3.11 标准库）** | ✅ 免费支持 TOML 读取，不加依赖。建议直接纳入后端列表。 |
| **PEP 734 多解释器（3.14 进标准库）** | ⚠️ 帮助有限。核心瓶颈是**跨进程串行写文件**，同进程内的并行解决不了。 |
| **PEP 779 自由线程** | ⚠️ 本机不是 free-threaded 构建；且本设计的并发点在 IPC + 文件锁，不在线程。 |

**诚实结论**：3.14 对本项目最大的红利是 **PEP 649/749**（正好落在我们选定的重载密集 API 形态上）
和 **`tomllib`**（白拿一个后端）。多解释器和自由线程我不想硬凑——它们解不了这个设计的主要矛盾。

## 15. 两个面之间的分工（由真实用法反推）

```python
conf("slot.max.byte.b", 512, doc="格长档位之一（字节）；两档相加即为格长，全不写则不成立")
conf("slot.max.byte.kb", 0, doc="格长档位之一（千字节，1024 进制）；两档相加即为格长")
conf("pack.max.byte", 2 * 1024**3, doc="封口线（字节）：单个载体写满这个数就换新的一份")
conf("hub.default", "main", doc="默认 hub 名：写入不点名时进这一个")
conf("index.max.byte", 64 * 1024**2, doc="一个索引块的体积上限（字节）")

a = int(conf("slot.max.byte.b"))
```

### 15.1 op 是推断出来的，不是参数

「核心参数就四个：键、值、文档、类型」——**op 不在其中**。样例证明推断可行：

| 调用形态 | 语义 |
|---|---|
| `conf(key)` | 读 |
| `conf(key, value)` | 写（声明 + 值） |
| `conf(key, value, doc=...)` | 声明（带文档） |
| `conf(key, doc=...)` | **仅登记**（无值 ⇒ 只更新词表） |

第四条正好对应「没有默认值的只更新词表」。

### 15.2 真实关系：`conf` 是 `AutoConf` 的匿名口子

```python
def conf(*args, **kwargs):
    return _engine(*args, **kwargs)      # _engine 是 AutoConf 的单例
```

- `AutoConf` 是一个**类型**（底层可能是单例），它定义**所有可调参数**，并带完整类型注解。
- `conf` 是它的**匿名透传口子**：`*args, **kwargs` 原样转发。
- 「口子给你留了」= `**kwargs` 是开放集合。**能改什么，取决于 `AutoConf` 这个类型里有什么。**
- 因为底层是单例，你可以在**任何模块、任何时刻**调 `conf(...)` 重新调整引擎——这正是 logging 的用法。

| | `conf(*args, **kwargs)` | `AutoConf` 类型 |
|---|---|---|
| 角色 | 匿名口子，日常入口 | 参数的定义者 |
| 参数 | 开放集合，透传 | 完整、有类型、有默认值 |
| 用途 | 读 / 写 / 登记 / 临时调整引擎 | 类型提示、参数清单、校验 |

**补救措施（不牺牲匿名性）**：不要让 `conf` 做包装函数，而是把它做成
**绑定到单例上的同一个可调用对象**（`conf = _engine.__call__`，或用 `ParamSpec` 转发）。
这样既保住开放参数，又能让 IDE 拿到完整签名。
—— 这一条是为修掉 §16.1 记录的那个问题。

### 15.3 「临时」不是彩蛋，是单例可变的必需品

底层是单例 + 任意位置可改 ⇒ **隐式全局可变状态**。logging 就是这么干的，代价众所周知
（互相覆盖、测试互相污染）。

所以「临时改配置 / 临时改引擎配置」必须有一个**作用域**定义，
否则 `conf(flush_window_ms=10)` 会影响整个进程，包括别人的库。

作用域的载体我仍猜是**前缀覆盖层**：一个用前缀做键空间的覆盖层，只在作用域内可见，
出作用域自动失效。杀手级收益是**测试隔离**：

```python
with AutoConf(home=tmp_path):
    conf("db.url", "sqlite:///:memory:")
```

不用改全局状态、不用改环境变量、不用重启。**待确认。**

### 15.4 四条必须钉死的规则

1. **未知 kwargs 立刻报错。** `**kwargs` 的默认行为是静默吞掉拼写错误：
   `conf("a.b", 1, tipe=int)` 会被当成某个引擎参数吃掉 ⇒ 用户以为声明了类型，其实没有。
   这是「魔法」最恶劣的失败模式：**静默失效**。
2. **参数清单必须从签名反射生成，不能手写。** `conf(help=True)` 直接
   `inspect.signature(AutoConf.__call__)` 输出。这样「越熟越能改」才有一个不脱节的入口。
3. **单例可改 ⇒ 必须有作用域**（见 §15.3）。
4. **引擎参数必须是可序列化的纯数据。** 它们要随事务传给子进程；
   传 `Path` / 回调 / 文件句柄会在 IPC 处炸掉。

### 15.5 连带结论：`AutoConf` 的注解 = 唯一事实来源

既然「只要保证这个类型里面有，想改的配置都能改」，那么这个**类型就是引擎的参数规格**。
于是下面三样东西应该全部从它派生，而不是各写一份：

| 产物 | 来源 |
|---|---|
| `conf(help=True)` 的参数清单 | `inspect.signature` |
| 参数默认值文档 | 注解 + 默认值 |
| 参数校验 | 类型注解 |

**注解即规格即文档即校验。** 而这正好是 3.14 惰性注解（PEP 649/749）的用武之地：
运行期反射注解的成本降下来了，`onconf` 可以放心把 `annotationlib` 用起来。

## 16. API 类型机制（已在本机实测通过）

### 16.1 具名参数与匿名参数共存，是 Python 的基本语法

```python
def f(named, opt=None, *, kw=None, **kwargs): ...
```

这不是「想想招」的事，Python 原生支持。真正的问题只有一个：
**让 `**kwargs` 那部分也有 IDE 提示。**

### 16.2 答案：`Unpack[TypedDict]`（PEP 692，3.12+；本机 3.14.8 实测通过）

```python
class EngineParams(TypedDict, total=False):
    home: str
    flush_window_ms: int
    audit: bool

@overload
def conf(key: str, /) -> Any: ...
@overload
def conf(key: str, value: Any, /, *,
         type: type | None = None,
         doc: str | None = None,
         **engine: Unpack[EngineParams]) -> None: ...
```

实测结果：

| 检查 | 结果 |
|---|---|
| 具名 + 匿名共存 | ✅ `(key, value, *, type, doc, **engine)` |
| 具名参数被识别 | ✅ `['key', 'value', 'type', 'doc']` |
| 匿名参数的注解 | ✅ `Unpack[EngineParams]` |
| `EngineParams` 键运行时可读 | ✅ `['home', 'flush_window_ms', 'audit']` |
| `annotationlib.get_annotations()` | ✅ 拿到真实类型（3.14 惰性注解可用） |
| 拼错参数 | ✅ `TypeError: 未知参数 ['tipe']；合法参数：[...]` |

### 16.3 一招解决四件事

1. 具名与匿名共存（§16.1）
2. **两部分都有 IDE 提示**——这是核心诉求
3. 未知参数**静态就被类型检查器拒绝**（`Unpack[TypedDict]` 是封闭的，不允许额外 key）
4. `EngineParams` 成为唯一事实来源 ⇒ 运行时校验 / `help` / 文档全部从它派生

第 3 条尤其重要：它把「静默失效」从运行期问题**提升为写代码时的红灯**。

### 16.4 一个必须知道的缺口：TypedDict 不携带默认值

TypedDict 只描述**名字与类型**，默认值得放在别处。所以需要一个运行期默认值表，
并**用测试断言两者键集合一致**：

```python
assert set(EngineParams.__annotations__) == set(ENGINE_DEFAULTS)
```

否则「唯一事实来源」会悄悄腐烂——这正是它最容易出问题的地方。

### 16.5 静态与运行时是两套，必须都写

`Unpack[TypedDict]` 是**纯静态**工具。运行时 `engine` 只是一个普通 `dict`，
所以运行时校验必须自己写，且**从同一个 TypedDict 生成**：

```python
unknown = set(engine) - set(EngineParams.__annotations__)
if unknown:
    raise TypeError(f"未知参数 {sorted(unknown)}；合法参数：{sorted(EngineParams.__annotations__)}")
```

**静态给 IDE，动态给用户，两者同源。**

## 17. 事实权威：文件绝对优先（核心语义）

### 17.1 原则

> **文件是绝对权威，代码不是。代码只负责被写入。**

- 代码里写的配置数据、默认值，**不构成读取的来源**。
- 事实权威 = **文件里有哪些配置项、值是多少**。
- **词表**是「有哪些键」的权威；**文件**是「值是多少」的权威。

### 17.2 六条派生规则（已修正）

| # | 规则 | 理由 |
|---|---|---|
| R1 | 代码里写的值不是「配置源」，它是一次**写请求**；事实存在文件里 | 权威 = **事实的存放地** |
| R2 | 写模式**可以创建或修改**配置项；「这次声明算不算变更」由**默认值指纹**判定（§17.8） | 防止每次启动冲掉用户手改的值 |
| R3 | **声明后立即读，也走文件**，不拿刚声明的默认值短路 | 「哪怕几纳秒，也当有超人改过它」 |
| R4 | 内存可缓存**从文件读回**的值，**绝不能缓存代码声明的值** | 缓存的是事实的副本 |
| R5 | **读强制提交事务** —— 读必须读文件，而待写的声明必须先落盘 | 固定窗口在「读」面前必须让路 |
| R6 | 读不到就是**报错**，永不返回「空」；`None` 是合法值，与「没有值」不同 | 见 §17.7 |

> **修正记录**：本节初稿曾写「R2：代码只能补缺，不能改写」——**这是错的**。
> 「改数值没有说不能改」，「写模式 = 声明创建新的配置项**或者修改配置项**」。
> 真正的约束不是"不能改"，而是"**怎么判断这次声明算不算一次变更**"，答案见 §17.8。

### 17.3 R6 的实现落点：`origin` 资格

§4 里的 `origin` 字段在这里获得明确定义：

- `origin="declared"` **永远不能作为 `get` 的返回值**。
- 声明的值只能先被**写进文件**，再以 `origin="file"` 的身份被读回来。

这是一条可以写成断言的规则，也是实现时最容易违反的一条。

### 17.4 R3 / R5 的代价

`conf("a.b", 512)` 紧跟 `conf("a.b")` ⇒ 中间必然发生**一次完整事务**
（起子进程 + 落盘 + 读回），实测 65~90 ms。

这是这套语义的固有成本，不是缺陷。它换来的是：
**「我读到的值，一定来自事实。」**

R3 的深层作用：它把「最近写入缓存」这个优化**从设计里彻底删除**。
一旦引入「我刚写的所以我记得」，就凭空多出一个隐式的、不可审计的配置来源。

### 17.5 两个面的最终定性

> 「我们也不是说不给动词 API，只是动词 API 被这个函数给包回去了。」

| 面 | 内容 | 角度 |
|---|---|---|
| `AutoConf` 类型 | **有很多动词 API**（东西确实多，没有动词不好搞） | 引擎 |
| `conf` 函数 | 只暴露 4 个参数（`key / value / type / doc`），调度 `AutoConf` | 数据 |

两个最重要的使用场景（配置角度、参数角度都不同）：

1. `from onconf import AutoConf` → 做**全局配置**
2. 全局配置完之后 `from onconf import conf` → **声明与获取配置项**

### 17.6 必须问清的场景：程序想持久化一个值怎么办

在 R2 + R4 下，`conf(key, value)` **改不了已存在的值**，临时覆盖又不落盘。
那么桌面应用保存用户偏好这类需求怎么走？

| 方案 | 说明 |
|---|---|
| (a) 不允许 | 配置只由人改，最纯，但砍掉一批场景 |
| **(b) 走 `AutoConf` 的动词 API** | 「`conf` 是温和面，动词才是强力面」——**倾向这个** |
| (c) 一个显式透传参数 | 简单，但在温和面上开了个洞 |

选 (b) 的话，「两个面**配置角度不一样、参数角度不一样**」这句话就完全落实了：
**数据面负责读与登记，强力面才动事实的边界。**

### 17.7 读 / 写由「参数结构」判定，不由 op 判定

**value 位被填了 ⇒ 写；空着 ⇒ 读。** 哪怕填的是 `None` / `""` / `0`，也算填了。

```python
_MISSING = object()          # 哨兵：唯一表示「没填」

def conf(key, value=_MISSING, *, type=None, doc=None, **engine):
    if value is _MISSING:
        ...   # 读模式
    else:
        ...   # 写模式：None / "" / 0 都是合法值
```

原文：「**哪怕你填个空，你都给我填着，不许空着。** 因为你一旦空着，我就认为你是要读取。」

- **`None` 是合法的配置值**，不等于「没填」⇒ 哨兵**不能**用 `None`。
- 词表因此必须区分三种状态：**未登记** / **已登记但无值** / **值为 `None`**。

**读模式的两个报错**（原话）：

> 「一读发现，要么这个配置项没有了，要么这个配置项没有值，我就报错」

| 情况 | 结果 |
|---|---|
| 键未登记 | **报错** |
| 键已登记但没有值（如 `conf(key, doc=...)` 只登记过） | **报错** |
| 键有值（含 `None`） | 返回值 |

推论：`conf(key, doc="...")` 这种「仅登记」的键，**读它就是报错**。这是设计使然，不是 bug。

### 17.8 「默认值」的真身：声明的指纹

这是本轮最关键的纠正。原文：

> 「发现这个配置项存在，默认值也存在，但同时发现默认值不一致，那么就会按照你代码的默认值去走。
> 它是不同场景不同决策的……**写的时候是一套权威，读的时候是一套权威。**」

我理解的机制（**需要确认**）：

**默认值不是「运行时兜底值」，它是「开发者意图的指纹」。**

```text
首次启动
  代码 conf("a.b", 512)     词表无记录 → 创建
                            文件 a.b = 512        词表 default = 512

之后每次启动
  代码 conf("a.b", 512)     与词表 default=512 一致 → 什么都不做 ✅
  用户手改文件 a.b = 1024   → 保持，不会被冲掉 ✅

开发者改代码
  代码 conf("a.b", 2048)    与词表 default=512 不一致 → 按代码的走 → 触发更新
```

这样三件事同时成立：

1. **每次启动重跑声明不会造成写放大**（一致 ⇒ 什么都不做）；
2. **用户手改的值不会被代码冲掉**；
3. **开发者改了默认值能被传播出去**。

这也正是子进程第一件事「核对变更（包括配置项的变更、**默认值的变更**）」的准确内容。

### 17.9 待确认：不一致时，更新的落点在哪

前提：词表记 `default = 512`，代码现在声明 `2048`，而文件里的值是 `1024`（用户改过）。

| 方案 | 结果 | 评价 |
|---|---|---|
| (i) 更新文件的值 | 文件变 `2048`，用户的修改被冲掉 | ❌ 违背 R1 |
| (ii) 只更新词表的 default | 文件保持 `1024`，词表记 `2048` | 保守，但用户永远升不上去 |
| **(iii) 三方合并** | 文件值 == 旧 default（用户没改过）⇒ 升到 `2048`；文件值 != 旧 default（用户改过）⇒ 保留用户值，只更新词表 | ✅ **推荐** |

(iii) 等于用**一次比较**就判定出「用户改过没有」，不需要额外状态字段。

> **已被否决**：用户采用「文件优先 + `force` 显式逃生口」，见 §18.1。

## 18. 写入对账与读取推断（算法级规格）

> 口径：**每一次校验都是全量校验**。存在的自然还存在着，不存在的自然被处理掉。

### 18.1 写入 = 三个集合的全量对账

- **期望集** = 代码本次声明的配置项
- **事实集** = 配置文件里实际存在的配置项
- **词表** = 持久化登记册（键、类型、文档、默认值、「空」标记）

| # | 情形 | 动作 |
|---|---|---|
| 1 | **清理未知数据**：事实有、期望没有 | **删除** |
| 2 | **补充缺失数据**：期望有、事实没有 | **补写**（叠加回去） |
| 3 | **补充缺失参数**：事实有该数据但缺元数据 | **补元数据**（进词表） |
| 4 | **保持原有数据**：两边都有，但**值不一致** | **尊重文件，不改**；除非 `force=True` |

注意 1 与 4 的对称性：

- **键的集合**以**代码/词表**为准 ⇒ 多出来的会被清掉；
- **值**以**文件**为准 ⇒ 不一致也不动。

这正是 §17.1 那句「词表是键的权威，文件是值的权威」的算法落地。

#### 情形 4 的细则

值不一致（文件值 ≠ 代码给的默认值）⇒ **以配置文件为最高优先，不修改**。
唯一例外：**`force=True`**（原话「强制刷新」）⇒ 以代码事实为最高优先，覆盖文件。

> **命名纠正**：原话里的 `Forth=true` 应该是 **`force`**。
> `Forth` 是一门编程语言的名字；「强制」的英文是 `force`。

#### 全新配置项（情形 2 的细则）

| 有默认值？ | 动作 |
|---|---|
| 有 | 写进**配置文件**（值 = 默认值），同时登记进词表 |
| 无 | **完全不碰配置文件**；只在**词表**里创建该项，默认值位置填「空」 |

**词表必须能区分「没有默认值」和「默认值是 `null`」**——两者语义完全不同：

| 词表里的表示 | 含义 | 读它 |
|---|---|---|
| `default` 键缺失 | 无值 / 仅登记 | **报错**（§17.7） |
| `"default": null` | 默认值就是 `None` | 返回 `None` |

对齐 JSON Schema 正好能表达这两种情况（缺省 vs 显式 `null`）。

### 18.2 读取 = 五步

```text
① 代码册说：去文件里读 key
② 在事实（配置文件）里找
   ├─ 找到 → 看有没有值
   │    ├─ 有值 → 文件写了什么就拿什么（老实拿）
   │    └─ 没有值 → 词表里有 ⇒ 「配置失误」报错
   └─ 没找到 → 不要像小孩子一样只找一点点，去词表里翻译一下
        ├─ 词表里也没有 → 报错「配置不存在」（事实不存在）
        └─ 词表里有     → 报错「配置不合理」（配置失误）
③ 类型推断（§18.3）
④ 与声明类型比对、必要时转换（§18.3）
⑤ 返回
```

**两类错误必须分开**，因为责任方不同：

| 错误 | 含义 | 谁的问题 |
|---|---|---|
| 配置不存在 | 词表里都没有，代码也没声明过 | 键名用错了 |
| 配置不合理 / 配置失误 | 词表里有，文件里没有 | 部署遗漏 |

### 18.3 类型推断 → 与声明比对 → 转换

**第一步：基础类型推断**（从文件里读出来的「草稿类型」）

| 现象 | 推断 |
|---|---|
| 绝大多数 | `str` |
| 数值形态 | `int` / `float` |
| 布尔形态 | `bool` |

**第二步：结构推断解析**

若出现 `{}` / `[]` / `()`，继续解析成 `dict` / `list` / `tuple`。
理由：**不同语言的结构表达不一致**，所以要按这套逻辑再推一层，才能拿到「真正的数值」。

**第三步：与代码声明的 `type` 比对**

```text
推断类型 == 声明类型  → 直接返回
推断类型 != 声明类型  → 尝试转换到声明类型
                        能转   → 返回转换结果
                        不能转 → 抛异常，提示类型不一致
```

这回答了 §15.4 的问题：**`type` 同时承担校验与转换**，
但顺序是「**先按内容推断，再向声明类型收敛**」，而不是「声明类型至上」。
所以 `int(conf("slot.max.byte.b"))` 里那个 `int()` 确实应该删掉。

### 18.4 两个必须确认的风险

#### 风险 A：清理未知数据在多进程下会误删（严重）

「期望集」如果取的是**本进程本次的代码声明**，那么：

```text
进程 A 声明 {a, b}
进程 B 声明 {b, c}
文件里现在有 {a, b, c}          # 两个进程都跑过

A 再启动 → 全量对账 → c 不在 A 的声明集里 → 清理掉 c ❌
B 再启动 → c 缺失 → 又补回来
→ 两个进程周期性互删，来回抖动
```

**解法（需要选）**：

| 方案 | 说明 |
|---|---|
| **(a) 清理基准改成「词表」而非本次声明** | 词表是持久共享的登记册；A 知道 c 登记过，就不会删 |
| (b) 清理**按前缀作用域**限定 | 本进程只清理自己命名空间内的未知键 |
| (c) 自动清理降级为**报告**，删除必须显式 | 最安全，但需人工介入 |

倾向 **(a)**：它和「词表是键的权威」是同一句话的两面——
既然键的权威是词表，那「多出来的键」就该拿词表比，而不是拿本次声明比。

**顺带**：如果早先说的「前缀控制」本来就是这个作用（给每个进程/模块划命名空间），
那 (b) 才是原意。**请明确。**

#### 风险 B：用户手加的键会被自动清掉

情形 1 是**破坏性**的：用户在配置文件里手加一个键（代码没声明过），下次启动就被删。
对「本地文件配置引擎」来说这是很强的行为。

如果这是要的，必须**明确写进 README**；如果不是，
那 (b) 前缀方案正好能给用户划一块「只属于人」的区域。

### 18.5 待确认

1. 情形 4（值不一致）时，**词表里记录的默认值要不要更新成代码的新值**？
2. `force` 是 `conf(key, value, force=True)` 的**数据面参数**，还是 `EngineParams` 里的引擎参数？
   倾向数据面——它描述的是「这一次写入的意图」。
3. 风险 A 选哪个方案？
4. 两类错误（配置不存在 / 配置不合理）要不要用**两个不同的异常类**？建议要。

## 19. 多进程模型：单读写者（评估）

### 19.1 提出的模型

```text
A B C D E F G 启动
   ↓ 临时通信对话 / 「探嗅进程」做成员发现
   ↓ 选出「权威对象」（例如 A）
A 作为读写进程，向其余进程广播 IPC 端点（方向 + 路径）
   ↓
其余进程把变更发给 A，由 A 统一收口
   ↓
A：定时组建事务 → 向权威进程汇报 → 写入 → 冲突则汇报
```

本质：**永远只有一个读写者，所有并发从这个口子收回来。**

### 19.2 这是成熟模式，但有四处可以砍掉

| # | 问题 | 建议 |
|---|---|---|
| 1 | **成员计数（"知道有多少个大爹"）不必要** | 配置写入不需要「等所有人到齐」。砍掉计数 ⇒ 连带砍掉整个动态成员发现难题 |
| 2 | **独立的「探嗅进程」本身是新的单点** | 不必有独立进程：**谁先原子创建锁/端点，谁就是 writer**（`O_CREAT｜O_EXCL`、Windows 命名互斥体） |
| 3 | **单点故障**：A 崩了，全体写入瘫痪 | 锁由 OS 在进程退出时自动释放 ⇒ **下一个进程重新抢**。不需要心跳也能自愈 |
| 4 | **「权威进程的冲突裁决」职责多余** | 单写者 + 到达顺序 = 全局顺序 = **LWW，没有需要裁决的冲突** |

第 4 条尤其重要：**单写者的全部意义就是消除冲突。**
如果还需要一个仲裁者，说明写入并没有真正串行。

### 19.3 但它意外买到了一样东西：全局声明集

这是它比「解决并发写」更值钱的地方，也是 §18.4 结论的**修正**。

| 模型 | 库能否看见全局声明集 | 风险 A |
|---|---|---|
| 各进程直连写文件 | ❌ 看不见别的进程声明了什么 | 无职责（§18.4） |
| **单写者收口** | ✅ writer 汇聚所有进程的声明 | **有职责，而且有能力履行** |

所以在单写者模型下，「清理未知数据」的基准可以取**所有进程声明的并集**，
我上一轮构造的误删场景**从根上消失**。

**这才是单写者模型的真正价值：它不是为了并发，是为了「全局事实」。**

### 19.4 与早先「短命事务进程」模型的冲突（必须二选一）

| | 短命事务进程 | 选举出的单写者 |
|---|---|---|
| 谁写 | 每次事务起一个子进程 | 常驻的一个业务进程（A） |
| 并发控制 | OS 文件锁串行 | 消息队列收口 |
| 单点 | **无** | **有**（A 崩了要重选） |
| 发现机制 | 不需要 | 需要（端点广播 / 约定路径） |
| 事务启动成本 | 每次 65~90 ms | 一次选举，之后只发消息 |
| **全局声明集** | ❌ | ✅ |
| 跨进程批量落盘 | ❌ | ✅（窗口搬到 writer 里） |

两者不兼容，要选一个。

### 19.5 建议路线：先 WAL，后收口

有一条中间路线能拿到「**全局顺序 + 全局声明集**」，却**不需要选举**：

```text
每个进程 → 短临界区加锁 → append 到同一个 x.wal（实测 1.8 µs/条）
落盘      → 谁拿到锁谁合并（或短命事务进程合并）
读取      → 主文件 + 回放 WAL
```

- **全局顺序** = WAL 的追加顺序，天然给出，不需要仲裁者；
- **全局声明集** = WAL 里所有进程声明过的键的并集，风险 A 同样可解；
- **无单点、无选举、无发现、无心跳**。

代价：跨进程批量落盘不如 writer 模型紧凑。

建议里程碑：

| 阶段 | 内容 |
|---|---|
| M1 | 纯内存核心：对账四条 + 读取五步 + 类型推断转换 + 哨兵判定 |
| M2 | 单进程 + 词表（JSON Schema + 哈希短路）+ 四个后端 |
| M3 | WAL + 短临界区锁 ⇒ 多进程正确性到手 |
| M4 | 视实测决定是否升级为「选举单写者」（仅在跨进程批处理成为瓶颈时才值得） |

### 19.6 待确认

1. **「探嗅进程」和「读写进程」是同一个还是两个？**
   若是两个，那么读写进程向权威进程「汇报」的意义需要说明——单写者下没有可裁决的冲突。
2. **读是否也要走 writer？建议不要。**
   但读需要一个**落盘屏障**：读之前要确认「我自己的待写已经落盘」（R3）。
   所以依赖的是 flush 屏障，不是读本身。否则 writer 一挂，全体连读都读不了。







## 20. 日志与审计（体验层）

### 20.1 强制日志：可改去向，不可关闭

- 用户可决定日志**去终端还是去文件**；
- **不可以关闭**。理由：关掉它不是「少看几行」，是**缺失配置审计**。

但「关不掉」必须精确到**存在性**，不能连「每行都写」一起锁死，否则热路径会炸
（循环里 `conf("x")` 一万次 = 一万行日志）。

| 操作 | 策略 |
|---|---|
| **写**（`[Write]` / `[Change]`） | **全量，永不聚合** —— 它是事实 |
| **读**（`[Read]`） | **同事务内同键去重聚合**（`n=1000`）—— 它可重复、无副作用 |
| **进程结构**（`[Start]` / `[Link]` / `[Send]`） | **一次一条、立即输出** —— 它描述「此刻进程在干什么」，攒着就没意义了 |

### 20.2 字段评估：原设计缺四样

原格式：

```text
[R]-[xx-xx-xx-xx] : item : file : data : ipc-id
```

**格式问题**：`:` 做分隔符会被值里的冒号撕裂——
`db.url = sqlite:///data/app.db` 会让这一行从中间断掉。
建议改 `key=value` 空格分隔（自描述、可扩展、不怕值里有分隔符）。

**缺的字段**：

| # | 缺什么 | 为什么必须 |
|---|---|---|
| 1 | **`old → new`** | `[Change]` 只记「内容被改了」，没记改前是什么。审计 90% 的价值在「从什么变成什么」 |
| 2 | **`origin`**（file / vocab / env） | 要能回答「这个值是哪来的」 |
| 3 | **`op`**（fill / overwrite / clean / register / **skip**） | 尤其 **`skip`**：值不一致但尊重文件、**想改没改**。不记这个，用户会以为声明没生效 |
| 4 | **结果 / 错误** | 键不存在、类型转不过去、锁拿不到 —— 失败必须留痕，否则审计只记录成功的历史 |

### 20.3 「到底是谁改的」——能记，答案不是 pid

| 身份 | 怎么拿 | 成本 |
|---|---|---|
| **调用点** `app/config.py:12` | 写时抓一帧 `sys._getframe(1)` | ~1 µs，**最有用** |
| **事务 / 进程** | `txn` + `pid` | 近零 |
| **应用 / 主机** | 用户经 `EngineParams` 声明（`identity="order-svc@host-3"`） | 零，可选 |

**「谁改的」在配置语境下的正确答案是「哪段代码」和「哪个部署」，不是 pid。**
用 `co_filename` + `f_lineno` 即可，**不要用 `inspect.stack()`**（很贵）。
对这套设计格外划算：声明写在文件头 ⇒ 调用点就是「声明的第几行」。

### 20.4 审计文件

1. **append-only**，不要重写 —— 天然是历史，且崩溃安全；再加**轮转**（按大小/日期）。
2. **「首次为空」值得再想**：首次运行正是「这个系统第一次建立事实」的时刻，
   恰恰最该留痕。若要区分创建与修改，可以再加一个标签（当初提的是 `[M]`=修改）——
   **实现期没加**：`[Change]` 的 `old=-` 已经说明了「之前没有」，多一个标签多一处不一致的机会。

### 20.5 级别名：用**完整的词**（原设计是单字母，实现期改了）

`[Read] [Write] [Change] [Error]` 四个配置事实级别，加 `[Start] [Link] [Send]` 三个
进程结构级别 —— 首字母大写、完整的英文词：视觉锚点、等宽列对齐、`grep '^\[Write\]'` 精确，
与 syslog / nginx / k8s 的级别字段惯例一致。

本节原本定的是单字母 `[R] [W] [C] [E]`。改的原因是**一眼看得懂**比少敲几个字母重要：
日志是给人读的第一手材料，`[Write]` 不需要查对照表，`[W]` 需要。

### 20.6 最终格式

```text
[Start]-[05:12:34.500]-[txn=0 pid=4821] item=- file=app.yaml id=order-svc
[Link]-[05:12:34.501]-[txn=0 pid=4821] item=- file=app.yaml id=order-svc op=bind
[Send]-[05:12:34.502]-[txn=0 pid=4821] item=slot.max.byte.b file=app.yaml id=order-svc op=read
[Read]-[05:12:34.567]-[txn=7 pid=4821] item=slot.max.byte.b file=app.yaml origin=file data=512 n=1
[Write]-[05:12:34.568]-[txn=7 pid=4821] item=pack.max.byte  file=app.yaml op=fill data=2147483648
[Change]-[05:12:34.568]-[txn=7 pid=4821] item=pack.max.byte  file=app.yaml old=- new=2147483648 at=app/config.py:12
[Error]-[05:12:34.570]-[txn=7 pid=4821] item=db.port       file=app.yaml err=type-conflict want=int got=str
```

- **时间**：终端用 `HH:MM:SS.mmm`；**审计文件带完整日期**（审计要跨天查）。
- **`ipc-id`** 拆成 `txn`（事务号，用来把多行归并成一个事务）+ `pid`。
  只能留一个就留 `txn` —— 审计是按事务读的，不是按进程读的。
  **`txn=0` 表示「不属于任何配置事务」**：`[Start]` / `[Link]` / `[Send]` 这类进程结构
  记录用 0，因为客户端与写者各数各的 txn，混进同一个文件会出现两个同号的批次。

## 21. 日志对齐（体验层）

### 21.1 那个算法叫弹性制表位（elastic tabstops）

核心思想：**列宽由该列最宽的单元格决定**，而不是固定制表位。

但日志和编辑器最大的区别在于：

> **弹性制表位要求「先知道这一列最宽的是谁」，
> 而流式日志逐行产生——输出第一行时，还不知道第三行会不会更长。**

### 21.2 我们有一个别人没有的东西：批次

日志**天生按事务批量产生**（§13.3）。所以：

```text
事务结束 → 这一批日志行已在内存 → 算完列宽 → 一次性输出
```

**批次内完美对齐，且免费**——因为批次本来就存在。
跨批次的列宽跳动，用「列宽只增不减」的滑动最大值抑制。

### 21.3 必须用显示宽度，不能用 `len()`（实测）

| 行 | 竖线显示列位 |
|---|---|
| ① 用 `len()` 补空格 | `[77, 77, 79, 77, **84**]` ← 中文那行偏了 **6 列** |
| ② 用显示宽度补空格 | `[78, 78, 78, 78, 78]` ✅ |

原因：`len("配置")` 是 2，**显示宽度是 4**（全角）。20 行 stdlib 就能算对：

```python
def cell_len(s: str) -> int:
    total = 0
    for ch in s:
        if unicodedata.combining(ch):
            continue
        total += 2 if unicodedata.east_asian_width(ch) in ("W", "F") else 1
    return total
```

附带坑：**ANSI 颜色码是零宽**，`\x1b[31m` 会被 `len()` 算进去 ⇒ 一上色又歪。
所以算宽度必须在**剥掉 ANSI 之后**做。

### 21.4 不要为此引入 rich

`rich.cells.cell_len()` 现成可用，但**不要用**：日志是**强制路径**，
而 `import rich` 实测 **222 ms**（空解释器的 5.6 倍）。
为对齐让所有程序启动多付 222 ms 不值。

**结论**：对齐用 20 行 stdlib；rich 只留给 `report()`（可选、惰性导入）。

### 21.5 三条落地约束

1. **截断只能发生在终端渲染层，绝不能落到文件**（文件那份必须无损）。
2. **超宽策略**：只对「长文本列」截断并加 `…`；键名、文件名、时间**不截断**。
3. **对齐是给人看的**：文件里保持 `key=value` 紧凑形态，终端才对齐。同源、渲染不同。

## 22. IPC 选型：TCP loopback + HTTP

### 22.1 实测（本机 Windows / httpx 0.28.1 / 300~500 次）

| 方式 | 延迟 |
|---|---|
| 进程内直接调用 | **0.09 µs** |
| 裸 TCP loopback 往返 | **38 µs** |
| 手写 HTTP/1.1 over socket | **112 µs** |
| stdlib `http.client`（keep-alive） | **226 µs** |
| **httpx `trust_env=False`** | **543 µs** |
| httpx 默认（`trust_env=True`） | **28,619 µs** ← **53 倍** |

结论：loopback HTTP 约 **0.5 ms**，相对 65~90 ms 的事务成本可以忽略 ⇒ 选型成立。

### 22.2 硬性约束：`trust_env=False`，否则配置流量会进代理

第一次测出 25 ms/次，排查结果是 **httpx 默认 `trust_env=True`**，
在 Windows 上通过 `urllib.request.getproxies()` **读注册表里的系统代理**：

```text
env : {}                                              ← 环境变量是空的
reg : {'http': 'http://127.0.0.1:7897', ...}          ← 注册表里有
```

也就是说：**本机的配置写入 IPC 会被送到 127.0.0.1:7897 这个代理软件。**

这不只是性能问题，是**安全问题**——一个第三方进程能看到你所有的配置读写。

**结论：`httpx.Client(trust_env=False)` 是硬性要求，不是优化。**
同理，endpoint 必须显式，不依赖任何环境推断。

### 22.3 地址抽象（唯一该为分布式做的事）

```python
AutoConf(endpoint="tcp://127.0.0.1:0")     # 本机，端口自动分配
AutoConf(endpoint="tcp://10.0.0.5:7701")   # 将来
```

本机与远程**同一条代码路径**，将来要改的只有配置值。
**不要现在引入任何分布式机制**（选举、心跳、幂等键、逻辑时钟）。

### 22.4 为什么「好上分布式」不是选 TCP 的理由

协议层确实好改：API 是纯数据、消息式、无状态，天生就是协议形状。
但语义层不好改——三条基石全部建立在「单机」之上：

| 基石 | 分布式下会怎样 |
|---|---|
| **文件是绝对权威** | 文件在哪？在本机 ⇒ 别人读不到，读也得走网络；在共享存储 ⇒ 回到分布式文件锁噩梦；做副本 ⇒ 「哪个副本权威」是一致性问题 |
| **单写者** | 从「进程单点」升级为「集群 SPOF」。本机靠 **OS 释放锁**自愈，跨机器没有它——无法区分「死了」和「慢了」，这是 CAP 的入口，做对要引进 quorum + 选举 |
| **读强制提交** | 本机 65~90 ms；跨网络是往返 + 可能的一致性等待，而「声明后立即读」在导入期很常见 |
| **声明集哈希** | 跨机器哈希不一致不再意味着「代码改了」，而是「版本不一致」——那是发布问题 |

选 TCP 的正当理由是**现在就能兑现**的三条：Windows 上 TCP 最省事、
endpoint 天然是 `host:port`（本机 / 远程同构）、
HTTP 让 `curl` 调试与**跨语言**免费——而跨语言是核心卖点。

## 23. 分布式：结论是「不做」，而且理由是本质性的

### 23.1 「分布式 + 单权威 = 中心化」这个判断是对的

本设计的根基是**单一事实源**（文件绝对权威 + 单写者收口）。
把它「分布」出去，得到的不是分布式系统，而是**一个搬远了的中心**——
这不是去中心化，是远程集中化。

> **把 single-source-of-truth 系统「上分布式」，
> 是在概念层面走错了方向，不是实现层面没做好。**

### 23.2 正确形态是「同步配置型」：靠确定性，不靠协调

提出的替代方案：**每台机器上的配置一模一样**（词表、默认值一致），
其余值各自为政。这在分布式里有个准确的名字：**无协调复制（coordination-free replication）**。

它成立，恰好因为本设计早已定下的那条：

> **代码只提供期望 ⇒ 词表 = f(代码) ⇒ 每台机器都能独立重算出同一份词表。**

**一致性不是靠协调达成的，是靠确定性达成的。**
所以「词表分发」这件事根本没有存在必要——本地现场生成即可。

### 23.3 由此，V2「网络词表」降级为「网络哈希对账」

原话：「机器启动时真正的作用，其实就是远程拉个词表下来……
甚至说，远程词表可能都不需要。」

同意，而且可以更进一步：**真要跨机核对，只传哈希就够了。**
§18.7 的声明集哈希（16 字节）现成可用。

| | 网络词表（原 V2） | 网络哈希对账 |
|---|---|---|
| 传什么 | 整份 schema | **16 字节** |
| 能改行为吗 | **能** ⇒ 攻击面 | **不能** |
| 冲突模型 | 版本 / 合并 | 只有「一致 / 不一致」 |
| 价值 | 下发 | **观测** |

**价值从「下发」变成「核对」**，复杂度从「分布式一致性」降到「贴一个字符串」。
**建议 V2 改成这个，甚至可以先只做日志里打一行哈希。**

### 23.4 分布式对这东西没有价值（更根本的理由）

原话：「你把它丢到分布式上面去，最直接的结果就是没用。」

同意，而且理由比「启动时用一下」更硬：

- **读是一次性的**（启动期）；**写是稀疏的**（无变更不写，§13.5）；
- 分布式系统的存在理由是**并发压力 / 数据量 / 地理分布**——这三个它一个都不占；
- 所以这不是「暂时不做」，而是**这件东西本质上不需要分布式**。

### 23.5 边界声明：跨机一致性是发布系统的活

配置引擎应当**假设同一份代码已在所有机器上**。
把配置与代码推到所有机器，是 CI/CD、容器镜像、Ansible 这类工具的职责。

**引擎不管分发，它只管「本机事实」。** 边界清楚，且不与现有工具链打架。

### 23.6 那为什么还选网络 IPC

不是因为分布式，而是因为**它是最简单的 IPC**（§22.4）：
Windows 上最省事、endpoint 天然 `host:port`、`curl` 可调试、跨语言免费。

## 24. 启动成本预算：该压的是导入和进程，不是 IPC

### 24.1 实测（本机，9 次平均）

| # | 项 | 成本 | 能否砍 |
|---|---|---|---|
| 1 | 解释器启动 | 41 ms | ❌ 换语言才行 |
| 2 | **`import rich`** | **+180 ms** | ✅ 惰性（已定 §21.4） |
| 3 | **`import httpx`** | **+101 ms** | ✅ **必须惰性**（§24.3） |
| 4 | `import http.client`（stdlib） | +29 ms | ✅ 用不到就别导 |
| 5 | 我们自己的核心 | +30 ms（其中 `dataclasses` 约 +15） | ⚠️ 可优化 |
| 6 | `import yaml` | +18 ms | ✅ 按后端惰性 |
| 7 | **起一个事务子进程** | **+65 ms / 次** | ✅ 按批起 / 单写者 |
| 8 | `import socket` | +1.8 ms | 已近零 |
| 9 | **一次 IPC 往返** | **+0.5 ms** | ❌ **全表最小** |

### 24.2 一条尖锐的算术

> 一次 IPC 往返 **0.5 ms**，而 `import httpx` 要 **101 ms**。
> **导入 httpx = 200 次 IPC 往返。**
> 而一个程序一辈子通常只做 1~3 次事务。

也就是说：**为了省 IPC 的钱而导入 httpx，花的钱是 IPC 本身花费的 30~100 倍。**

### 24.3 三条新增约束

1. **`httpx` 必须惰性导入。** 默认 `import onconf` 不许碰它，
   否则每个用户白付 101 ms。
2. **IPC 不是默认路径**，分三层：

   | 场景 | 用什么 | IPC 成本 |
   |---|---|---|
   | 单进程（绝大多数） | 进程内直连 | **0** |
   | 多进程 | 文件锁 + WAL | **0** |
   | 实测证明跨进程批处理是瓶颈 | 单写者 + IPC | 0.5 ms / 事务 |

3. **endpoint 显式**（§22.2），不依赖环境推断。

### 24.4 反直觉结论：单写者模型里 IPC 是收益，不是拖累

在单写者模型下，IPC **替代了「每次事务起一个子进程」的 65 ms**：

```text
短命事务进程：65 ms / 事务
单写者 + IPC：0.5 ms / 事务      ← 快 120 倍
```

所以：**IPC 的成本只有在和「进程启动」相比时才有意义，而它永远赢。**
真正该问的问题不是「IPC 慢不慢」，而是「**我需要起多少次进程**」。

### 24.5 保留网络的理由（不变）

不换命名管道 / AF_UNIX：**它们买不到全表最小那一行的 0.5 ms，
却要付跨平台代价**（Windows 命名管道要 pywin32、AF_UNIX 支持受限），
还要放弃 `curl` 调试与跨语言。

### 24.6 已知可优化项（先不做）

`dataclasses` 占我们自己核心导入成本的约 15 ms。
若要把启动压到极致，把 `Decl` / `VocabEntry` / `Action` 换成 `__slots__` 手写类即可。
**暂不做**——可读性优先，等有实测需求再说。

## 25. IPC 选型修正：把「传输 / 协议 / 客户端库」拆开

### 25.1 三个概念被混在一起了

| 层 | 例子 | 导入 | 往返 |
|---|---|---|---|
| **传输** | TCP loopback（stdlib `socket`） | **+6 ms** | **30 µs** |
| **传输** | Windows 命名管道（`multiprocessing.connection`） | +19 ms | **35 µs** |
| 协议 + 客户端库 | HTTP + `httpx` | **+105 ms** | **543 µs** |
| 协议 + 客户端库 | HTTP（stdlib `http.client`） | +32 ms | 226 µs |

**101 ms 是 httpx，不是网络。30 µs 才是 TCP 本身。**
「换掉 httpx」和「换掉网络」是两件完全不同的事，收益差两个数量级。

### 25.2 实测：命名管道并不比 TCP 快（Windows / 300 次）

```text
TCP loopback 裸 socket        30.31 us/次
multiprocessing.connection    34.68 us/次   (Windows 走命名管道)
命名管道 / 裸 TCP  = 1.14 x
```

**在噪声范围内。传输层换不来任何东西。**

### 25.3 各选项矩阵

| 方案 | 跨平台 | 跨语言 | 额外依赖 | 导入 | 认证 |
|---|---|---|---|---|---|
| TCP loopback（`socket`） | ✅ | ✅ | 无（stdlib） | +6 ms | ❌ 自己加 |
| **`multiprocessing.connection`** | ✅ 自动选平台原生 | ❌ pickle | 无（stdlib） | **+19 ms** | ✅ `authkey` |
| Windows 命名管道（`pywin32`） | ❌ 绑死 Windows | ✅ | **C 扩展** | — | ✅ |
| AF_UNIX | ❌ Windows 受限 | ✅ | 无 | — | ❌ |
| HTTP + `httpx` | ✅ | ✅ | httpx | **+105 ms** | ❌ 自己加 |

### 25.4 结论：传输不换，分场景选

| 场景 | 用什么 | IPC 成本 |
|---|---|---|
| 单进程（绝大多数） | 进程内直连 | **0** |
| 多进程 | 文件锁 + WAL | **0** |
| Python 进程间升级 | **`multiprocessing.connection`** | +19 ms / 35 µs |
| 跨语言 | HTTP + httpx（惰性） | +105 ms / 543 µs |

**跨语言是使用 HTTP 的唯二理由**（另一个是 `curl` 调试），而它不是默认需求。

### 25.5 回答「Windows 原生 IPC 很多」

Windows 确实有命名管道 / mailslot / 共享内存，但：

- **mailslot** 是单向广播，不是请求-响应；
- **共享内存** 要自己配同步原语；
- **命名管道** 在 Python 里要 `pywin32`（C 扩展）。

**而 `multiprocessing.connection` 已经把这些包好了**：
Windows 上走命名管道，POSIX 上自动换成 AF_UNIX，**同一份代码，不需要 pywin32**。
这正好回答「不可能绑死在 Windows 上」——它不绑 Windows，也不绑 POSIX。

### 25.6 安全：pickle 必须配 `authkey`

`multiprocessing.connection` 用 pickle，**未通过 `authkey` 认证的连接不能发 pickle**。
所以 `authkey` 必须随机生成，并放在只有本机可读的位置（endpoint 文件 0600）。

这比裸 TCP 端口**更安全**——裸端口是本机任何进程都能连。

### 25.7 最重要的一条：现在什么都不选

默认路径（WAL + 文件锁）**根本不需要 IPC**。
所以 M1~M3 不引入任何 IPC 实现，只留一个 **seam**：

```python
AutoConf(endpoint="auto")        # 默认：进程内直连 + WAL，无 IPC
AutoConf(endpoint="pipe://...")  # 升级：multiprocessing.connection
AutoConf(endpoint="tcp://...")   # 跨语言：HTTP + 惰性 httpx
```

等 M4 实测**证明**跨进程批处理真的是瓶颈，再按 §25.4 选。**大概率永远不需要。**

## 26. 命名空间冲突：为什么「零全局状态」才是目标

### 26.1 论点比原话更强

原话是「万一其他项目也用 loopback，可能回环冲突」。更准确的表述是：

> **TCP 端口是唯一一个「命名空间天生全局、无法按项目隔离」的选项。**

| 命名空间 | 冲突可能 | 能否按项目隔离 |
|---|---|---|
| **TCP 端口** | 端口号是**机器全局**的 | ❌ 只能靠「随机端口 + 发现机制」绕 |
| Windows 命名管道 | 全局命名空间，但**名字任意** | ✅ 用配置目录 hash 命名 |
| AF_UNIX 路径 | 就是文件系统路径 | ✅ 直接放在配置目录里 |
| **文件锁 / WAL** | **就是文件本身** | ✅ 天然隔离，零全局状态 |

所以 TCP 的代价不是「可能冲突」，而是：
**它逼你引入一个全局命名空间，而你本来可以完全没有全局状态。**

### 26.2 `endpoint="auto"` 的准确语义

**一个配置目录 = 一个独立的 IPC 世界。**

```text
<conf-dir>/
  app.yaml
  app.yaml.wal
  app.yaml.lock
  onconf.endpoint          # endpoint 名 + 随机 authkey，0600
```

1. **默认**：文件锁 + WAL —— 零 IPC、零命名空间；
2. **需要升级**：endpoint 名 = `hash(配置目录绝对路径)`，
   Windows 走命名管道、POSIX 走该目录下的 AF_UNIX —— **命名空间按项目隔离**；
3. **跨语言**：才显式指定 `tcp://`，并接受端口这个全局命名空间。

**用户什么都不用配**：没有端口、没有 host、没有防火墙规则、没有 authkey 分发。

### 26.3 「库不该开 socket」是个身份问题

这一条比技术性能更重要：

- 会在 `netstat` 里暴露，被运维 / 安全软件盯上；
- 企业环境可能限制 loopback 监听；
- 沙箱 / 杀软可能直接拦；
- 用户会问「**为什么一个配置库在监听端口？**」

**库静默开网络端口是 surprise behavior。默认路径必须不开。**

## 27. YAML 的词表：不需要第二套格式

### 27.1 结论

**YAML 没有自己的词表标准**——YAML 规范里没有 schema 语言，`yaml-schema` 之类的只是社区项目。

**但它也不需要**，因为：

> schema 工具作用于**解析后的数据模型**，不是文本。
> YAML 1.2 是 JSON 的**超集**，两者共享同一套数据模型（str / number / bool / null / array / object）。

所以：**词表永远只输出一份 JSON Schema，不搞第二种格式。**

### 27.2 差别只在「怎么指向词表」

| | 指向方式 | 进入数据模型吗 |
|---|---|---|
| JSON | 一个**数据成员**：`"$schema": "schema/settings.json"` | ✅ 会 |
| YAML | 一条**注释**：`# yaml-language-server: $schema=./settings.schema.json` | ❌ 不会 |
| YAML | 编辑器侧映射（VS Code 的 `yaml.schemas`） | ❌ 不会 |

（VS Code / YAML Language Server 支持上面那条 modeline 注释。）

### 27.3 这两个差别各有一个后果

1. **JSON 的 `$schema` 会被对账扫到** ⇒ 必须豁免（§18.1 已修）。
2. **YAML 的 schema 指针活在注释里** ⇒ 外科手术式回写一旦冲掉注释，
   **等于冲掉用户的 schema 绑定与 IDE 补全**。

第 2 条把「保住注释」从**礼仪**升级为**功能正确性**：
对 YAML 后端来说，丢注释不是「不够优雅」，是**破坏用户工具链**。

### 27.4 YAML 里 JSON 没有的东西（外科手术必须原样保留）

| 特性 | `safe_load` + `dump` 会怎样 |
|---|---|
| **注释** | **全丢** |
| **锚点 / 别名**（`&a` / `*a`） | 展开成重复内容，体积膨胀 |
| **多文档**（`---`） | 只读得到第一份，写回时拍平 |
| **标签**（`!!str` 等） | 丢失 |
| 键序 | `sort_keys` 默认乱序（要显式关掉） |

**结论**：YAML 后端**只能**走外科手术式回写，没有「全量重 dump」这个选项。
这也是 M2 里唯一一个「做错了用户会真的生气」的地方。

### 27.5 待定：多文档 YAML 支不支持

我们现有模型是「一份值文件 = 一个顶层对象」，多文档（`---` 分隔）与它冲突。
**建议 v1 不支持**，遇到就明确报错，不要静默只读第一份。

## 28. 键永远扁平，值随便嵌套（已定）

### 28.1 约定

> **key 是扁平的，任何后端都不给嵌套。value 随你怎么嵌，引擎不管。**

两边的理由不一样：

| | 结论 | 理由 |
|---|---|---|
| **key** | **永远扁平**（点分字面量） | 一旦嵌得离谱，**对解析能力有影响**——「这个键的值占哪几个字节」变得不确定，外科手术式回写就不可靠了 |
| **value** | **任意嵌套** | 值是数据，不是地址。引擎只负责原样搬运 |

### 28.2 值的嵌套在**代码层面**就解决了

引擎不需要理解「路径」。要往值里面钻，Python 本身就是那个工具：

```python
conf("storage.pack")          # 拿到值（可能就是一份容器）
conf("storage.pack")["max"]   # 往下钻 —— 这是 Python 的活，不是引擎的活
```

**所以引擎永远不需要处理「路径进入值内部」这件事。** 这一刀砍掉了一整类复杂度。

### 28.3 用值当键（间接寻址）：**支持** —— 我上一版判错了，这里更正

原话：

> 「它相当于我的第一个配置项，内容其实代表了第二个配置项；那么第二个配置项可以当第三个配置项，
> 这本身我一点限制都没有。这其实是个**纯文字组织的问题**，你凭什么限制掉？」

对。我上一版把两件不同的事混成了一件：

| | 是什么 | 对静态扫描的影响 |
|---|---|---|
| **值引用值** | `conf("alias", "real.key")` —— 值的内容恰好是个键名 | 键仍是字面量，**完全不受影响** |
| **键用表达式算** | `conf(conf("a"))` —— 实参是运行期算出来的 | 扫描器看不见那一层 |

而**引擎两边都不需要限制**：键是什么就查什么，**零改动**。

```python
conf("alias.pack", "core.storage.pack.max.byte")   # 值就是一个键名
conf(conf("alias.pack"))                            # ⇒ 等于 conf("core.storage.pack.max.byte")
```

**代价只有一个，而且必须明示**：门禁第 1 条（键必须是 `ast.Constant[str]`）
**看不见 `conf(conf(…))` 里的那一层**。所以：

* 想要静态可查，就让**第一实参保持字面量**——`conf(conf("alias.pack"))` 至少看得见 `alias.pack` 这层；
* 真要动态拼键，**可以**，但那个键放弃了「一处声明」「键名拼错有人管」这些保障。

> **这是使用者的选择，不是引擎的禁令。**
> 引擎不设限；门禁的能力边界如实写进 README 即可。

（实现上顺带加了一条好转的错误：键不是字符串时明确报
`键必须是字符串，拿到 int（512）。如果是 conf(conf(…)) 这种间接寻址，说明内层取到的值不是键名。`
——比让它掉进「配置不存在」里强得多。）

### 28.4 对后端的影响

| 后端 | 天然形态 | 是否冲突 |
|---|---|---|
| JSON | 顶层扁平对象（`Cairn/config/settings.json` 就是这样） | ✅ 天然一致 |
| YAML | 顶层不缩进的扁平映射 | ✅ 已按此实现（§27、`_yaml_backend`） |
| `.env` / 环境变量 | 扁平 | ✅ 天然一致 |
| **TOML** | 表头 `[section]` 会产出嵌套 | ⚠️ 用 **dotted key**（`a.b.c = 1`）或把表头**归一成点分键** |

TOML 那条要在做该后端时定：表头 `[storage]` + `pack = 1` 归一成键 `storage.pack`，
本身仍是扁平点分键空间，只是**物理形态上多了一层表头**，回写时要落在那一段里。

### 28.5 一个诚实的限制（值太复杂时）

外科手术式回写对**跨多行的容器值**做不到精确定位：

- **YAML**：`render()` 遇到跨行的值**直接报错**（§27.4），不做猜测；
- **JSON**：容器值渲染成**紧凑单行**，替换整个值区间。如果原文件里那个值是 prettified
  的多行写法，替换后会被压成一行——**变动仍在「我们被要求改的那个值」的区间内**，
  但格式会变。

这不是缺陷，是我们把边界划在「值的字节区间」上换来的确定性。

### 28.6 `$schema` 指针：**每次落盘都保证有**

原话：

> 「这个词表指针该有的得有啊……你在 VSCode 上写配置，如果没有写词表指针，
> 你都不知道词表搁哪儿，除非自己去翻。」

所以口径从「只在新建文件时写」改成「**每次落盘都保证有**」：

| 情况 | 行为 |
|---|---|
| 新建文件 | `$schema` 是**第一条**（随后追加的配置键排在它后面） |
| 已存在的文件缺它 | **补上**（追加到末尾，功能等价） |
| 已经有了 | **一个字节都不动**（幂等） |

两个说明：

1. 它是**指令**不是配置键，不参与对账（§18.1）——这正是「指令键豁免」那条规则存在的理由。
2. 在**这一个点**上，「不改用户没让我们动的行」让位于「让用户的编辑器能工作」。
   取舍很清楚：多一行指令 vs 用户面对几十项配置只能靠翻文件。

指针是个**相对路径**（`schema/settings.json`），编辑器以值文件所在目录为基准解析。

## 29. 引擎装配收口 —— 两个实现期才暴露的发现

### 29.1 规则 1（清理未知数据）需要「期望集完整」这个前提

这是语义级的，不是性能级的。判据是「事实里有、**期望集**里没有」，
可引擎一次 `conf()` 调用只知道**到目前为止**声明过的键：

```python
conf("a.b", 1)      # 此刻期望集只有 {a.b}
conf("c.d", 2)      # 此刻期望集只有 {a.b, c.d}
```

第一次调用若就按规则 1 对账，文件里**还没声明到**的键会被当成「未知数据」全清掉。
实测现象：刚写进去的 `c.d` 被下一次声明删了。

**修法**：`reconcile(clean_unknown=...)`

| 场景 | `clean_unknown` | 原因 |
|---|---|---|
| 增量声明（每次 `conf(k, v)`） | **False** | 期望集不完整 |
| 提交点（`sync()` / 进程退出） | **True** | 期望集完整 |

**这不是性能优化，是正确性前提。** 它也修正了我们对 §13.3 的理解——
之前以为「事务边界」主要是为了攒批省 IO，其实它**先是**为了让规则 1 有资格执行。

### 29.2 `conf(key, doc=…)` 算读还是登记 —— 我们自己文档里两处决定打架

- §17.7 原话：「value 位空着 ⇒ 读」；
- §15.1 却列了一行「`conf(k, doc=…)` ⇒ 仅登记」。

测试把冲突逼出来了。**钉死的口径**：判据不是「value 位空没空」，
而是**这一行到底在不在声明**：

| 调用 | 语义 |
|---|---|
| `conf(key)` | 读 |
| `conf(key, value)` | 声明 + 写 |
| `conf(key, value, doc=…)` | 声明 + 写 + 登记说明 |
| `conf(key, doc=…)` | **登记（必填键）+ 立刻取值** ⇒ 没配就报错 |

最后一行的用途是「**启动即校验必填项**」：键进词表，事实里没值就当场失败。
这也和 Cairn 侧那份约定的「登记 + 取值（必填键），缺值语义：报错」对上了。

### 29.3 v1 的提交点：增量 + `sync()`，不是固定窗口

- `conf(k, v)` 当场把**这一个键**补写 / 覆盖（`clean_unknown=False`），
  并返回当前生效值 ⇒ 紧跟其后的 `conf(k)` 从文件读回来，天然满足 R3；
- `sync()` / 进程退出（`atexit`）是**完整提交点**，规则 1 在这里跑；
- **写放大**：稳态下 `reconcile` 产出空动作（词表已记着同样的类型 / 文档 / 默认值）
  ⇒ 一个字节都不写。声明集哈希（§18.7）是更进一步的整体短路，**尚未接线**——
  目前靠词表 diff 达到了同样效果。

固定窗口（§13.3）留给 M3 的多进程场景，接的是同一个 `Engine`，接口不变。

## 30. 攒批窗口的默认值：**反过来**（实现后修正）

原设计（§13.3）把固定窗口当默认行为。实现完之后**默认值被反过来了**：

> **默认当场落盘（`flush_window = 0`），攒批窗口按需开。**

### 30.1 为什么

「文件是绝对权威」这条一旦成立，**写入的可见性延迟就是对它的削弱**：
别的进程去读那个文件时，看不到你刚声明的东西 —— 而多进程正是目标场景之一。

而且实现期撞上一件很直白的事：窗口默认开启会**当场打破一条安全不变量测试**
（它声明完立刻检查配置目录里有哪些文件，而那些文件还没被写出来）。

### 30.2 它并不解决原本以为要解决的问题

原以为攒批是为了防写放大。但**词表 diff 已经把它挡住了**：稳态下对账产出空动作，
一个字节都不写（§29.3）。所以「每次声明都写」不等于写放大。

真正需要攒批的是**启动期一口气声明很多键**这种突发场景，而那正是调用方
自己知道的事：

```python
AutoConf(home="…", flush_window=0.2)   # 攒一批再写
```

### 30.3 窗口开启后的语义

落盘发生在四个提交点：**窗口到期 / 一次读 / `sync()` / 进程退出**。
前三个**不做规则 1**，只有 `sync()` 与进程退出做（§29.1）。

## 31. 并发：OS 锁 + 锁内**按需**重读

### 31.1 锁必须是**操作系统**的锁

进程崩溃时操作系统自动释放它 —— 「死锁文件」这个经典难题直接消失，
不需要心跳、不需要超时判定、不需要「谁的 PID 还活着」的探测。

自制的 `O_CREAT|O_EXCL` 锁文件做不到这一点。那是在重新发明一个更差的轮子。

### 31.2 提交 = 锁内重读 + 读改写 + 原子替换

少了「锁内重读」就会出现：A 和 B 各自基于同一份旧内容写回，后写的把先写的整段盖掉。

### 31.3 指纹必须同时看**两个文件**

指纹（mtime + size）要看值文件**和**词表。只看值文件会漏掉「只登记不给值」这类
提交 —— 它不碰值文件，却会改词表。漏掉之后本地词表比磁盘旧，写回去就会把
别人刚登记的键**挤掉**。

### 31.4 实测

四个真进程各写各的键，一个都不丢
（`tests/test_engine.py::TestRealProcesses`）。

## 32. 专职写者：抢绑端点即选举（已交付）

§19.2 一直把「一个专职写者收口」列为目标，§25.7 却按当时的判断把它推迟了，理由是
「大概率永远不需要」。**那个判断是错的**，而且错的不只是「多一层机械」那一层 —— 见 32.4。

### 32.1 选主不是加锁，是**抢绑端点**

实测（`multiprocessing.connection`，Windows 命名管道）：

```text
① 第一个 Listener 绑上        : ok
② 第二个 Listener 绑同一地址  : 被拒（PermissionError）
```

抢绑本身就是一次**原子操作** —— 操作系统保证同一个地址只有一个能绑上。所以「谁是
写者」不需要锁文件，只需要一个**命名空间**：协调借的是命名空间的原子性，硬锁借的是
临界区的排他性。前者不需要心跳、不需要判活、不会留下死锁文件。

端点名由**配置目录的绝对路径**派生。Windows 上要先 `normcase`：`D:\a` 与 `d:\a` 是
同一个目录但字符串不同，不折叠大小写就会**两个写者写同一个目录**。

### 32.2 认证搬到应用层，因为 `authkey=` 的等待**没有上界**

`multiprocessing` 的 `authkey` 在 `Client(...)` 的**构造函数里**完成挑战应答，而这一步
**没有超时**：端点上只要「有人听、没人答」，`conf()` 就永远不返回。抓到的栈是：

```text
_recv_bytes → answer_challenge → Client → connect() → Channel.__init__()
```

改成连上之后自己发 `("hello", 认证码)`、**带超时地**等 `"welcome"`。认证强度不变，
等待从此有界。

顺带钉死这把钥匙的定位：**它不是密码学边界**。真正的边界是配置目录的文件系统 ACL
—— 能读 `settings.key` 的进程本来就能读 `settings.json`。它防的是**串台**，
不是**攻击**。

### 32.3 实现期撞上的四个坑

1. `Client(...)` 在构造函数里就完成握手 ⇒ 「先 Client 再 accept」是**死等**。
2. **`Listener.close()` 关不掉正在 `accept()` 的那个 handle。** `PipeListener.accept()`
   是「先造一个备用实例、再去阻塞等待」的：

   ```text
   self._handle_queue.append(self._new_handle())   # 先补一个新实例
   handle = self._handle_queue.pop(0)              # 取走最早那个去阻塞等待
   ```

   `close()` 清的是队列里那个**新的**。后果是端点名不消失 ⇒ 下一个进程永远抢绑不到
   （写者真空）。所以 `close()` 的顺序只能是「举旗 → 关会话连接 → 开空连接叫醒 →
   join → **最后才** close」。修之前那个测试文件跑 **82.94 秒**（孤儿实例触发
   `PIPE_BUSY` 的 20 秒重试），修完 **0.40 秒**。
3. **一条连接不能串行服务。** 第一版 `_serve` 是 accept 完就蹲在 `_handle` 里 `recv`，
   于是客户端 A 的整条会话把端口堵死：客户端 B **连得上，却没人跟它握手**，它只会
   得出「没有写者」的结论。单客户端时完全看不出来。现在 accept 只负责接，接到就交给
   一个会话线程。
4. `authkey_for` 先 `O_CREAT|O_EXCL` 再 `write`，留下一个**空文件**窗口：并发的读者
   读到空字符串，两把钥匙分叉。改用 `os.link` —— 目标已存在就失败，而内容早已写好。

### 32.4 一条必须**收回**的论证：全局声明集只在写者活着时成立

§19.3 写的是「专职写者让规则 1（清理未知数据）拿到完整基准」。**这条要加前提。**

照这个论点写的守护测试，第一次就失败了，而且失败得很难看：

```text
{'$schema': …, 'key.of.sync2': …}      ← 三个键只剩最后一个
```

原因：每个子进程自己当写者、写完就退出；下一个写者接手时**声明集是空的**，它的规则 1
把前任的键当成「未知数据」删掉了。

**所以：声明集不是持久状态。** 写者一换人，并集就跟着没了。进程起一个退一个的用法，
跨进程的规则 1 **仍然不安全** —— 这跟有没有专职写者无关。

| 写者的寿命 | 规则 1 的基准 |
|---|---|
| 长命（先起一个守着的写者，短命客户端轮流 `sync`） | **所有进程**的声明并集 ⇒ 安全（有守护测试） |
| 短命（每进程自己当写者） | 退化成「我这一个进程声明了什么」 ⇒ 不安全 |

剩下的是**设计问题**：要不要让声明集跨写者交接持久化？**倾向是不**，而是把规则 1
明确限定在「单写者且长命」的前提下 —— 多进程 + 短命进程下，**没有任何一个进程**知道
完整期望集。这不是实现问题，是信息不可得。

### 32.5 攒批窗口留在**客户端**，不搬到写者身上

两个位置语义不同，只有一个是对的。窗口搬到写者的话，客户端显式配的 `flush_window`
会被**静默忽略**（同一 home 上两个不同窗口的引擎共用一份配置，测试立刻会炸）。

留在客户端还有第二个好处：突发期省下的是 **IPC 往返**，不只是磁盘写 —— 一批声明
只发一次。

### 32.6 一个引擎一条通道，不是「一个配置目录一条」

同一进程里两个引擎指着同一个配置目录完全正常。按目录共用一条通道的话，第二个引擎会被
塞进第一个引擎的通道，它的声明就落到**另一个引擎**的声明集上了。

### 32.7 顺手定掉：WAL 不做

原本给 WAL 留的位置是「不丢更新 + 持久」。现在这四件事各有来源：

| WAL 要买的 | 现在的来源 |
|---|---|
| 合并突发写 | 攒批窗口（客户端侧，§30） |
| 持久 | 声明可从**代码**重新推导；词表每次整体重写 |
| 串行 | 专职写者（唯一收口点） |
| 顺序 | 读改写 + 原子替换 |

结论：**不做**。

### 32.8 已交付：§20 / §21 的日志与审计

`_audit.py` 把这两节落了地，实现时定下的几处口径（与本节正文的差别、以及实现期才暴露的
边界，都在这里）：

* **记录写在执行点**：谁真正动了配置目录，谁写日志与审计文件。经 IPC 的请求由写者执行、
  由写者记，但记录里的 `pid` / `id=` / `at=` 仍是**发起方**的（调用点在客户端抓，
  随声明过线）。`pid` 与 `id=` 都按**线程**存：写者的应答线程各自服务不同客户端，
  共用一个字段会让主线程自己的声明被记成远端调用方。
* **级别名落地成完整的词**（§20.5 改的那一条）：配置事实四个
  `[Read]` / `[Write]` / `[Change]` / `[Error]`，进程结构三个
  `[Start]`（引擎起来了）/ `[Link]`（`op=bind` 成了写者 / `op=connect` 连上写者 /
  `op=fallback` 端点不通、就地执行）/ `[Send]`（一次请求真的过了 IPC；`op=read` /
  `op=commit`，commit 的 `data=` 是本批声明数）。三个进程结构级别**一次一条、立即输出**，
  且带 `txn=0` —— 它们不属于任何配置事务（客户端与写者各数各的 txn，混在一起会撞号）。
  这也是「日志即调用日志」那句话最直观的兑现：一个多进程跑起来，日志自己就把
  启动 → 连接 → 发送 → 配置事实这条链讲清楚了。
* **客户端补的是「执行点这一次真正输出出去的」记录**：成功的那批（写 / 变更 /
  被这次提交收口的读）会回传，客户端补到自己的日志去向，**审计文件不重复写**。
  由此有两条要记住：远端失败时执行点虽然记了账，但客户端那一侧本来是空的 ——
  所以**发起方自己也会记一条 `[Error]`**；而纯远端的读会攒在写者的事务里等它的下一个提交点，
  因此**不一定**出现在客户端的日志里（权威流是审计文件）。
* **事务 = 提交窗口**：`flush_window=0`（默认）时每次 `conf(key, value)` 落盘就是一个事务；
  窗口开启时一个窗口是一个事务。**读的记录不立即输出**，攒在事务里等下一个提交点
  （写提交 / `flush()` / `sync()` / 退出）—— 这正是 §21.2 说的「批次本来就存在」，
  代价是纯读的程序要到退出才看见日志行。
* **写全量的 `op` 集合**：§20.2 的 fill / overwrite / clean / register / skip，加上
  `update_meta`（只改词表：类型、说明、默认值指纹）与 `noop`（本批声明已经满足，
  文件不用动 —— 回答 §13.8 那句「本次运行声明了哪些键」）。`skip` 照 §20.2 记 `old` / `new`。
* **只有 `[Change]`，没有 `[M]`**：§20.4 提过再加一个「修改」标签区分创建与修改，
  实现只发 `[Change]`，创建与否看 `old=-` 就够（多一个标签多一处不一致的机会）。
* **去向只有一个开关**：`log="stderr"`（默认）/ `"stdout"` / 文件路径；**不可关闭**。
  `audit=True` 再加一份 `<home>/audit.log`（`O_APPEND`、`0600`、超过 1 MiB 按时间戳轮转）。
  两路输出**互不牵连**：审计文件写失败要抛（日志那一份照写），日志去向坏掉也不毁审计那一批。
* **两种渲染同源**：终端用显示宽度做弹性制表位并截断长文本列，文件保持 `key=value`
  紧凑形态且**永不截断**（§21.5 约束）。键名 / 身份 / 调用点里的 CR / LF 会被折成可见转义：
  否则一个换行就能伪造出额外的审计行。
* §6 的「JSONL 事件流 + rich 报告」**没有**按原样做：事件流就是上面这套文本行（JSONL 与
  人读两份格式会让「哪份是准的」变成问题），`report()` 仍属未实现。

**已知边界**（实现期暴露，不再往回改，但要看清楚）：

* **审计文件假定「一个执行点」**：同一配置目录上第二个引擎也开 `audit=True` 时，它会把
  **自己本地的**记录（例如它自己的类型冲突 `[Error]`）追加进同一个 `audit.log`，而 `txn` 是
  按进程编号的 —— 文件里因此可能出现两个同号的批次，轮转也不再是单写者。
  要严格「一个写者」就别在客户端进程开 `audit`（默认关）。
* **写不出就没了**：`close_txn` 先清缓冲再输出，审计文件写失败**没有重试**，那一批只剩
  终端那一份。
* **写者进程内自己的调用没有和应答线程共用同一把锁**：`Engine.read` / `_commit_local`
  在 `_is_writer()` 时直接就地干，而远端会话走 `Owner.submit`（持 `Owner._lock`）。
  文件一致性由 OS 锁兜着（同进程两个 fd 的 `msvcrt.locking` 也会互相冲突，所以其中一边
  可能等满 `lock_timeout` 后抛 `LockTimeoutError`），但引擎内存态在那个窗口里是可竞争的。
  这一条**没有回归测试守护**，见威胁模型 T4 的残余风险。

### 32.9 POSIX 长路径：端点搬到短名字的临时目录

`AF_UNIX` 的 `sun_path` 只有 **104 字节**（含结尾 NUL）。端点名原本就是
`<home>/schema/settings.sock`，路径一深（macOS 的 pytest `tmp_path` 正是
`/private/var/folders/…`）`ipc.Listener` 直接抛错；而 `_attach` 是**尽力而为**的，
于是专职写者**静默失效** —— 所有请求退到就地执行，界面上只多几条 `[Link] op=fallback`。
照出来的症状在 macOS CI：8 条 owner 测试失败，覆盖率掉到 89%（`_owner.py` 只到 50%）。

处理：自然路径超过上限（留余量后取 **100 字节**，见 `SOCKET_PATH_LIMIT`）时，端点改成
`<tmpdir>/onconf-<uid>/onconf-<sha256(home)[:24]>.sock`。**仍然只由配置目录决定**
（哈希的是解析后的绝对路径），所以同一个目录在每个进程里算出的端点完全一样；`0o700`
的子目录是**补回来的隔离** —— 端点在共享的临时目录里，别人能连上就等于能冒充写者。
Windows 不受影响：命名管道不进文件系统。

探活（清残留的前置判断）同时改了判据。写者被 `SIGKILL` 会在磁盘上留下 socket 文件，
不删就**没人能再当写者**；但「有人在听」只能用**纯 `connect`** 判断，不能拿 `_hello`
打招呼 —— 打招呼是**有状态**的，写者一忙（正在做一轮读改写），那句问候就排到超时才
被读成「没人」，于是**活写者的端点被当残骸删掉**，下一个进程绑上来就是两个写者写同一
个目录。3.14 的 `Client(authkey=None)` 不再被补成进程默认钥匙，构造函数里只剩一次即时
的 `connect(2)`：有人在听就成功，是残骸就当场拒绝。

状态见[路线图](../roadmap.md)。
