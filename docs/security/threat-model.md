# 运行时威胁模型

> **适用范围**：`onconf` v1.0.0（2026-10-04 的工作区状态）
> **性质**：描述**当前实现**的信任边界与已知缺口，不是设计愿景。
> 设计与语义问题见[设计稿索引](../design/index.md)。
>
> 本文里每条判断都给出了代码依据。**行号会随开发漂移，符号名不会** —— 引用时以符号名为准。

---

## 1. 一句话结论

`onconf` 的威胁面**不是网络，而是本地文件系统与并发**。

它默认不开**网络端口**、不 spawn 子进程、不对配置内容做 `eval` / `exec` / `pickle`。
序列化入口按后端分开：YAML 只走 `yaml.safe_load` / `safe_load_all`，JSON 走 `json.loads`，
TOML 走 `tomllib.loads`，`.env` 是纯行扫描。
**引擎不开任何监听**：没有端点、没有 IPC、没有子进程（T10）。

**并发丢更新**的边界写在 T4：进程内由一把内存锁收口，**跨进程明确接受**（「一个目录一个
写者」是调用方的部署责任）；**持久性**与**机密性**（T5 非原子写、T6 文件权限）
分别由原子写与 `0600` 权限位守护。
因此当前版本**不适合存放需要严格保密的密钥**，也不替多进程之间的竞争兜底。

---

## 2. 资产

| 资产 | 说明 | 被破坏的后果 |
|---|---|---|
| **值文件的字节完整性** | 用户手写的 JSON / YAML / TOML / `.env`，含注释、缩进、键序 | 用户的手写内容丢失（本项目的核心卖点就是「未触及的字节逐字不动」） |
| **配置值的机密性** | `.env` / `settings.*` 里常见密码、令牌、连接串 | 凭据泄漏 |
| **配置值的可用性** | 程序启动依赖它 | 程序起不来 |
| **词表与 JSON Schema** | `<home>/schema/settings.json`，库自己的资产 | 编辑器补全失效；若被误提交则泄漏「存在哪些键、默认值是什么」 |
| **开发者机器** | 库在开发者的用户态下运行 | 任意文件读写 |

## 3. 信任边界

```text
   开发者代码（可信）                 磁盘上的配置文件（不可信）
   ┌──────────────┐                 ┌────────────────────────┐
   │ conf(...)    │                 │ settings.json / .yaml  │
   │ 声明 + 默认值 │                 │ settings.env           │
   └──────┬───────┘                 │ schema/settings.json   │
          │                         └───────────┬────────────┘
          ▼                                     │ 解析（safe_load / json / tomllib / 行扫描）
   ┌─────────────────────────────────────────────▼──────────┐
   │                      Engine                             │
   │  home ← home= 参数 / ONCONF_HOME / ./conf  （可信输入） │
   │  值文件 ← file_name / file_type / 键内嵌路径（包含性校验）│
   │  ←──── 读 / 对账 / 外科手术式回写 ────→                  │
   └─────────────────────────────────────────────┬──────────┘
                                                 │ 原子写（fsync + os.replace）
                                                 ▼
                                        值文件 + schema
```

`onconf build` / `onconf sync`（命令行）是另一条入口：它只 `ast.parse` 项目里的
`*.py`、读 `conf(...)` 的实参，**不 import、不 eval**，然后走同一个引擎落盘。

### 边界判定

| 输入 | 可信？ | 理由 |
|---|---|---|
| `home=` 参数、`ONCONF_HOME` | **可信** | 由开发者/部署方控制；库不做目录包含性校验（T2） |
| 配置文件的**内容** | **不可信** | 可能来自部署、模板、他人提交 |
| 值文件**名字**（`file_name`） | **不可信** | 过包含性校验：纯文件名、无分隔符、无 `..`、非绝对、解析后仍在 `<home>` 内（T1） |
| 多文件键里的**路径段** | **不可信** | 同上；多文件关闭时根本不参与解析（T1） |
| 键名（`conf("a.b.c")`） | 可信但**不该拼进路径** | 多文件关闭时不拼；开启时只有 `:` 左边那段过校验后才拼（T1） |
| 命令行扫描到的**项目源码** | 不可信，但只做语法分析 | `ast.parse` 不执行任何代码；扫不动的调用不猜、直接列为问题（T13） |

## 4. 威胁清单

严重度：🔴 高 / 🟠 中 / 🟡 低 / ✅ 已缓解或不适用

### T1 — 外部字符串路径穿越 ✅ 已缓解（包含性校验）

**攻击设想**：声明 `conf("../../etc/passwd", 1)`，或在多文件模式下声明
`conf("../../etc/passwd:x", 1)`，诱导库把值写到配置目录之外。

**结论：由包含性校验守护。** 所有「外部字符串 → 路径」的转换只经过一个模块
（`src/onconf/_paths.py`），五条规则缺一不可：

1. `file_name` 必须是**纯文件名**（多文件的路径段必须是相对路径）；
2. 不含 `\`、不带盘符形态（`C:`）；
3. 路径分量里没有空段、`.`、`..`；
4. 不接受空字符串与 NUL；
5. **解析后必须仍在 `<home>` 之内** —— 既有符号链接指向外侧时也会被 `resolve()` 展开而拒绝。

**守护的是目的，不是某一种手段**：值文件路径与键内嵌路径都过包含性校验
（见[路线图 009](../roadmap/index.md)）。

**守护**：`tests/test_security_invariants.py` 里逐条覆盖（非法文件名、含 `..` / 绝对路径 /
分隔符的键内嵌路径、行为级「配置目录外无任何新文件」），另有 `tests/test_paths.py` 与
`tests/test_engine.py::TestMultiFile`。多文件**关闭**时 `:` 不参与解析，行为级回归原样成立。

---

### T2 — 通过 `ONCONF_HOME` 重定向写入位置 🟡 接受

**攻击设想**：攻击者能设置进程环境变量，把配置目录指向敏感位置，再借库的写入破坏目标文件。

**结论：接受为可信输入。** `_engine.default_home()` 直接取环境变量并 `.resolve()`；
`Engine.__init__` 对 `home=` 参数同样只 `.resolve()`，**不做目录包含性检查**。

`.resolve()` 只做路径规范化（消除 `..`），**不是安全边界**。

**为什么不修**：配置目录必须可由部署方指定，这是功能而非缺陷。真正需要的是**文档约束**：
不要让不可信来源控制这个环境变量。生产环境里应把它当作与 `PATH` 同级的可信配置。

**若要收紧**（列为候选改进）：允许 `home` 落在某个显式允许的根目录之下，越界即报错。

---

### T3 — 符号链接被替换 🟡 低（行为与「跟随」相反）

**攻击设想**：把 `settings.json` 换成指向 `~/.ssh/authorized_keys` 的符号链接，
诱导库把值写进那个目标。

**结论：不会写到链接目标。** 落盘走 `_engine._atomic_write_text`：先在**同目录**建临时文件，
写完 `fsync` 之后 `tmp.replace(path)`（即 `os.replace`）。rename 作用于**目录项本身**，
所以被替换掉的是那条符号链接 —— 链接位置变成一个普通文件，链接目标一个字节都不会被碰。
实测（2026-10-04）：写入后 `link.is_symlink()` 为假，链接目标内容不变，新内容落在原链接路径上。

**残余风险（取舍而非漏洞）**：这会**断开用户特意设置的符号链接**（例如把 `settings.json`
链到别处的共享配置）。外科手术式回写本就要求「改动只落在这一份文件上」，要共享配置请让
两份文件各自独立，或用部署工具同步。这个行为**没有**专项回归测试守护，改落盘路径时要重读本条。

---

### T4 — 并发写丢更新 / 写坏文件 🟠 接受（写权限归调用方）

**攻击设想**：同一台机器上起了两份程序（或一份程序的多个模块），都写同一个值文件。
读-改-写之间没有跨进程互斥 → 后写者覆盖先写者；极端情况下写出内容交错的文件。

**结论：进程内已缓解，跨进程明确接受。** 引擎不再提供跨进程互斥（没有锁、没有独立
写者进程、没有 IPC）：**同一时刻只有一个写者是调用方的部署责任**。

进程内那一层由引擎兜住：一份值文件一把**纯内存**的锁，同一进程里的多个实例、多个线程
共用它，所以它们不会丢彼此的更新。实现见 `_engine._instance_lock`，回归见
`tests/test_engine.py::TestInstanceConcurrency`。

跨进程那一层只做两件事，都不是互斥：

- **写权限由进程树定**：创建实例的进程是属主，`fork` / `spawn` 派生出来的进程只读，
  想写就当场抛 `ConfError`。这挡住的是「子进程以为自己也能写」，挡不住「两个平级进程
  都自称属主」。
- **替换带界重试**：Windows 上 `os.replace` 撞上并发读者会失败，读者不参与互斥，
  所以由替换这一侧等几百毫秒（见 `_engine._replace_with_retry`）。

**残余风险**：两个平级进程同时写同一个值文件会**丢更新**，而且没有任何运行期机制
会阻止它。正确姿势是起进程之前用 `onconf sync` 把配置落好、运行期全部只读；
口径见[并发模型](../design/concurrency.md)。

### T5 — 非原子写导致文件被截断 ✅ 已缓解

**攻击设想**：进程在写入中途被杀、或机器断电 → 值文件只剩半截，
而这个文件正是程序启动要读的。

**结论：已缓解。** 值文件与词表都经 `_engine._atomic_write_text`：**同目录**临时文件
（`os.replace` 只在同一文件系统内原子）→ 写入 + `fsync` → `os.replace` → `fsync` 父目录
（POSIX；Windows 不允许以 `O_RDONLY` 打开目录，跳过这一步）。行尾按文件原本的样子写回，
所以 Windows 上不会把用户的 LF 文件偷偷改成 CRLF。

**残余风险**：父目录那条 `fsync` 在 Windows 上没有等价物 —— 掉电后仍可能丢掉最后一次
rename。内容不会半截，只是可能退回上一版。

**守护**：落盘路径有回归测试。**没有**崩溃注入测试（那需要模拟文件系统），这一点如实记。

---

### T6 — 文件权限过宽导致凭据泄漏 ✅ 已缓解（POSIX）

**攻击设想**：`.env` 或 `settings.yaml` 里放数据库口令，
新建文件沿用系统 umask（POSIX 常见 022）→ 同组或其他用户可读。

**结论：已缓解。** 新建文件走 `tempfile.mkstemp`（POSIX 上就是 `0600`）；替换前若目标已存在，
则**沿用它原本的权限位**（`stat.S_IMODE`）—— 也就是**只对新文件收紧，不擅自改用户特意
放宽的权限**。审计文件同样按 `0600` 创建（`_log._append_file`）。

**残余风险**：Windows 上 `chmod` 只切换只读位，实际保护来自配置目录的 ACL；库也不做目录
权限校验 —— `settings.json` 里放明文口令，读得到目录的人就读得到它。

**缓解**：自己保证配置目录权限正确（例如建目录时就 `700`）。

---

### T7 — YAML 反序列化导致任意对象构造 / 代码执行 ✅ 已缓解

**攻击设想**：配置文件里放 `!!python/object/apply:os.system [...]` 之类的标签。

**结论：已缓解。** 代码只使用 `yaml.safe_load` 与 `yaml.safe_load_all`
（见 `_yaml_backend` 的 `loads()` 与 `find()` 实现）；**不存在** `yaml.load`、
`FullLoader`、`UnsafeLoader`。同时全库无 `eval` / `exec` / `pickle`。

**守护**：CI 的 bandit 扫描 + 回归测试（检查源码中不出现危险调用）。

---

### T8 — YAML 别名膨胀 / 「十亿笑声」DoS 🟡 低（未处理）

**攻击设想**：用锚点与别名构造指数级展开的 YAML，读配置时吃掉内存与 CPU。

**结论：未处理。** `safe_load` 只解决「不能构造任意对象」，**不限制别名展开规模**。

**当前判定为低**：配置文件是本地且由开发者/部署方提供的，不是公网输入。
若将来出现「读取他人提供的配置」的场景，这条要升级处理。

---

### T9 — 词表 / schema 泄漏「有哪些键、默认值是什么」 🟡 低（部分缓解）

**情形**：`<home>/schema/<file_name>.json` 由库整篇重写（这是设计决定），
里面会包含键名、说明与默认值（词表只记这三样）—— 而默认值有可能是占位密钥或内网地址。

**结论**：库不控制该文件是否被提交。仓库侧已通过 `.gitignore` 忽略 `/conf/`，
但这只覆盖**本仓库自己的**演示目录，不覆盖使用者的目录。

**建议**：使用方应把配置目录排除在版本控制之外；不要用真实密钥做默认值。

---

### T10 — 网络暴露 ✅ 已避免（不变量）

**结论**：`src/onconf/` 里**没有** `import socket`，没有任何 TCP / HTTP 客户端调用，
也从不监听任何东西 —— 没有端点、没有 IPC，连子进程都不起。
运行时依赖闭包只有 `pyyaml` 与 `rich`；跨语言的 HTTP 路线**判定不做**。

**这是一个必须保持的不变量**：配置库静默监听端口会被运维/安全软件盯上，
也可能被企业策略或沙箱拦截。任何「默认路径开端口」的改动都是安全回归。

### T12 — 日志泄漏配置值 🟠 中（已实现，接受为取舍）

**攻击设想**：日志里原样记着 `data=` / `old=` / `new=`，
于是 `.env` 里的口令、连接串跟着落进 `<home>/audit.log` 或调用方指定的落点。

**结论：记录里确实有真实值，这是有意为之。** 审计 90% 的价值就在「从什么变成什么」，
把值抹掉等于把审计废掉。已经做到的缓解：

- **文件出口恒写**（取舍本身：没有开关可退），但**控制台出口可以关**（`log_console`）；
- 审计文件只追加（`O_APPEND`）、按 **`0600`** 创建，**不创建自己的父目录**；
  **谁发起谁记账**，每个进程只写自己那几行；
- 字段是**白名单**（`item` / `file` / `origin` / `op` / `data` / `old` / `new` / `n` /
  `at` / `err` / `msg` / `reason` / `id`），不是把值对象整个 dump 出去；
- 键名 / 身份 / 调用点里的 CR / LF 会被折成可见转义 —— 否则一个换行就能往审计文件里
  **伪造出额外的记录行**。

**残余风险**：Windows 上 `chmod` 只切换只读位，审计文件的实际保护来自目录 ACL；
库**不做值脱敏**，也不去猜哪个键是密钥 —— 脱敏与加密是**调用方自己挂的钩子**
（`log_scrub` / `log_encode`），不是引擎自带的能力。要放真实凭据，就把配置目录整个排除在
版本控制与日志采集之外，或者挂上自己的钩子。
另外，同一个目录上多个进程会往同一个文件里追加，而 `txn` 是按进程编号的 ——
文件里可能出现两个同号的批次（每行带 pid，读的人据此分辨）。默认**不轮转**，所以没有
「并发改名撞车」这条失败模式；调用方自己给的轮转策略要自己保证同样的性质。

**守护**：`tests/test_log.py::TestFileSink::test_the_audit_file_is_private`（POSIX 上断言
`0600`）、`test_the_file_sink_never_creates_its_parent`（审计不造目录）、
`test_key_names_never_become_audit_paths`（审计文件名固定，不参与键名拼接）、
`TestIdentityIntegrity::test_a_newline_in_a_key_cannot_forge_a_line`（换行折成转义）。

### T13 — 命令行：静态扫描与删除动作 🟡 低（已设计缓解）

**攻击设想**：命令行扫到不可信的源码（第三方仓库、被别人改过的声明文件），
（a）借扫描执行任意代码；（b）凭一份不完整的期望集把用户手写的键删掉。

**结论：两条都被设计挡住。**

- **不执行代码**：扫描只做 `ast.parse` + `ast.literal_eval` —— 不 `import`、不 `eval`；
  求不出字面量的调用**不猜**，逐条列成问题。
- **期望集不完整就不删**：`sync` 遇到任何读不懂的调用时**拒绝删除任何键**并以非 0 退出；
  加 `--no-clean` 只补缺、不删除。`build` 是完整重建、会丢手改内容，但由人显式发起，
  `--dry-run` 可以先看一遍，`--path` 可以重建到别处、原目录一个字节不动。
- **删除动作受 T1 约束**：只可能删 `<home>` 之内、且**当前声明集引用到的**值文件里的键；
  未被引用的值文件不会被加载，也就不会被清理。

**残余风险**：`build` 的语义就是「以声明为准重写值文件」，它会丢掉该文件里手改的键、
注释与格式（值文件是用户的资产）。命令行会列出重建了哪些文件、多少键，但**不替你备份**。

**守护**：`tests/test_cli.py`（`--dry-run` 一个字节不写、期望集不完整时拒绝删除、
`--no-clean` 保留未声明的键、非字面量列为问题、`--help` 不写文件）。

## 5. 不变量与守护方式

以下性质必须长期成立。它们已写入
[`SECURITY.md`](https://github.com/HanYang06/OnConf/blob/main/SECURITY.md)
（仓库根文件不在本站点的 `docs_dir` 内，只能给绝对链接），并由回归测试守护：

| 不变量 | 守护 |
|---|---|
| 默认路径不开网络**端口**、不起子进程 | 源码静态检查（`src/` 无 `import socket`、无 TCP / HTTP 客户端、无 `subprocess`） |
| YAML 只用 `yaml.safe_load` / `safe_load_all` | 源码静态检查（无 `yaml.load` / `FullLoader` / `UnsafeLoader`） |
| 无 `eval` / `exec` / `pickle` | 源码静态检查 |
| **外部字符串只经一道包含性校验到达路径** | `tests/test_paths.py` 逐条规则 + `tests/test_security_invariants.py`（非法文件名 / 路径段、行为级「配置目录外无任何新文件」）+ `tests/test_engine.py::TestMultiFile` |
| **命令行不执行项目代码** | `tests/test_security_invariants.py` 的源码静态检查（`src/` 无 `eval` / `exec` / `__import__`）；扫描只做 `ast.parse` |
| 落盘后 `$schema` 指针存在 | `tests/test_engine.py`（只对能吃下成员的后端：JSON / YAML；多文件按各自层级算相对路径） |
| 审计文件只追加、`0600`、不造父目录，且文件名不来自键名 | `tests/test_log.py`（POSIX 断言权限位；另断言配置目录外无新文件） |
