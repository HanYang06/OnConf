# 运行时威胁模型

> **适用范围**：`onconf` v1.0.0（2026-10-04 的工作区状态）
> **性质**：描述**当前实现**的信任边界与已知缺口，不是设计愿景。
> 设计与语义问题见 [`../design/DESIGN.md`](../design/DESIGN.md)。
>
> 本文里每条判断都给出了代码依据。**行号会随开发漂移，符号名不会** —— 引用时以符号名为准。

---

## 1. 一句话结论

`onconf` 的威胁面**不是网络，而是本地文件系统与并发**。

它默认不开**网络端口**、不 spawn 子进程、不对配置内容做 `eval` / `exec` / `pickle`。
序列化入口按后端分开：YAML 只走 `yaml.safe_load` / `safe_load_all`，JSON 走 `json.loads`，
TOML 走 `tomllib.loads`，`.env` 是纯行扫描。
**唯一的「监听」是本机同用户的端点**：写者的命名管道（Windows）或 Unix socket 文件
（POSIX，落在 `<home>/schema/settings.sock`），不占端口、不出机器（T10）。

**并发丢更新这一项已经关闭**（专职写者收口，见 T4；OS 锁 + 锁内按需重读退居兜底）。
原先敞着的**持久性**与**机密性**两处（T5 非原子写、T6 文件权限）已经关闭。
仍然敞着的是**跨进程规则 1 的语义边界**：写者的声明集不是持久状态，写者一换人清理基准
就重置（DESIGN §32.4）。
因此当前版本**可以多进程并发写，但仍不适合存放需要严格保密的密钥**。

## 2. 资产

| 资产 | 说明 | 被破坏的后果 |
|---|---|---|
| **值文件的字节完整性** | 用户手写的 JSON / YAML / TOML / `.env`，含注释、缩进、键序 | 用户的手写内容丢失（本项目的核心卖点就是「未触及的字节逐字不动」） |
| **配置值的机密性** | `.env` / `settings.*` 里常见密码、令牌、连接串 | 凭据泄漏 |
| **配置值的可用性** | 程序启动依赖它 | 程序起不来 |
| **词表与 JSON Schema** | `<home>/schema/settings.json`，库自己的资产 | 编辑器补全失效；若被误提交则泄漏「存在哪些键、默认值是什么」 |
| **开发者机器** | 库在开发者的用户态下运行 | 任意文件读写 |

## 3. 信任边界

```text
   开发者代码（可信）                 磁盘上的配置文件（不可信）
   ┌──────────────┐                 ┌────────────────────────┐
   │ conf(...)    │                 │ settings.json / .yaml  │
   │ 声明 + 默认值 │                 │ settings.env           │
   └──────┬───────┘                 │ schema/settings.json   │
          │                         └───────────┬────────────┘
          ▼                                     │ 解析（safe_load / json / tomllib / 行扫描）
   ┌─────────────────────────────────────────────▼──────────┐
   │                      Engine                             │
   │  home ← home= 参数 / ONCONF_HOME / CWD   （可信输入） │
   │  值文件 ← 固定白名单文件名                  （无键名拼接）│
   │  ←──── 读 / 对账 / 外科手术式回写 ────→                  │
   └─────────────────────────────────────────────┬──────────┘
                                                 │ 原子写（fsync + os.replace）
                                                 ▼
                                        值文件 + schema
```

### 边界判定

| 输入 | 可信？ | 理由 |
|---|---|---|
| `home=` 参数、`ONCONF_HOME` | **可信** | 由开发者/部署方控制；库不做包含性校验 |
| 配置文件的**内容** | **不可信** | 可能来自部署、模板、他人提交 |
| 配置文件的**路径** | 半可信 | 由固定白名单推导，键名不参与 |
| 键名（`conf("a.b.c")`） | 可信但**不该拼进路径** | 当前实现确实没有拼（见 T1） |

## 4. 威胁清单

严重度：🔴 高 / 🟠 中 / 🟡 低 / ✅ 已缓解或不适用

### T1 — 键名路径穿越 ✅ 不适用

**攻击设想**：声明 `conf("../../etc/passwd", 1)`，诱导库把值写到配置目录之外。

**结论：当前实现不可能发生。** 值文件路径由固定白名单推导，键名只用于文件**内部**的寻址：

- `_engine._VALUES_CANDIDATES = ("settings.yaml", "settings.yml", "settings.json", "settings.toml", "settings.env")`
- `_engine._pick_values_file()` 只在这**五个**常量之间选择
- schema 路径是 `home / SCHEMA_DIR / f"{values_path.stem}.json"`，`stem` 同样来自白名单

**守护**：`tests/test_security_invariants.py` 里有对应的回归测试。若将来引入「每个键一个文件」之类的布局，这条必须重新评估。

---

### T2 — 通过 `ONCONF_HOME` 重定向写入位置 🟡 接受

**攻击设想**：攻击者能设置进程环境变量，把配置目录指向敏感位置，再借库的写入破坏目标文件。

**结论：接受为可信输入。** `_engine.default_home()` 直接取环境变量并 `.resolve()`；
`Engine.__init__` 对 `home=` 参数同样只 `.resolve()`，**不做目录包含性检查**。

`.resolve()` 只做路径规范化（消除 `..`），**不是安全边界**。

**为什么不修**：配置目录必须可由部署方指定，这是功能而非缺陷。真正需要的是**文档约束**：
不要让不可信来源控制这个环境变量。生产环境里应把它当作与 `PATH` 同级的可信配置。

**若要收紧**（列为候选改进）：允许 `home` 落在某个显式允许的根目录之下，越界即报错。

---

### T3 — 符号链接被替换 🟡 低（行为与「跟随」相反）

**攻击设想**：把 `settings.json` 换成指向 `~/.ssh/authorized_keys` 的符号链接，
诱导库把值写进那个目标。

**结论：不会写到链接目标。** 落盘走 `_engine._atomic_write_text`：先在**同目录**建临时文件，
写完 `fsync` 之后 `tmp.replace(path)`（即 `os.replace`）。rename 作用于**目录项本身**，
所以被替换掉的是那条符号链接 —— 链接位置变成一个普通文件，链接目标一个字节都不会被碰。
实测（2026-10-04）：写入后 `link.is_symlink()` 为假，链接目标内容不变，新内容落在原链接路径上。
（早先版本走 `Path.write_text()`，那才会跟随链接；这条已随原子写一起改变。）

**残余风险（取舍而非漏洞）**：这会**断开用户特意设置的符号链接**（例如把 `settings.json`
链到别处的共享配置）。外科手术式回写本就要求「改动只落在这一份文件上」，要共享配置请让
两份文件各自独立，或用部署工具同步。这个行为**没有**专项回归测试守护，改落盘路径时要重读本条。

### T4 — 并发写丢更新 / 写坏文件 ✅ 已缓解

**攻击设想**：同一台机器上起了两份程序（或一份程序的多个模块），都写同一个值文件。
读-改-写之间没有任何互斥 → 后写者覆盖先写者；极端情况下写出内容交错的文件。

**结论：已缓解。** 常规路径是**专职写者**：一个配置目录上只有抢绑到端点的那个进程做
读改写，其余进程把请求交给它，磁盘上的读-改-写因此天然串行（T4 的实测见下）。
端点这条路不通时退回 **拿锁 → 锁内重读 → 读改写 → 释放锁**：

- 锁是**操作系统**的锁（Windows `msvcrt.locking`、其它平台 `fcntl.flock`），
  所以进程崩溃时由 OS 释放 —— 不存在「陈旧的锁文件」这个经典问题，
  也不需要心跳、超时判定或「谁的 PID 还活着」的探测。
- 拿不到锁会在超时（默认 10 秒）后抛 `LockTimeoutError`，而不是静默写坏文件。
- 指纹必须同时看**两个**文件：只看值文件会漏掉「只登记不给值」这类提交
  （它不碰值文件，却会改词表），漏掉之后写回去会把别人刚登记的键挤掉。

设计依据见 DESIGN §31；真进程实测见 `tests/test_engine.py::TestRealProcesses`
（四个真进程各写各的键，一个都不丢）。

**残余风险**：上述实测覆盖的是「各写各的键」，不是「N 个进程对**同一个键**并发递增、
最终值等于 N」这种同键竞争；后者当前**没有回归测试守护**。

**残余风险（写者进程内部）**：写者**自己**的调用没有和它的应答线程共用同一把锁 ——
`Engine.read` / `_commit_local` 在 `_is_writer()` 时直接就地执行，而远端会话走
`Owner.submit`（持 `Owner._lock`，注释里本来就写着「主线程 + 应答线程也要互斥」）。
文件一致性仍由 OS 锁兜着，但**同进程两个 fd 的操作系统锁同样会互相冲突**
（2026-10-04 实测：第二次 `exclusive()` 在超时后抛 `LockTimeoutError`），所以
「写者主线程正在落盘 + 会话线程同时提交」时，其中一边会等满 `lock_timeout` 后报错；
同一窗口里 `_decls` / `_pending` / `_facts` 也是可竞争的。修法很短（让就地那条路也走
`Channel.submit`，统一进 `Owner._lock`），但它改的是并发模型，**动手前要单独评估**。

### T5 — 非原子写导致文件被截断 ✅ 已缓解

**攻击设想**：进程在写入中途被杀、或机器断电 → 值文件只剩半截，
而这个文件正是程序启动要读的。

**结论：已缓解。** 值文件与词表都经 `_engine._atomic_write_text`：**同目录**临时文件
（`os.replace` 只在同一文件系统内原子）→ 写入 + `fsync` → `os.replace` → `fsync` 父目录
（POSIX；Windows 不允许以 `O_RDONLY` 打开目录，跳过这一步）。行尾按文件原本的样子写回，
所以 Windows 上不会把用户的 LF 文件偷偷改成 CRLF。

**残余风险**：父目录那条 `fsync` 在 Windows 上没有等价物 —— 掉电后仍可能丢掉最后一次
rename。内容不会半截，只是可能退回上一版。

**守护**：落盘路径有回归测试。**没有**崩溃注入测试（那需要模拟文件系统），这一点如实记。

---

### T6 — 文件权限过宽导致凭据泄漏 ✅ 已缓解（POSIX）

**攻击设想**：`.env` 或 `settings.yaml` 里放数据库口令，
新建文件沿用系统 umask（POSIX 常见 022）→ 同组或其他用户可读。

**结论：已缓解。** 新建文件走 `tempfile.mkstemp`（POSIX 上就是 `0600`）；替换前若目标已存在，
则**沿用它原本的权限位**（`stat.S_IMODE`）—— 也就是**只对新文件收紧，不擅自改用户特意
放宽的权限**。写者的认证码 `schema/settings.key` 同理，而且因为硬链接共享 inode，`chmod`
必须在 `os.link` **之前**做。

**残余风险**：Windows 上 `chmod` 只切换只读位，实际保护来自配置目录的 ACL；库也不做目录
权限校验 —— `settings.json` 里放明文口令，读得到目录的人就读得到它。

**缓解**：自己保证配置目录权限正确（例如建目录时就 `700`）。

### T7 — YAML 反序列化导致任意对象构造 / 代码执行 ✅ 已缓解

**攻击设想**：配置文件里放 `!!python/object/apply:os.system [...]` 之类的标签。

**结论：已缓解。** 代码只使用 `yaml.safe_load` 与 `yaml.safe_load_all`
（见 `_yaml_backend` 的 `loads()` 与 `find()` 实现）；**不存在** `yaml.load`、
`FullLoader`、`UnsafeLoader`。同时全库无 `eval` / `exec` / `pickle`。

**守护**：CI 的 bandit 扫描 + 回归测试（检查源码中不出现危险调用）。

---

### T8 — YAML 别名膨胀 / 「十亿笑声」DoS 🟡 低（未处理）

**攻击设想**：用锚点与别名构造指数级展开的 YAML，读配置时吃掉内存与 CPU。

**结论：未处理。** `safe_load` 只解决「不能构造任意对象」，**不限制别名展开规模**。

**当前判定为低**：配置文件是本地且由开发者/部署方提供的，不是公网输入。
若将来出现「读取他人提供的配置」的场景，这条要升级处理。

---

### T9 — 词表 / schema 泄漏「有哪些键、默认值是什么」 🟡 低（部分缓解）

**情形**：`<home>/schema/settings.json` 由库整篇重写（这是设计决定，§18.6），
里面会包含键名、类型、默认值 —— 而默认值有可能是占位密钥或内网地址。

**结论**：库不控制该文件是否被提交。仓库侧已通过 `.gitignore` 忽略 `/conf/`，
但这只覆盖**本仓库自己的**演示目录，不覆盖使用者的目录。

**建议**：使用方应把配置目录排除在版本控制之外；不要用真实密钥做默认值。

---

### T10 — 网络暴露 ✅ 已避免（不变量）

**结论**：`src/onconf/` 里**没有** `import socket`，没有任何 TCP / HTTP 客户端调用，
也从不监听网络端口 —— IPC 用的是标准库 `multiprocessing.connection`
（`_owner.claim` → `ipc.Listener(address)`），不是 HTTP。
`httpx` **已从运行时依赖里移除**：跨语言的 HTTP 路线**判定不做**（DESIGN §22 顶部的推翻
说明），运行时依赖闭包只剩 `pyyaml` 与 `rich`。此前那句「为 M2/M3 的 IPC 预留」早随
IPC 交付而过期 —— 交付时选的是标准库 `multiprocessing.connection`，不是 HTTP。

写者确实**会监听**，但只监听**本机同一用户**可达的端点：Windows 是命名管道
（`\\.\pipe\onconf-<配置目录哈希>`），POSIX 是配置目录里的 Unix socket 文件
（`<home>/schema/settings.sock`）。两者都不是网络端口，也出不了本机。

POSIX 还有一支：路径超过 `sun_path` 上限（104 字节）时，端点搬到
`<tmpdir>/onconf-<uid>/onconf-<配置目录哈希>.sock`，那个子目录是 **`0700`**（每次用
之前都 `chmod` 确认一遍）。这是**补回来的隔离** —— 端点在共享的临时目录里，别人能连上
就等于能冒充写者。取舍与实测见 DESIGN §32.9。

**这是一个必须保持的不变量**：配置库静默监听端口会被运维/安全软件盯上，
也可能被企业策略或沙箱拦截（DESIGN §26.3）。任何「默认路径开端口」的改动都是安全回归。

### T12 — 审计日志泄漏配置值 🟠 中（已实现，接受为取舍）

**攻击设想**：日志 / 审计文件里原样记着 `data=` / `old=` / `new=`，
于是 `.env` 里的口令、连接串跟着落进 `<home>/audit.log` 或用户选的日志文件。

**结论：记录里确实有真实值，这是有意为之。** 审计 90% 的价值就在「从什么变成什么」
（§20.2），把值抹掉等于把审计废掉。已经做到的缓解：

- **去向由调用方选**，`audit` 默认**关**：不开就没有审计文件（但强制日志仍在，
  它默认去 `stderr`，不落盘）；
- 审计文件只追加（`O_APPEND`）、按 **`0600`** 创建；执行点（写者）是常规路径上唯一的
  写者，客户端补的只是自己的日志、**不重复写审计文件**；
- 字段是**白名单**（`item` / `file` / `origin` / `op` / `data` / `old` / `new` / `n` /
  `at` / `err` / `msg` / `reason` / `id`），不是把值对象整个 dump 出去；
- 键名 / 身份 / 调用点里的 CR / LF 会被折成可见转义 —— 否则一个换行就能往审计文件里
  **伪造出额外的记录行**。

**残余风险**：Windows 上 `chmod` 只切换只读位，审计文件的实际保护来自目录 ACL；
库**不做值脱敏**，也不去猜哪个键是密钥。要放真实凭据，就别开 `audit`，
或者把配置目录整个排除在版本控制与日志采集之外。
另外，「唯一写者」只在**只有一个进程开 `audit`** 时成立：同一目录上第二个引擎也开
`audit=True` 时，它本地的记录会追加进同一个文件，而 `txn` 是按进程编号的
（DESIGN §32.8 的「已知边界」）。轮转同理 —— 它是为单写者设计的。

**守护**：`tests/test_audit.py::TestSinks::test_the_audit_file_is_private`（POSIX 上断言
`0600`）、`test_key_names_never_become_audit_paths`（审计文件名固定，不参与键名拼接）、
`TestOriginIntegrity::test_a_newline_in_a_key_cannot_forge_a_line`（换行折成转义）。

## 5. 不变量与守护方式

以下性质必须长期成立。它们已写入
[`SECURITY.md`](https://github.com/HanYang06/OnConf/blob/main/SECURITY.md)
（仓库根文件不在本站点的 `docs_dir` 内，只能给绝对链接），并由回归测试守护：

| 不变量 | 守护 |
|---|---|
| 默认路径不开网络**端口** | 源码静态检查（`src/` 无 `import socket`、无 TCP / HTTP 客户端）；端点只落在本机命名管道 / Unix socket |
| YAML 只用 `yaml.safe_load` / `safe_load_all` | 源码静态检查（无 `yaml.load` / `FullLoader` / `UnsafeLoader`） |
| 无 `eval` / `exec` / `pickle` | 源码静态检查 |
| 键名不参与路径拼接 | 行为测试：用含 `../` 的键名写入，断言配置目录之外无任何变化 |
| 落盘后 `$schema` 指针存在 | `tests/test_engine.py`（只对能吃下成员的后端：JSON / YAML） |
| 审计文件只追加、`0600`，且文件名不来自键名 | `tests/test_audit.py`（POSIX 断言权限位；另断言配置目录外无新文件） |
